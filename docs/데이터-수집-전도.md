# 데이터 수집 전도(全圖) — 어디서 어떻게 당겨오나

> 사장님 2026-09-04 「지금 어디서 어떻게 당겨오는지를 써봐. 어떤 걸 어디에 연결, 어떻게 구현하고. **올인할 수 있는 가능성**하고 그런 것들을 다 감안하고.」

이 문서 = **원천 → 파이프라인 → 출력(ERP·시트·Firestore) → 앱**을 한 장에 잇는다. 원자 «칸별» 원천은 [원자-원천지도](원자-원천지도.md), 단계 «세부»는 [자동동기-매뉴얼](자동동기-매뉴얼.md)에 있고, 여기는 **전 구간을 연결·구현·현재상태로** 본다.

## 0. 한 줄 / 큰 그림 — ★방법이 바뀌었다(2026-09-04)

> 사장님 2026-09-04 「이제는 **외부 시트와 우리가 제공한 공급사 시트를 읽어서 Firestore에 저장하고, 그걸 판매시트에 내려주는** 방식으로 바뀌었잖아.」

**새 방법 = Firestore가 원자의 «집». 판매시트는 거기서 내려주는 출력이다.**

```
외부 공급사 시트 + 우리 제공 공급사 시트(정제시트)
   │  읽어서 정제 (30분마다)
   ▼
★ Firestore products  (원자 = 차번 키 · 구조적 유일 · «저장 정본»)      ← 여기가 집
   │
   ├──⑯ make-sample──▶  판매시트 4탭(상품리스트·손오공구독·픽업구독·오플구독)   ← 내려주는 출력
   └──직접 읽음─────▶  파인더(상품찾기)                                    ← ERP 화면
```

★핵심: **원자는 Firestore 한 곳에 있고, 판매시트도 파인더도 «거기서» 나온다.** 화면이 시트를 다시 세거나 따로 읽지 않는다 → 숫자가 갈라질 수 없다.

**⚠ 지금은 과도기 — RTDB가 아직 중간에 있다.** 옛 경로(정제시트→판매시트⑥→ERP v4/products⑦)가 원자를 여전히 RTDB에 채우고, ⑭ 미러가 그걸 Firestore로 베낀 뒤 ⑯이 판매시트로 내린다. 즉 **실배선은 아직 `시트→정제→v4/products(RTDB)→⑭ 미러→Firestore→⑯ 판매시트`**다. 목표(엔드게임)는 RTDB를 걷어 **`시트→Firestore 직접→판매시트`**로 짧게 만드는 것 — RTDB 제거(§5)가 끝나면 완성된다.

```
[지금·과도기]  시트→정제→⑥판매시트→⑦ v4/products(RTDB)→⑭ Firestore→⑯ 판매시트(재발행)
[목표·엔드게임] 시트→정제→Firestore products →(⑯)→ 판매시트 · 파인더 직접
```

## 3. 어디에 쓰나 — Firestore가 집, 나머지는 출력

```
★ Firestore products (차번=docId, 유일, 저장 정본) ─┬─⑯ make-sample──▶ 판매시트 4탭 (1Y1Mx…)
                                                    └─직접 읽음────────▶ 파인더(상품찾기)
             ▲
             │ ⑭ 미러 (과도기: RTDB v4/products → Firestore)
        v4/products(RTDB)  ← ⑥ 판매시트→⑦ ERP 로 채워짐 · 걷어낼 대상
```

- **Firestore products** — 차번=문서키라 중복 «구조적으로» 불가. **원자의 집**이자 대수 정본. **파인더가 지금 여기를 직접 읽는다**(비용절감·§5). 값에서 원가·수수료·차대번호·계좌는 걷어내(미러가) 노출 안전.
- **판매시트 4탭**(`1Y1Mx…`) — 사람이 보는 상품 목록 = **Firestore에서 내려준 출력**(⑯ `make-sample-sheet-google --main`이 Firestore를 읽어 「집안 서식」으로 발행). 탭마다 열·요금블록이 다르다(상품리스트=개월별 · 구독=반납/인수형 · 오플=km별). 대수 = 차번중복 빼고 셈, Firestore와 같아야 한다.
- **v4/products(RTDB)** — 과도기의 중간 저장. ⑥(판매시트)→⑦(ERP)로 채워지고 ⑭이 Firestore로 미러. **RTDB 제거의 대상**이다(§5) — 없어지면 원자가 처음부터 Firestore로 간다.
- ⚠ **⑥ vs ⑯** — ⑥은 정제시트로 4탭을 «단순 서식»으로 쓰고(과도기 잔재), ⑯이 그 위를 Firestore값·집안서식으로 «재발행»한다. ⑯이 실패하면 시트는 ⑥의 단순 서식으로 남는다. 엔드게임에선 ⑥이 빠지고 ⑯만 남는다.

## 5. 앱이 읽는 길 — RTDB → Firestore 전환 중

```
파인더(상품찾기)  ──▶  Firestore products      ★1단계 완료·운영 LIVE (비용 끊김)
그 밖 서버 API    ──▶  RTDB v4/… (직접)         ⚠ 이관 남음 (인증 게이트·계약·정산·전자계약)
```

- **왜 옮기나** — RTDB는 대역폭 과금(월 30만원↑). 브라우저마다 붙던 파인더 구독이 비용을 몰았다 → Firestore(문서단위, 저렴)로. **파인더는 이미 옮겨 비용이 끊겼다.**
- **남은 것** — 서버 인증 게이트(`verifyActiveBearer`가 매 요청 RTDB `users/{uid}` 읽음)와 계약·정산·전자계약 서버 라우트 53개가 아직 RTDB 직접 읽기/쓰기. 이관은 [firestore-migration 메모리]의 순서(㉠게이트→㉡서버읽기→㉢파이프라인쓰기→㉣삭제)대로 단계로. **RTDB 삭제는 그 뒤.**
- v3=라이브 읽기 / v4=오버레이 쓰기 규칙은 [CLAUDE.md] 데이터·엔진 절 참고.

## 7. 올인 판단 — 지금 상태 · 남은 것 · 위험

**튼튼한 것(믿고 올인 가능):**
- 원천→정제→원자→시트/ERP가 **오케스트레이터 하나·미러표 하나**로 정리돼 있다. 입구가 갈리지 않는다.
- **대수 정본이 하나**(판매시트=원자=ERP=시트). 화면이 따로 안 센다.
- **불변/변동/정책 3분류**가 명확해 「한 번 박고 검수만」이 된다.
- 검사 단계(⑧~⑫)가 어긋남을 매 회차 «찾아» 남긴다. 관제탑으로 눈에 보인다.

**아직 손이 필요한 것:**
- **자동 미러는 4곳뿐**(아이카·오토플러스·이안카·아이언). 나머지(SA·리더스·스타·렌트존·우리캐피탈·오플)는 문패가 자기 시트 — 미러표에 넣어야 전자동.
- **차종마스터는 남의 몫** — 정제칸이 비면 원자가 빈다. 우리가 채우는 게 아니라 «검수»만.
- **정책 갭** — 원천이 안 주는 칸(면허기간·추가운전·긴급출동 등)은 오버라이드로 손입력. 매칭실패 3대·마스터갭 트림 75대는 사람이 한 번 확인.
- **RTDB→Firestore 이관 미완** — 파인더만 옮겼다. 서버 전 계층 이관 전엔 RTDB를 못 지운다(§5).

**위험(과거 실측):**
- **미배포 = 미수정** — 고쳐도 main·운영에 안 가면 「또 바뀌었다」가 된다. 화면 커밋은 `npm run check:deployed`로 센다.
- **화면 확인은 «카드가 그려지나»로** — 머리 숫자(742대)가 보여도 목록이 빌 수 있다. 데이터·로그로 대신하지 않는다.
- **커밋 제목을 믿지 마라** — diff와 화면을 본다(목록 접은 커밋 제목이 「되돌린다」였다).

**올인하려면 순서:** ① 자동 미러를 전 공급사로 넓힌다 → ② 정책 오버라이드·매칭실패를 「한 번」 다 박아 검수대기를 0으로 → ③ RTDB→Firestore 서버 이관 마치고 RTDB 삭제(월 30만원↓) → ④ 관제탑을 운영에 띄워 매일 «화면»으로 확인.

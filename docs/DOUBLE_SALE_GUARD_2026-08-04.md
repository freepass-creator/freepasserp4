# 이중판매 가드 — 트윈 경로 차단 (2026-08-04, Claude)

B2B 제한 오픈은 **영업자가 여럿 들어오는 첫 순간**이다. 혼자 쓸 때 안 터지던 게 여기서 터진다.
같은 차를 둘이 팔면 고객 하나는 차가 없고 정산은 2건 나온다 — 오픈이 만드는 위험 중 가장 비싸다.

`LAUNCH_QA_2026-07-30.md` 에 미해결로 남아 있던 세 건을 확인했다.

| QA | 내용 | 확인 결과 |
|---|---|---|
| RACE-1 | 세션 캐시를 읽어 남의 락을 못 봄 | **이미 닫힘** — `getFresh` 캐시 우회(settlement-engine.ts:305·327) |
| TWIN-1 | 같은 실물이 복수 코드 → 가드가 코드 단위라 무력 | **열려 있었음 → 이번에 닫음** |

## 1. 트윈은 이론이 아니라 지금 데이터다

실데이터 전수(읽기 전용, `tmp/audit-twin.mts`):

```
매물 1,086 · 판매 노출 가능 1,055
신원키(실번호판·VIN) 없음 508 — 합치지 않음

트윈 그룹 102 · 관련 레코드 271
★ 두 코드 이상이 동시에 판매 가능한 그룹  100
★ 그중 공급사가 서로 다른 그룹            42
서로 다른 코드로 계약이 갈린 트윈          0   ← 아직 사고는 안 났다
```

같은 번호판이 공급사별로 다른 코드를 달고 올라온다.

```
P:182하4240   엘씨렌트_182하4240[출고불가]  PT-0026_182하4240[출고가능]  RP021_182하4240[출고가능]
P:161호1257   엘씨렌트_161호1257[출고불가]  PT-0026_161호1257[출고가능]  RP021_161호1257[출고가능]
```

그리고 이미 한 건은 «계약이 붙은 코드의 쌍둥이가 아직 판매가능» 상태다.

```
P:54나7852   계약중=PT-0024_54나7852   아직 팔 수 있는 쌍둥이=RP021_54나7852[출고가능]
```

## 2. «목록에서 dedup 하니까 괜찮다» 는 착각이었다

`list('product')` 은 `dedupeProductsByVehicle` 로 신원당 1건만 보여 준다.
그래서 화면상으로는 쌍둥이가 안 보인다. 문제는 **승자 선정 규칙**이다.

```
rtdb-products.ts:123-125
  richness(가격·정책·차종·연식·사진) → product_code 유무 → updatedAt
```

**락 상태가 판정에 없다.** 결과:

```
① 영업자 A 가 코드 X 로 계약 → 락은 X 에만 찍힌다(syncVehicleLock 은 계약 매물 1건만 스탬프)
② 시트 동기화가 쌍둥이 Y 에 가격·사진을 채운다 → richness 역전
③ 목록 승자가 Y 로 바뀐다 — Y 의 vehicle_status 는 '출고가능'
④ 영업자 B 가 Y 를 보고 계약 → 가드는 product_code 비교 → X ≠ Y → 전부 통과
```

시트 동기화는 매일 돈다. ②는 가정이 아니라 일상 동작이다.

## 3. 무엇을 고쳤나

### TWIN-1 — 가드를 «코드»가 아니라 «실물» 단위로

`twinsOf(productCode)` 신설. 같은 `vehicleIdentity`(실번호판 → VIN 11자↑)를 가진 코드 집합을 만든다.

- **`listRawFresh` 를 쓴다.** 이유 둘: `list` 는 dedup 이 끝나 쌍둥이가 애초에 안 보이고,
  세션 캐시를 우회해야 다른 영업자가 방금 건 락을 본다(RACE-1 과 같은 이유).
- **신원키가 없으면 합치지 않는다.** '미정'·'-' 같은 placeholder 를 공유하는 서로 다른 차를
  한 대로 묶으면 멀쩡한 매물이 서로를 막는다. 실측 508건이 여기 해당한다.
- **조회 실패는 자기 코드만으로 degrade.** 권한·네트워크 오류가 정상 거래를 막는 쪽으로 실패하지 않는다.

적용 지점 둘 — 계약금 선점(`rivalDepositClaimFrom` 이 코드 집합을 받음)과 완료 직전 중복검사.

**쌍둥이에서는 «주인 있는 락»만 본다.** 주인 없는 `출고불가` 는 다른 공급사가 자기 재고에 건
수기 보류지 이 차가 팔렸다는 뜻이 아니다. 위험 트윈 100 중 42 가 공급사 교차라,
그것까지 막으면 멀쩡한 거래가 죽는다.

### FIN-1 — 완료 재시도 경로에 같은 가드를

`finalizeContractIfReady` 는 `ContractPanel.tsx:139` 배너에서 **직접** 불린다.
`applyStepCheck` 를 안 거치므로 가드가 통째로 빠져 있었다. 둘이 **같은 함수**(`duplicateSaleReason`)를
쓰도록 합쳤다 — 판정이 갈리면 한쪽만 뚫린다.

덤으로 `계약취소` 조기 반환도 넣었다. 취소된 계약에서 배너를 누르면 정산과 락이 되살아났다.

## 5. 시나리오 재확인 — 실제로 막히나

교차 영업자가 핵심이다. 계약목록은 **역할 스코프(영업자=본인 것만)** 라 B 는 A 의 계약을 못 본다.
따라서 실효 방어선은 매물의 락 스탬프다.

```
A 가 코드 X 에 계약금 선점 → syncVehicleLock 이 X 에 [계약중 · locked_by_contract=A] 스탬프
B 가 쌍둥이 코드 Y 에 계약금 선점 시도
  → twinsOf(Y) 가 X 를 같은 실물로 묶음
  → X 의 주인 있는 락 발견(A ≠ B)
  → "같은 차량이 다른 매물코드(X)로 이미 계약중 상태입니다(계약 A) — 중복 계약 불가"  ✅
```

돈이 오가기 전에 막힌다.

## 6. 남긴 것 — 의도적으로

**쓰기 확장은 안 했다.** `syncVehicleLock` 이 트윈 전체에 락을 스탬프하게 만들면
목록에서도 사라져 더 깔끔하지만, **다른 공급사의 매물 레코드에 쓰는 것**이라
`v4/products` 리프 권한 재검증이 먼저다(:678 주석의 permission_denied 함정과 같은 자리).
읽기 가드만으로 돈 사고는 막히므로 오픈 전에 감수할 위험이 아니다.

그래서 남는 증상: **팔린 차가 목록에 잠깐 보일 수 있다.** B 는 계약금 단계에서 차단되므로
금전 사고는 없고, 헛걸음이 생긴다. 오픈 후 처리.

**근원 제거(트윈 병합 배치)도 별도다.** 102 그룹 271 레코드를 `_merged_into` 로 접으면
가드가 필요 없어지는 게 정답이지만, 어느 코드를 남길지는 공급사 계약 관계 판단이라 사람이 정해야 한다.

## 7. 남은 구멍 — 원자성 (코덱스가 잡음, RACE-2)

커밋 직후 코덱스가 `scripts/sim-vehicle-lock.mts` 에 **14번 테스트**(동시 선점)를 추가했고 실패한다.
지적이 맞다. 이 가드는 **읽고-확인-쓰기**(check-then-act)라 같은 tick 의 두 요청은 둘 다 통과한다.

### 내 첫 판단은 틀렸다

「선점이 겹쳐도 완료 단계에 `duplicateSaleReason` 라는 독립 게이트가 있으니 완료는 하나만 된다」고
봤다. 확인해 보니 아니다(`tmp/sim-race-severity.mts`).

```
① 동시 선점        → 2건 모두 성공 · 매물 락 주인은 1개(마지막 쓰기 승)
② 동시 완료        → 2건 모두 계약완료 · 정산도 2건 생성    ← 진짜 이중판매가 된다
③ 순차 완료(현실)  → 두 번째 차단 "이미 완료된 계약(…)이 있는 차량입니다 — 이중판매 불가"  ✅
```

완료 게이트도 같은 check-then-act 라 동시에는 같이 뚫린다. **가설을 검증 없이 적지 않은 게 다행이다.**

### 실제로 뚫리려면

B 가 5/5 에 도달하려면 계약금 선점을 통과해야 한다(`getProgress` 가 전 단계를 요구). 즉 —

```
① 계약금 선점이 동시에 겹쳐 둘 다 '계약중'  (수백 ms 창)
② 그리고 완료 버튼까지 동시에 겹침          (또 수백 ms 창)
```

**두 번 겹쳐야** 이중판매가 완성된다. 한쪽만 겹치면 ③에서 막힌다.
시간이 벌어진 모든 경우(현실의 절대다수)는 이미 막혀 있다.

### 근본 해결은 규칙 변경을 요구한다

`locked_by_contract` 리프만 원자적으로 compare-and-set 하고 싶지만, 후보 Rules 의 `lockSet`
(`build-release-candidate.mjs:62`)이 **같은 write 안에서** `vehicle_status` 가 `계약중`·`출고불가` 일 것을
요구한다. 리프 하나만 쓰는 트랜잭션은 `vehicle_status` 가 아직 `출고가능` 이라 거부된다.
부모 노드 트랜잭션은 `v4/products/$code` 쓰기 권한이 admin·provider 뿐이라 영업자가 못 쓴다.

→ 원자 선점을 하려면 `v4/product_locks/$code` 같은 **compare-and-set 전용 노드**를 규칙에 새로 열어야 한다.
그런데 지금 콘솔 게시를 기다리는 후보 Rules 는 이미 26/27 로 검증을 끝낸 산출물이다.
여기서 규칙을 건드리면 그 검증이 무효가 되고 오픈이 뒤로 밀린다.

**판단: 이번 오픈에 태우지 않는다. 다음 규칙 개정에 포함한다.**
근거는 위의 «두 번 겹쳐야 한다» + 제한 오픈은 영업자가 소수라는 것이다.
대신 사후 탐지는 싸다 — 같은 `product_code`(및 트윈 신원)에 `계약완료` 가 2건 이상인지 주기 조회.

## 8. 오픈 판정

**차단 아님.** 순차 경로는 전부 닫혔고, 남은 것은 두 번 연속 동시성이 겹치는 경우다.
이 수정으로 오픈이 막히지 않고, 오픈이 만드는 위험의 큰 쪽을 닫았다.

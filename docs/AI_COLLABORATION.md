# AI 협업 및 인수인계 규칙

이 프로젝트는 다음 역할 분담을 기본 개발 파이프라인으로 사용한다.

> Claude Code = 기획·**설계** + 위험영역 **게이트/판단**
> Cursor = **구현·노가다**(대량·반복·리팩터)
> Codex = **독립 전수검증**(sim·빌드·타입·적대) + 수정·완료 책임

## 토큰 경제 · 역할 경계 (핵심)

목표: **각 도구가 잘하는 것에 집중 + 토큰 분산 → 비용↓ 퀄리티↑.**

- **토큰 많이 드는 일(대량 구현·리팩터·전수검증·대형파일 통독)은 Claude Code가 직접 하지 않는다.** → Cursor(구현) / Codex(전수검증)로 오더를 **제안**한다(직접 조종 아님).
- **Claude Code = 고레버리지·저토큰:** PLAN 설계, 아키텍처 제약 명시, 그리고 **위험영역(RTDB 규칙·정산/돈·데이터 마이그레이션·인증/보안)의 최종 go/no-go 판단**. exhaustive 검증은 Codex 담당이고, Claude는 **위험 게이트만 스팟**으로 본다.
- **Codex의 위험영역 수정(`database.rules.json`·정산엔진·rtdb-adapter)은 게시/머지 전 Claude 게이트를 통과**해야 한다. 로컬 에뮬레이터 통과 ≠ 실데이터 안전(레거시 스냅샷·필드 형태로 정당 write가 막힐 수 있음).
- **RTDB 이중읽기 tolerance**(v3+v4 `.catch(()=>[])`)를 throw로 바꾸지 않는다 — 계약·정산 페이지가 통째로 안 열린다.

세 도구는 서로의 결과를 무조건 신뢰하지 않는다. 각 단계는 이전 단계의 산출물과
사용자의 원래 요구사항을 비교하고, 차이가 있으면 명시적으로 기록한다.

**차종마스터·mf- 코드 쓰기 = 커서만**(2026-08-23). 클로드·코덱스·제미나이는 요령(`lib/domain/vehicle-master-playbook.ts`)대로 가져다 쓰기만 하고, 키·이름을 바꾸지 않는다.

## 최우선 원칙

최종 검증 기준은 Claude Code의 설계 문서가 아니라 **사용자의 원래 요구사항**이다.

Codex는 항상 다음 세 가지를 함께 비교한다.

1. 사용자의 원래 요구사항
2. Claude Code가 작성한 `PLAN.md`
3. Cursor 또는 다른 구현자가 만든 실제 변경사항

설계와 원래 요구사항이 충돌하면 원래 요구사항을 우선한다. 다만 중요한 기술 선택,
범위 확대, 데이터 계약 변경, 보안 정책 변경은 사용자의 승인이 필요하다.

## 1. Claude Code: 기획·설계

Claude Code는 구현 전에 코드베이스를 조사하고 `PLAN.md`를 작성한다.

`PLAN.md` 필수 항목:

- 원래 사용자 요구사항을 가공하지 않은 형태로 요약
- 명시적 제약조건과 비기능 요구사항
- 현재 코드와 데이터 흐름 조사 결과
- 영향받는 파일과 모듈
- 고려한 대안과 트레이드오프
- 권장안과 선택 이유
- 단계별 구현 순서
- 파일별 예상 변경사항
- 테스트 계획
- 완료 조건
- 가정, 미확정 사항, 사용자 결정 필요 항목
- 롤백 또는 실패 시 복구 방법

Claude Code는 선택지를 제안하지만 중요한 기술 결정권을 임의로 행사하지 않는다.
사용자 승인이 필요한 항목은 `PLAN.md`에서 명확히 표시한다.

## 2. Cursor: 구현·반복 작업

Cursor는 `PLAN.md`와 사용자의 원래 요구사항을 읽은 뒤 작은 단위로 구현한다.

각 작업 단위에서:

1. 변경 대상과 목적을 확인한다.
2. 관련 코드만 수정한다.
3. 타입 검사와 관련 테스트를 실행한다.
4. 결과를 `IMPLEMENTATION_LOG.md`에 기록한다.
5. 다음 작업으로 이동한다.

`IMPLEMENTATION_LOG.md` 필수 항목:

- 완료한 계획 단계
- 실제 변경 파일
- 주요 구현 결정
- 실행한 테스트와 결과
- 계획과 달라진 부분
- 설계 변경 이유
- 알려진 문제와 미완료 항목
- 현재 작업 트리 상태

설계를 크게 변경해야 한다면 임의로 밀어붙이지 않는다. 변경 이유와 영향 범위를
기록하고, 사용자 결정이 필요한 경우 작업을 멈추고 확인한다.

## 3. Codex: 독립 검증·수정·완료 책임

Codex는 설계자나 구현자의 설명만 보고 완료 판정을 내리지 않는다. 저장소의 실제
변경사항과 실행 결과를 직접 확인한다.

검증 순서:

1. 원래 사용자 요구사항을 다시 확인한다.
2. `PLAN.md`의 범위와 완료 조건을 확인한다.
3. `IMPLEMENTATION_LOG.md`와 실제 diff가 일치하는지 확인한다.
4. 요구사항 누락, 범위 이탈, 회귀, 보안, 데이터 호환성 문제를 검사한다.
5. 타입 검사, 테스트, 프로덕션 빌드를 직접 실행한다.
6. 발견한 문제는 요청 범위 안에서 직접 수정한다.
7. 수정 후 전체 검증을 다시 실행한다.
8. `VERIFICATION.md`에 근거와 결과를 기록한다.

`VERIFICATION.md` 필수 항목:

- 검증한 원래 요구사항
- 요구사항별 구현 충족 여부
- 계획 대비 실제 변경 차이
- 발견한 문제와 직접 수정한 내용
- 실행 명령과 결과
- 회귀·보안·데이터 호환성 점검 결과
- 남은 위험과 미검증 범위
- 최종 판정: PASS / CONDITIONAL PASS / FAIL

Codex의 역할은 문제를 나열하는 데서 끝나지 않는다. 요청 범위 안에서 안전하게
고칠 수 있는 문제는 수정하고, 다시 검증한 뒤 완료 여부를 판정한다.

## 공통 인수인계 파일

| 파일 | 책임자 | 목적 |
|---|---|---|
| `PLAN.md` | Claude Code | 요구사항, 설계, 구현 계획, 완료 조건 |
| `IMPLEMENTATION_LOG.md` | Cursor | 실제 구현 과정, 계획 변경, 단계별 테스트 |
| `VERIFICATION.md` | Codex | 독립 검증, 수정, 최종 판정 |
| `docs/REFACTOR_PROGRESS.md` | 현재 작업자 | 장기 리팩터링의 누적 진행 상태 |
| `HANDOFF.md` | 모든 도구 | 프로젝트 전체 인수인계 진입점 |

모든 문서에는 가능하면 날짜, 대상 브랜치 또는 커밋, 작업 트리 상태를 기록한다.
문서의 “완료” 표시는 실제 코드와 검증 결과가 뒷받침해야 한다.

## 충돌 처리

우선순위는 다음과 같다.

1. 사용자의 최신 명시적 요구사항
2. 사용자에게 승인받은 기술 결정
3. 저장소의 실제 동작과 데이터 계약
4. `PLAN.md`
5. 구현 중 편의를 위한 판단

문서끼리 충돌하거나 오래된 문서가 발견되면 조용히 하나를 선택하지 않는다. 충돌
내용과 선택 근거를 인수인계 문서에 기록한다.

## FreepassERP4 기본 검증

구조 변경 후 최소 검증:

```powershell
npm.cmd run typecheck
npm.cmd run build
npx.cmd tsx scripts/sim-agent.mts
npx.cmd tsx scripts/sim-phase12.mts
```

계약·차량 상태·정산을 수정했다면 관련 생애주기와 정산 시뮬레이션을 추가로 실행한다.
Firebase 규칙이나 인증을 수정했다면 UI 테스트만으로 완료 판정하지 않고 규칙 수준의
권한 시나리오를 별도로 검증한다.

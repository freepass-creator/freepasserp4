## 1. 만든 것 — 시트 → 파이어베이스 올리기

| 파일 | 하는 일 |
|---|---|
| `lib/server/settlement-sheet-import.ts` | 가름·쓰기 규칙 (화면이 쓴다) |
| `app/api/settlement/ledger/import/route.ts` | `GET` 세어보기 · `POST` 올리기 · 관리자만 |
| `scripts/import-settlement-from-sheet.mts` | 같은 일을 명령줄로 (`npm run settlement:import`) |
| `app/settlement/ledger/page.tsx` | 목록 머리 「시트에서 가져오기」 단추 |

### 지켜야 하는 규칙

```
시트에 있고 ERP 에 없다   → 올린다
값이 다르다              → 보여만 준다 (--overwrite / body.overwrite 라야 덮는다)
ERP 에만 있다            → 건드리지 않는다 (ERP 에서 접수한 줄)
```

★**ERP 에서 사람이 고친 줄은 overwrite 여도 안 덮는다** — `v4/settlement_events` 에 이력이 있으면 비켜 간다.
★**시트 빈칸은 «지우라»가 아니다** — 창구가 아직 안 적었을 수 있다.
★**한 탭이라도 못 읽으면 아무것도 안 올린다** — 안 읽힌 탭의 줄이 「없는 줄」로 보이기 때문.
★**쓴 뒤 되읽어 대조한다** — 쓰기 성공 응답과 「값이 맞다」는 다른 말.

## 2. ★제일 위험한 자리 — 여기부터 봐 달라

1. **`migrate-settlement-to-erp` 와 헷갈리면 값이 지워진다.**
   그건 `db.ref(NODE).update(made)` 로 **ERP 전체를 시트 값으로 덮는다.** 그날 ERP 에서 고친 것이 사라진다.
   새로 만든 `import` 는 새 줄만 올린다. 두 파일 머리에 서로를 가리키는 경고를 박아 뒀는데, **경고가 아니라 코드로 막혀 있는지** 봐 달라.

2. **이력 잠금이 실제로 걸리나.**
   `eventKey` 는 `차번|접수일` 을 RTDB 금지문자 치환한 값이다(`settlement-store.eventKey` 와 같아야 한다).
   ⚠ **접수일을 고치면 이력 키가 바뀐다** — 그러면 잠금이 풀린다. 이게 구멍인지 판단해 달라.

3. **쌍둥이 파일이 갈릴 수 있다.**
   화면은 `lib/server/…`, 명령줄은 `scripts/…` 로 **같은 규칙을 두 벌** 적어 놓았다(부팅이 달라서).
   한쪽만 고치면 어느 쪽으로 올렸느냐에 따라 원장이 달라진다. **드리프트 검사가 필요한지** 판단해 달라.

4. **`refused` 계산.** 서버 쪽은 `locked && overwrite` 면 바뀐 칸이 없어도 refused 를 센다.
   명령줄 쪽은 잠긴 줄을 아예 건너뛴다. **두 숫자의 뜻이 같은지** 확인.

## 3. 시험 방법 (제안)

돌아가는 서버가 필요하다(`npm run dev`, 4004). 인증은 `scripts/check-settlement-erp-store.mts` 가
쓰는 방식 그대로 — 관리자 uid 로 custom token → identitytoolkit → idToken.

```
① 시트 「접수」 탭 맨 아래에 시험 줄 (차번 99시험0002 — 기존 시험 줄과 안 겹치게)
② npm run settlement:import         → 새 줄 1 로 잡히나
③ --apply                            → ERP(v4/settlement_rows)에 실제로 들어갔나 · 되읽기 통과하나
④ API PATCH 로 그 줄의 한 칸을 고친다 → v4/settlement_events 에 이력이 생기나
⑤ 시트의 그 칸을 또 다르게 고친다
⑥ --apply --overwrite                → ★그 줄이 «비켜감(refused)» 인가. ERP 값이 그대로인가
⑦ 치운다 — ERP 줄 remove + 시트 줄 삭제
⑧ npm run settlement:drift          → 시트/ERP 줄 수가 시험 전으로 돌아왔나
```

⚠ **시험 줄은 반드시 치운다.** 원장에 남으면 그게 실적으로 세어지고 청구서에 실린다.
⚠ **시험 기대를 짐작으로 적지 마라.** 당월접수는 인도돼도 그 달엔 자리를 안 옮기고,
   갓 접수한 줄은 요율이 없어 수수료 0 이 정상이다.

**시험 전 실측(2026-08-28)** — 시트 432줄 · ERP 432줄 · 새 줄 0 · 다른 칸 0.

## 4. 같이 봐 줄 것 — 오늘 정산에서 바뀐 나머지

### (가) ERP 에서 고칠 수 있는 칸을 넓혔다
서버(`settlement-store.EDITABLE_FIELDS`)는 22칸을 진작 열어 두었는데 화면이 6칸만 열고 있었다.
→ 조건 8칸(상품구분·계약기간·렌탈료·보증금·차량가액·분납여부·납입회차·비고) 편집,
  환수 셋(환수일·환수금액·환수사유) 입력, 영업자연락처.

- 볼 것: **화면에서 보내는 칸이 전부 흰 목록 안에 있나.** 밖이면 서버가 400 으로 막아야 한다.
- 볼 것: **판매수수료·출고수수료·요율·청구금액·지급액은 여전히 못 고치나.** 그건 요율표에서
  나오는 값이라 화면에서 열면 돈 계산이 두 벌이 된다.
- 볼 것: 환수를 켤 때 **날짜·금액이 같이 가고, 끄면 같이 지워지나**(인도완료와 같은 손).

### (나) 차량대장을 걷어냈다
`run-settlement-sheet` 가 3단계 → 1단계. 접수는 직접 입력.
`build-plate-registry` · `publish-plate-registry-tab` 은 **[안 씀]** 표식만 붙이고 남겨 뒀다.

- 볼 것: 파이프라인에서 정말 빠졌나. 남긴 두 스크립트가 **어디서도 안 불리나**.

### (다) 접수 폼 검사를 지금 규격에 맞췄다
`check-intake-form.mts` 가 옛 다섯 구간을 보고 있어 4건이 붉은 채였다(폼은 08-27 에 「상태는 체크로」로 바뀜).
→ 네 구간 + 체크 셋으로 고쳤다. 지금 ○ 다 맞음.

- 볼 것: **검사가 느슨해진 것은 아닌가.** 코드에 맞춰 검사를 구부린 것이면 검사가 죽은 것이다.

### (라) 금액 표기
`lib/format.ts` — 대여료 `655,000원`(축약 안 함) · 보증금 `121만원`.
- 볼 것: 엑셀 대여료 열 폭(`EXCEL_PRICE_MAX`)이 실측 최대(대여료 4,988,000)를 담나.

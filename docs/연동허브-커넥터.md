# 연동 허브 · 커넥터 — 화면 «위계» SSOT

> 사장님 2026-09-05 「구조는 나쁘지 않아. 세부화면·목록·열 안 어긋나게 «위계» 잘 파악해서 하자.」
> 「당겨오기와 내보내기는 사실 한 몸. 당겨와서 우리 걸로 하고, 어디로 나가는지 세부까지 눈으로 확인하고, 원자도 거기서 직접.」

★**이 문서가 위계의 정본이다.** 화면마다 열·섹션 순서를 새로 짜지 않는다 — 여기 한 위계를 모든 화면이 그대로 따른다. 그래야 «어긋나지」 않는다. 뿌리 = 원자의 «역할»([`lib/domain/atom-fields.ts`](../lib/domain/atom-fields.ts)).

## 0. 한 몸 — 연동은 IN·샘·OUT

```
당겨오기(IN)          샘                     내보내기(OUT)
원천 → 원자화     원자 데이터베이스        원자 → 여러 옷
(시트·API·홈피·ERP)   (차번=키·구조적 유일)   (판매시트·ERP·B2C·화이트라벨·채널·외부API)
```
- **커넥터 하나 = 원천 하나 또는 목적지 하나.** 새 원천/목적지는 «커넥터 추가».
- **데이터는 늘 샘 하나** — 어느 옷도 샘을 다시 세거나 덮지 않는다(드리프트 금지, CLAUDE.md).

## 1. 화면 넷 (라우트 위계)

| 화면 | 라우트 | 무엇 |
|---|---|---|
| **샘** | `/spring` | 원자 데이터베이스 그 자체(실시간 감시·상세). ★이미 배포됨. |
| **연동 허브** | `/connectors` | IN·샘·OUT 한 장. 원천·목적지를 «요약»으로. 누르면 세부로. |
| **원천 세부** | `/connectors/in/[code]` | 한 원천의 전체 생애(위치→원본→우리 원자→나가는 곳→직접처리). |
| **목적지 세부** | `/connectors/out/[key]` | 한 목적지의 발행 세부(무엇을·언제·성패). |

**빵부스러기(breadcrumb) 위계 고정:** `연동 허브 › 원천 세부 — {code}` · `연동 허브 › 목적지 세부 — {name}` · 샘은 `/spring` 자립.

## 2. ★목록 «열 위계» — 모든 리스트가 같은 순서 (SSOT)

어느 화면의 원자 목록이든(샘·원천세부·미리보기·목적지) **이 순서·이 성질로만** 찍는다. 역할(atom-fields)이 순서를 정한다:

```
[건강]  │  공통(정체·제원)                           │  변동(매시간)        │  [원천·확정]
건강배지 │ 차번 · 원산지 · 제조사 · 모델 · 세부모델 · 세부트림  │ (상태) · 주행 · 대여료 │ 공급사 · 원천 · 갱신 · 원문
        │ · 선택옵션 · 외장 · 내장 · 연식 · 연료 · 배기량 · 인승 · 구동 · 배터리 · 차종구분 · 상품구분 │
```
- **건강**은 늘 맨 앞(문제 먼저 정렬의 축). **공통 → 변동 → 원천/확정** 순서 불변.
- 좁은 목록(미리보기·목적지)은 **왼쪽부터 잘라 쓴다**(건강·차번·차명·상태·대여료). 순서는 그대로 — 열을 «재배치」하지 않는다.
- 「차명」 = 제조사·모델·세부모델·트림을 «이 순서로» 이어 붙인 한 칸(공간 좁을 때). 원자엔 넷이 따로.
- 숫자(배기량·주행·요금·연식)는 우측·모노. 상태·건강만 색(초록/주황/빨강 셋).

## 3. ★상세 «섹션 위계» — 모든 상세가 같은 순서 (SSOT)

원자 한 대의 상세(샘 우측·원천세부 등)는 **이 섹션 순서로만**:

```
① 정체·공통 (불변)   차번·정체·제원 — 「한 번 박고 안 바뀜」
② 현재 상태·변동     출고상태·주행 + 갱신시각 + 건강    ← 매시간
③ 주요 정책          policy_code 조인 · 자격·연령 / 주행·보험 / 비용·결제 · 미확보=회색
④ 기간별 대여료      그 차 가진 기간 가로 · 대여료/보증금 위아래 · 인수형 별도줄
⑤ 무결성 점검        불변식 위반(문제/주의) 또는 정상
⑥ 공급사 원문(비공통) 원문.차명·옵션 + 「새 칸」 자동감지
```
- 라벨그리드 규격 하나: 라벨칸 고정폭 · 값 좌(문자)/우+모노(숫자·금액) · 빈값=「미확보」(원천 없음, 오류 아님).

## 4. 원천 세부 «생애 위계» (한 원천 = 이 순서로)

```
머리    {code} · 종류 · N대 · 건강분포 · [지금 당겨오기][미리보기][검수 N건]
📍위치   원천이 실제 어디 있나 — [열기 ›](그 시트/API로) · 마지막 당겨오기 · 자동갱신 주기
①변환   원본 → 우리 원자 (before/after) — 공급사가 준 그대로 ▶ 정제·원자화(어떻게 우리 걸로 했나)
②원자   이 원천이 만든 원자(§2 열 위계) + 「샘에서 이 원천만 보기 ›」(/spring?in={code})
③나감   이 원천의 원자가 나가는 목적지 칩(누르면 목적지 세부)
④직접   정밀타격(재수집) · 검수 · 원자 열기 — 그 원천 원자를 여기서 바로
```

## 5. 데이터·경계 (누가 읽고 누가 쓰나)

- **읽기(내 화면 몫)**: 원천·목적지 «요약·세부·건강·변환·나감»은 **Firestore products를 그대로 읽어** 파생(source·provider_company_code로 묶고, `atom-health`·`atom-fields`로 성질·건강). 원천 위치(URL)는 `v4/partners.sheet_url`. **읽기전용.**
- **쓰기·외부(수집·발행 파이프라인 몫)**: 「당겨오기/미리보기」(외부 원천 읽기)·「내보내기」(외부 발행)·「정밀타격」은 **서버 자격증명**으로 도는 파이프라인(direct-ingest·publish). 화면 버튼은 그걸 부른다. ⚠ 그 파이프라인·자격은 **수집 세션 몫**(이 화면 세션과 lane 다름).
- **원자 값은 손으로 안 고친다** — 원천/오버라이드에서(방향-데이터플랫폼 §3).

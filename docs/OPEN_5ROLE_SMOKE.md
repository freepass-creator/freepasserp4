# 오픈 전 5역할 실계정 수동 smoke

작성: Codex · 2026-08-04  
기준: `docs/AUTHORIZATION_MODEL.md` · 사용자 원래 역할 요구사항

## 목적과 안전조건

자동 `smoke:b2b-roles`는 session과 상품 브리지 **GET만** 확인한다. 이 문서는 계약·채팅·재고·정산의 허용 write와 타 조직 denial을 실제 계정으로 확인한다.

- 운영 계약·실고객·실정산을 테스트에 사용하지 않는다.
- `QA_OPEN_` 접두사의 전용 상품·방·계약만 사용하고 시작 전 v4 preimage와 종료 후 잔여 0건을 확인한다.
- 테스트 계정·조직 생성이 필요하면 사용자의 명시 승인 뒤 수행한다.
- Preview와 Production은 같은 RTDB를 사용하므로 Preview write도 운영 데이터 write로 취급한다.
- Rules 게시 전 baseline과 게시 직후 결과를 같은 계정·같은 QA 레코드로 비교한다.

## 계정 세트

| 역할 | 필요한 소속 |
|---|---|
| 플랫폼 관리자 | `admin` |
| 영업채널 관리자 | 채널 A `agent_admin` |
| 영업자 | 채널 A 직원 A1 `agent` |
| 공급사 관리자 | 공급사 A `provider_admin` |
| 공급사 직원 | 공급사 A 직원 P1 `provider` |

차단 확인용으로 채널 B 계약/방 1건과 공급사 B 상품/계약/방 1건을 준비한다. 실제 사람 데이터 대신 비식별 QA 레코드를 쓴다.

각 성공 write에서 `sender_uid` 또는 audit actor가 실제 로그인 계정과 일치하고, 계약의 `agent_uid`·`agent_channel_code`·`provider_company_code`가 바뀌지 않았는지 확인한다.

## 필수 denial

각 항목은 버튼 숨김이 아니라 실제 write/read 요청이 403 또는 `PERMISSION_DENIED`인지 확인한다.

1. 영업채널 관리자: 채널 B 계약·방 접근 및 수정 거부.
2. 영업자 A1: 같은 채널 다른 영업자의 계약·방 접근 및 수정 거부.
3. 영업 역할 둘 다: 재고관리 write, 공급사 단계, 정산 확정·보류·환수 거부.
4. 공급사 관리자·직원: 공급사 B private 상품·계약·방 접근 및 수정 거부.
5. 공급사 역할 둘 다: 영업 측 단계, 영업 지급액, 플랫폼 순수익 접근 거부.
6. 공급사 직원: 회사 설정·직원 관리·대량 삭제/복원 같은 고위험 조직 작업 거부 여부를 기록한다. 현재 역할 세분화 잔여가 있으면 숨기지 말고 오픈 예외 승인 대상으로 올린다.
7. 비활성·삭제·반려·승인대기·익명 계정: session·상품 브리지·업무 데이터 접근 거부.

## 차량 선점·복원 시나리오

1. 같은 QA 차량을 가리키는 계약 A/B를 만든다.
2. 영업 계정 두 개가 동시에 계약금 입금을 시도한다.
3. 정확히 1건만 성공하고 다른 1건은 충돌해야 한다.
4. 성공 계약의 차량만 `계약중`, claim owner와 `locked_by_contract`가 같은 계약이어야 한다.
5. 성공 계약의 체크를 해제해 claim 삭제·차량 복원을 확인한다.
6. 공급사 입금확인 경로도 같은 서버 claim을 유지하는지 확인한다.

## 정산 표시 검증

- 관리자: R1·R2·순수익 전체와 최종 상태 변경 가능.
- 영업채널 관리자/영업자: 자기 범위의 R2만 표시, 상태 변경 불가.
- 공급사 관리자/직원: 자기 회사 R1·정산 상태만 표시, R2·순수익 비노출, 상태 변경 불가.
- 금액은 UI 문자열만 보지 말고 계약 snapshot과 정산 private 원자에서 계산된 값이 일치하는지 확인한다.

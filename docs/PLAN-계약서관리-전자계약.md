## 0. 먼저 — 이 설계의 신뢰도

실측 중에 두 번 틀렸다. 같은 실수를 반복하지 않도록 적어 둔다.

| 내가 말한 것 | 실제 | 왜 틀렸나 |
|---|---|---|
| 「정비/서비스 섹션이 없다」 | `FIELD_MAP` 140필드에 다 있다 | 화면 9섹션만 보고 규격을 안 봤다 |
| 「서명은 착한거래가 한다」 | 프리패스 자체 파이프라인이 쓰이는 중 | 옛 메모리를 믿고 코드를 안 봤다 |
| 「자체 전자계약이 이미 있다」 | **어느 커밋에도 없다. 전부 미커밋 작업물** | 작업트리의 파일을 완성품으로 읽었다 |

**`lib/server/freepass-esign.ts` · `app/api/freepass-esign/**` · `app/sign/[token]`
· `components/FreepassEsignPanes.tsx` 는 2026-08-10 현재 커밋되지 않았다.**
다른 세션이 쓰는 중이다. 이 설계는 그것이 «완성될 것»을 전제하되,
그 위에 무엇을 더 얹을지만 말한다. 그 파일들을 갈아엎지 마라.

## 1. 무엇을 만드는가

```
계약서관리  →  전자계약 발송센터
```

사장님 지시 넷을 한 줄로 합치면 이렇다.

```
지시 A  기존 계약서관리 메뉴를 «삭제»하고 새로 만든다
지시 B  기존 계약과 «무관하게» 전자계약서만 보낸다
지시 C  기존 엑셀을 «대체»한다는 개념으로 접근한다
지시 D  모바일 화면은 착한거래 것을 참고한다
지시 E  계약서관리는 「계약서 생성」과 「완료 보관」 둘로
```

### 지시 A — 고치는 게 아니라 지우고 새로 짓는다

「계약서관리」는 `/esign` 이다(`lib/tabbar.tsx` `NAV_LABEL.esign`).
지금 화면은 **관리자용 4패널**이고, 계약을 «고르지 않으면» 아무것도 못 한다.
엑셀을 들고 온 사람이 설 자리가 없다. 그래서 재배치가 아니라 **교체**다.

```
지운다   app/esign/page.tsx 의 지금 화면 구성 · NAV_LABEL.esign = '계약서관리'
새로 짓는다  전자계약 발송센터 (§3)
```

★ **한 커밋에서 지우고 세운다.** 지운 채로 두면 그 사이에 전자계약을 못 보낸다.
★ **패널 «내용»은 버리지 않는다.** 4패널이 하던 일(계약 데이터·연동·진행)은
   상세보기로 옮긴다. 지우는 것은 «첫 화면이 그 4패널이라는 사실»이다.
★ 메뉴 이름도 바꾼다 — 「계약서관리」는 무엇을 하는 곳인지 말해 주지 않는다.
   **「전자계약」**이 이 화면이 하는 일이다.

**핵심은 B다.** 지금은 ERP 계약이 있어야 전자계약을 보낼 수 있다.
그 사슬을 끊는 것이 이번 일의 전부라고 봐도 된다.

## 2. 지금 막고 있는 것 — 실측

자체 발행(`app/api/freepass-esign/contracts/[code]` `action=issue`)이 요구하는 선행조건:

```ts
if (S(contract.provider_agreement_done) !== 'yes')
  → '계약 진행중에서 약정 작성을 먼저 완료해 주세요.'      // ★이것이 사슬
if (!S(contract.customer_name) || !S(contract.customer_phone))
  → '고객명과 연락처를 먼저 확정해 주세요.'                 // 이건 남겨야 한다
```

`provider_agreement_done` 은 **ERP 계약 5단계 중 하나**다.
엑셀을 들고 온 사람은 그 단계를 밟은 적이 없다. 여기서 막힌다.

### 고치는 방향 — 값을 속이지 마라

`provider_agreement_done = 'yes'` 를 가짜로 넣어 통과시키면 안 된다.
그 값은 「공급사가 약정을 작성했다」는 뜻이고, 정산·감사가 그걸 믿는다.

대신 **계약이 어디서 왔는지**를 새 축으로 둔다.

```ts
contract.source = 'erp' | 'excel' | 'direct'
```

| source | 발송 조건 |
|---|---|
| `erp` | 지금 그대로 — 5단계를 밟아야 한다 |
| `excel` · `direct` | **BLOCK 0 이면 보낸다.** ERP 단계를 묻지 않는다 |

BLOCK 판정은 §5. 이 한 줄이 지시 B의 답이다.

## 3. 화면 — 계약서관리

### 3.1 구조

```
/esign   전자계약

┌ 보내기 ────────────────────────────────────┐
│  [＋ 엑셀 계약서 넣기]   ← 가장 큰 버튼        │
│  [＋ 직접 작성]  [ERP 계약에서]               │
└────────────────────────────────────────┘

  발송대기 3    서명중 5    확인필요 2    완료 27
  ────────────────────────────────────────
  김OO  아반떼        손오공   월 600,000 · 48개월   [보내기]
  이OO  K5           A렌터카  확인 필요 2건         [확인]
  박OO  카니발        웰릭스   서명중 · 어제 열람      [보기]
```

한 행에 **여섯 값**만 — 고객 · 차량 · 렌터카사 · 월대여료 · 기간 · 상태.
그 이상은 행을 눌러 상세에서 본다. 기존 3패널(데이터·연동·진행)은 **상세로 옮기고 지우지 않는다.**

### 3.2 두 갈래 (지시 E)

|  | 계약서 생성 | 완료 계약서 |
|---|---|---|
| 무엇 | 값을 채워 계약서를 만들고 보낸다 | 서명이 끝난 것이 모인다 |
| 고칠 수 있나 | 발송 전까지 | **못 고친다.** 열람·내려받기만 |
| 다시 보내려면 | — | 새 회차(Revision)를 만든다 |

보관함에서 고칠 수 있으면 그건 보관이 아니다.
서명된 문서를 고치는 순간 그 서명은 아무것도 증명하지 못한다.

### 3.3 상태 — 넷만 보여준다

내부 상태는 더 잘게 나뉘어도, 화면에는 넷이다.

```
발송대기   아직 안 보냄 (BLOCK 0 이면 보낼 수 있음)
서명중     보냄 · 열람 · 서명 진행
확인필요   BLOCK 있음 · 반려 · 만료
완료       서명 끝
```

「초안·발송가능·고객열람·서명진행·반려·만료·취소·재발송필요」를 그대로 노출하지 마라.
직원이 여덟 개를 외워야 하면 그건 상태가 아니라 숙제다.

## 4. 엑셀을 대체한다는 뜻 (지시 C)

**엑셀을 빼앗지 않는다. 엑셀 «뒤»를 없앤다.**

```
지금   엑셀 작성 → 출력 → PDF → 카톡 전달 → 서명 → 사진 회수 → 폴더 보관
목표   엑셀 작성 → 넣기 → 확인 → 보내기
끝    (엑셀도 필요 없어진 뒤에) 직접 작성 → 보내기
```

세 번째 줄로 바로 가려 하지 마라. 직원은 계약서를 엑셀로 «생각»한다.
그 습관을 그대로 둔 채 뒤의 다섯 단계를 없애는 것이 이번 목표다.

### 엑셀에서 무엇을 읽나

전체를 복제하지 않는다. **직원이 «입력한» 칸만** 읽는다.
서식·수식·안내문·약관 본문은 버린다 — 그건 우리 규격이 이미 갖고 있다.

실물 12부를 학습한 결과([공통계약서 문서](PLAN-프리패스-공통계약서.md) §1),
열두 회사가 적는 것은 사실상 같다. 다른 것은 숫자와 문구뿐이고 그건 정책값이다.

읽어야 할 칸(계약마다 바뀌는 것) — **열몇 개뿐이다.**

```
계약자   성명 · 연락처 · 주소 · (사업자면) 상호·사업자번호
차량     차종/트림 · 차량번호 · 현재주행거리
조건     대여기간 · 월대여료 · 보증금(분납) · 약정주행 · 만기인수 · 정비상품
```

나머지(회사 상호·계좌·대표자·보험 한도·면책·약관)는 **한 번만 입력한다** — §6.

## 5. 검증 — 세 등급

| 등급 | 뜻 | 발송 |
|---|---|---|
| PASS | 값이 있고 형식이 맞다 | 가능 |
| WARNING | 값은 있으나 확인이 필요 (자동이체일 없음·추가운전자 미확정) | 가능 · 배지 |
| BLOCK | 없으면 계약이 성립하지 않는다 | **불가** |

BLOCK 최소 다섯 — **렌터카사 · 고객명 · 연락처 · 월대여료 · 계약기간.**

BLOCK 이 있으면 버튼을 회색으로만 두지 말고 **무엇이 없는지 그 자리에 적는다.**
「보낼 수 없습니다」가 아니라 「연락처 없음」이라고.

판정은 `esign-compliance` 를 잇는다. 새 판정기를 만들면 화면과 서버가 다른 답을 한다.

## 6. 한 번만 입력하는 값

계약마다 바뀌지 않는 것은 **계약서가 묻지 않는다.** 회사 설정에서 한 번 받는다.

| 값 | 어디에 | 지금 |
|---|---|---|
| 상호 · 사업자번호 · 주소 | 파트너 | ✅ |
| **대표자** | 파트너 | ❌ 없음 — 계약서 `company_ceo` 가 빈다 |
| **대여료 입금계좌** | 파트너 | ❌ 없음 — `payment_account_no` 가 빈다 |
| 운전자 연령 · 범위 | 정책 | ✅ |
| 보험 한도 · 면책 | 정책 | ✅ |
| 정비 · 대차 · 긴급출동 | 정책 | ✅ |
| 약관 본문 · 버전 | 표준 | ✅ |

**대표자와 입금계좌 두 칸이 없어서 계약서가 미완성으로 나간다.** 이것부터 채운다.

★ 회사 고정값을 나중에 고쳐도 **이미 보낸 Snapshot 은 바뀌지 않아야 한다.**
계약에서 값을 고쳤다고 회사 기본값이 따라 바뀌어도 안 된다. 두 버튼을 분리한다.

## 7. 모바일 화면 (지시 D)

착한거래 쪽이 이미 충분히 다듬어져 있으므로 **그 화면을 기준으로 삼는다.**
`app/sign/[token]` 을 새로 디자인하지 말고, 착한거래 것과 나란히 놓고 맞춘다.

원칙 하나만 지킨다 — **A4 를 축소하지 않는다.** 모바일은 단계로 나눈다.

```
1 계약 기본     계약자 · 차량 · 기간 · 월대여료 · 보증금
2 차량·대여조건  차량번호 · 연식 · 주행 · 약정주행 · 만기인수 · 결제
3 운전자·보험   연령 · 범위 · 추가운전자 · 대인/대물/자손/자차 · 면책
4 정비·서비스   정비상품 · 오일 · 검사 · 대차 · 긴급출동
5 특약         있을 때만
6 약관         전문 조회 · 계약값 옆에 관련 조항 링크
```

동의는 **서명 직전에 항목별로** 받고 각각의 시각을 따로 남긴다.
한 번에 「모두 동의」로 받으면 나중에 「그건 못 봤다」에 댈 것이 없다.

## 8. 구현 순서

각 칸은 그것만으로도 쓸 수 있어야 한다. 반쯤 만든 채 다음으로 가지 않는다.

| # | 무엇 | 왜 이 순서 | 파일 |
|---|---|---|---|
| 1 | 파트너에 **대표자·입금계좌** | 없으면 계약서가 미완성으로 나간다 | `lib/intake/entities.ts` |
| 2 | `contract.source` 축 신설 + 발송 선행조건 분기 | **지시 B의 답.** 이게 없으면 나머지가 무의미 | 자체 발행 route |
| 3 | **옛 화면 삭제 + 발송센터 신설** (3버튼 · 상태 4탭 · 6값 행) | 지시 A. 엑셀 없이 직접작성만으로도 굴러간다 | `app/esign/page.tsx` · `lib/tabbar.tsx` |
| 4 | 두 갈래 (생성 / 완료 보관) | 지시 E | 같은 화면 |
| 5 | 검증 3등급 + BLOCK 5개 | 발송 버튼의 근거 | `esign-compliance` 확장 |
| 6 | 엑셀 넣기 — 양식 판정 · 원자 추출 · 확인 화면 | 여기서 지시 C가 완성된다 | `lib/domain/esign-excel/` |
| 7 | 손오공 Adapter (개인·개인사업자) | 실물 있음 ★ | 〃 `adapters/` |
| 8 | 모바일 6단계 정리 (착한거래 기준) | 지시 D | `app/sign/[token]` |
| 9 | Revision (R1·R2) | 운영에서 «고쳐야 할 일»이 생긴 뒤 | — |

**1·2 가 끝나면 지시 B가 달성된다.** 3~5 는 화면, 6~7 이 엑셀, 8 이 모바일이다.

### 엑셀 실물 위치

```
C:\Users\admin\Documents\카카오톡 받은 파일\계약서 양식\계약서 양식\
  02. 손오공\렌트\01. 손오공_개인(개인사업자) 계약서.xlsx
  02. 손오공\렌트\02. 손오공_법인사업자 계약서.xlsx
```

24개 공급사 폴더가 있다. 학습 도구 — `npx tsx scripts/learn-contract-labels.mts`.

**실물은 리포에 넣지 마라.** 고객 성명·주민번호·연락처가 들어 있다.
검사에는 값을 지운 구조 샘플만 쓴다.

## 9. 금지

- **`provider_agreement_done` 을 가짜로 `yes` 로 만들지 마라.** 정산·감사가 그 값을 믿는다.
- **미커밋 `freepass-esign` 파일을 갈아엎지 마라.** 다른 세션이 쓰는 중이다.
- **새 계약서 규격을 만들지 마라.** 규격은 `rental-contract.html`(140필드) 하나다.
- **공급사별 계약서를 만들지 마라.** 다른 것은 값이지 문서가 아니다.
- **PDF 를 원본으로 삼지 마라.** Snapshot 이 원본, PDF 는 그 그림이다.
- **약관을 고치지 마라.** 새 버전을 만들고, 체결된 계약은 그때 버전을 계속 본다.
- **인수증·CMS 를 본계약에 붙이지 마라.** 서명 시점이 다르다 —
  인수증을 함께 받으면 «아직 받지도 않은 차»를 받았다고 서명하게 된다.
- **엑셀 전체를 복제하지 마라.** 직원이 입력한 칸만 읽는다.
- 시험 계약은 `is_test` 로 가른다(있음). 실계약 목록에 새면 안 된다.

## 10. 아직 안 잠긴 문 — 먼저 처리할 것

표준계약서 3벌이 전부 `sample-v1` · `isSample: true` 다. 법률 검토 전이다.
운영 발행 잠금(`isEsignTemplateAllowed`)이 **착한거래 경로에만** 걸려 있었다.

자체 발행 route 에 같은 잠금을 넣는 한 줄과, 「발행하는 모든 문이 잠금을 부르는가」를
파일 단위로 세는 검사를 만들어 뒀다 — **커밋하지 않았다**(그 파일들이 남의 미커밋 작업이라).

```
app/api/freepass-esign/contracts/[contractCode]/route.ts   ← 잠금 한 줄 추가됨(미커밋)
scripts/sim-esign-issue-gate.mts                            ← 새 검사(미커밋) · 5/5 통과
```

그 파일을 커밋하는 사람이 **함께 담아 달라.** 지금은 배포된 적이 없어 급하진 않지만,
자체 발행이 운영에 나가는 순간 샘플 문안이 손님에게 간다.

## 11. 검사

```
sim-esign-issue-gate      발행하는 모든 문이 샘플 잠금을 부르는가 (새로 만듦)
sim-esign-excel-import    엑셀 → 원자 → 등급. 값 하나라도 어긋나면 실패
sim-esign-snapshot        발송 뒤 원본·정책을 바꿔도 Snapshot 이 안 변하는가
sim-esign-source-gate     source=excel 이 ERP 단계 없이 발송되는가 / erp 는 여전히 막히는가
check:template-drift      두 리포 서식 동일 (있음 — 끄지 마라)
```

`sim-esign-snapshot` 이 특히 중요하다. Snapshot 이 안 굳으면 **손님이 본 것과
보관본이 달라진다.** 그건 계약이 아니다.

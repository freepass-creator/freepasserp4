## 1. 6차 지적 ①·② 를 이렇게 고쳤다

### 1-1. 「읽고 → 쓰기」 사이가 안 묶여 있던 것

6차: 「A 의 심장이 멎어 B 가 뺏은 뒤, 그 전에 `runId===A` 를 확인해 둔 A 가 쓰면
B 의 lock 을 A 이름으로 덮어쓴다. 그 뒤 둘 다 쓰기 단계로 갈 수 있다.」 맞다.

**파일 하나로 진짜 CAS 는 못 만든다. 그래서 «애매하면 둘 다 물러난다»로 갔다.**

- `writeLock()` 이 **쓴 뒤 되읽어** 주인을 다시 본다. 내 것이 아니면 `lockLost`.
- 일꾼도 쓴 뒤 되읽어 어긋나면 `clearInterval` 로 **박동을 멈춘다**.
- `touchLock` 은 `lockLost` 면 더는 만지지 않고, 다음 `run()` 시작에서 `stop()` 한다.

→ A 는 되읽기에서, B 는 다음 박동(30초 안)에서 각각 「내 것이 아니다」를 보고 물러난다.
**둘 다 죽어도 잃는 건 한 회차**고, 스케줄러가 한 시간 뒤 다시 부른다. 살림보다 안전을 앞에 뒀다.

**봐 달라:**
- 이 「둘 다 물러난다」가 6차가 말한 경쟁을 **실질적으로** 닫나?
- A 가 되읽기로 알아채기까지의 창(쓰기 직후 수 ms)에 **둘 다 쓰기 단계에 있는 순간**이 남나?
  남는다면 그게 실제로 위험한 길이인가?
- 「둘 다 물러나서 그 시각 회차가 통째로 빠지는」 것이 운영상 받아들일 만한가?

### 1-2. `releaseLock` 이 주인을 «모르는데» 지우던 것

6차: 「`readLock()` 이 `null` 이면 소유자 불명인데 `rmSync` 한다. 부분 파일을 읽으면
다른 실행의 lock 을 지울 여지가 있다.」 맞다. → **모르면 안 지운다**로 바꿨다.

```ts
const held = readLock();
if (!held || held.runId !== RUN_ID) return;   // 모르거나 남의 것이면 손대지 않는다
rmSync(LOCK, { force: true });
```

**봐 달라:** 이러면 반대로 «내 lock 인데 못 읽어서 안 지우는» 경우가 생긴다.
그 lock 은 심장이 안 뛰니 5분 뒤 다음 회차가 뺏는다 — 그 정도면 되나?

## 2. 6차 지적 ② — 요구한 실측 셋을 «실제 6분»으로 다시 쟀다

5·6차 모두 「5초로만 쟀다」고 지적받았다. 이번엔 6차가 적어 준 세 항목 그대로 쟀다.

```
■ ① 긴 단계(6분) 동안 lock mtime 이 30초 주기로 전진하나
  1분째 0초 · 2분째 0초 · 3분째 0초 · 4분째 0초 · 5분째 0초 · 6분째 1초
  → 6분 내내 lock 나이 최대 1초 ✓

■ ② 그 도중(3분째)에 두 번째 실행이 들어오면
  → ✓ 물러났다 (쓰기 단계에 못 들어감)

■ ③ 일꾼을 멈추고 5분 지난 lock 을 8개가 동시에 뺏으면
  → ✓ 이긴 것 1개 (최종 주인 = 뺏기0)
```

막힌 단계는 1분짜리 자식 6번으로 흉내냈다(그동안 메인은 매번 완전히 막힌다).
시험 코드는 `hourly-sync` 와 **같은 방식**을 쓴다 — `open('wx')` 획득 · `rename` 뺏기 ·
일꾼 30초 박동 · 쓴 뒤 되읽기.

**봐 달라:** 이 셋이 6차가 적은 조건 1·2·3 을 채우나? 모자라면 **무엇을 더 재야 하는지** 적어 달라.

# 코덱스 검증 오더 — 원자화 정본화 (2026-09-04)

> 코덱스 = **검사만**(CLAUDE.md). 고치지 마라 — 어긋난 것을 «어디가 왜»로 보고하면 클로드가 고친다.
> 검증 기준 = **사용자 원래 요구사항**(아래 §1), 내 설계가 아니다.

## §1. 사용자가 시킨 것 (검증 기준)

사장님 2026-09-04:
1. **불변은 «한 번»만 원자화** — 원문 + 차종마스터 검증(영문·FL·공백)으로 제조사·모델·세부모델·세부트림·원산지·배기량·색·연식·구분을 한 번 박고 **안 바꾼다.**
2. **변동만 매시간 연동** — 배차상태·주행거리·대여료·보증금. (주행거리는 «변동»으로 바뀌었다 — 대여료처럼.)
3. **원자 하나를 ERP·구글시트가 «같이» 읽는다** — 화면이 따로 세지 않는다.
4. **정산원장에 차번 오르면 계약중**, 인도완료면 출고불가. 취소/환수는 자동해제 안 함.
5. **데이터 아예 없는 차(원문없음)는 내린다.** 원문 있는데 매칭만 실패한 차는 살린다.
6. **스펙·대여료·정책은 상태값과 무관하게 무조건 노출.**
7. **매뉴얼화 해서 안 움직이게** — docs/원자화-매뉴얼.md + `npm run check:atoms` 게이트.

## §3. 코덱스가 «전수»로 검증할 것 (독립 재현)

1. **게이트가 실제로 잡나** — `npm run check:atoms` 를 돌려 5개 규격(칸밀림·빈식별·색미분리·구분캐논·원문없음)이 0인지. 일부러 원자 하나를 어기게 만들어 exit 1 나는지(sim).
2. **트림 피커가 «지어내지 않나»** — `pickTrim` 이 그 세부모델의 마스터 `trims[]` 밖 값을 절대 안 내는지. 정규화(비지니스↔비즈니스 등)가 오탐(다른 트림 오매칭) 내는 사례 있는지.
3. **불변을 두 곳이 안 박나** — ⑥⑦(판매→v4)와 ⑬½(정제→v4)가 같은 불변 칸(색·모델)을 다투는지. write-once 가 옛 잘못을 굳히는 경로가 또 있는지.
4. **⑥ `--force-shrink` 가 진짜 손실을 내나** — 공급사 하나가 진짜 0대 된 날, ⑥ 이 통과해도 ⑯(Firestore 원자)이 그 차를 지키는지(원자는 출고불가 될 뿐 사라지지 않는지). 0대 전무 가드(line 818)는 살아 있는지.
5. **⑬½·⑯ 순서** — ⑬½(치유)→⑭(미러)→⑯(발행) 순서가 hourly-sync 에서 지켜지는지. 뒤바뀌면 낡은 원자가 실리는지.
6. **상태 규칙** — `mark-contract-in-listings` 가 계약중은 세우고 출고불가는 안 덮고 취소/환수는 안 푸는지. 정산원장 차번 ↔ 원자 vehicle_status 대조.
7. **주행거리 변동** — `columnOwner('주행거리')==='live'` 인지. 미러 VARIABLE 에 mileage 있는지. once 로 굳는 경로 없는지.

# 실측 기록 — 자동동기 (2026-08-30)

> 코덱스가 환경 오류(`uv_os_get_passwd ENOMEM`)로 못 돌린 것들을 여기 남긴다.
> 5차 점검서의 **최소조건 2·3** 에 대한 증거다.

## ① 잠금 원자성 — 10개가 동시에 달려들면 하나만 이기나

```
새로   · 10개가 동시에 달려듦 → 이긴 것 1개 [주자0] → ✓ 하나만 이겼다
죽은것 · 10개가 동시에 달려듦 → 이긴 것 1개 [주자0] → ✓ 하나만 이겼다
        (6분 전에 멎은 lock 을 미리 만들어 두고 «뺏기» 경쟁을 시킨 것)
```

새로 잡을 때는 `open(LOCK, 'wx')` — 파일이 이미 있으면 실패하므로 «만드는 것»과 «내가 만들었다»가
한 번에 일어난다. 죽은 것을 뺏을 때는 `rename(LOCK, LOCK.claim-내표딱지)` — 이름 바꾸기도 원자적이라
**한 놈만 성공**하고 진 쪽은 `ENOENT` 를 받고 물러난다.

★그래서 「둘이 동시에 «없네»/«죽었네»를 봐도」 이기는 것은 하나뿐이다 — 코덱스 5차 지적의 그 자리.

## ② 일꾼 심장박동 — 메인이 막힌 동안에도 뛰나

```
메인 5초 막힘(spawnSync) · lock 이 그동안 5초만큼 갱신됨 → ✓ 심장이 뛰었다
일꾼 타이머에 unref 를 걸면 · lock 0초 갱신            → ✗ 스레드가 즉시 죽는다
```

둘째 줄이 실제로 처음 짰던 코드다. 코드만 봐서는 멀쩡해 보였고 **실측으로만 잡혔다.**

## ③ ⑨ 상태 갈림 감사 — 판매 4탭 계약 수정 뒤

```
■ 상태가 어디서 갈렸나 — 원본 → 정제시트 → 판매시트 → ERP
  범위: 원본과 정제시트가 분리된 4개 공급사(RP004 · RP023 · RP031 · RP006)

■ 상태가 다른 차 0대 · 검토 필요 0대 · 미확인 0대

  기록 tmp/status-drift.json · 여기서 고치지 않는다 — 신호만 낸다

종료코드=0
```

**고치기 전: 미확인 559대 · 종료코드 2.** 원인은 데이터가 아니라 감사기에 손으로 박힌
「판매시트 발행 탭 **3개**가 아님」 하나였다. 픽업구독을 더해 4탭이 됐는데 그 숫자를 안 고쳐,
오류 하나가 판매 레이어를 통째로 `complete=false` 로 만들고 차 559대를 미확인으로 밀어냈다.


## ④ aiops 자동실행 기준값 — `--apply` 대조의 잣대

우리가 `--apply` 를 돌리면 이 값과 같아야 한다. 두 회차 연속으로 같았다.

| 회차 | 결과 | 걸린 시간 | 커버리지 | 실패 | 경고 |
|---|---|---|---|---|---|
| 11:42 | ok=true | 9분 53초 | 224/224 · 100% (모델없음 0 · 트림실패 0) | 없음 | 요금검수 7대(>6) |
| 12:42 | ok=true | 5분 34초 | 224/224 · 100% (모델없음 0 · 트림실패 0) | 없음 | 요금검수 7대(>6) |

★**두 회차 모두 내가 오늘 파일을 고친 «뒤»에 돌았고 실패 0 이다** —
`audit-status-drift.mts` 는 aiops 차례에 없고 `sales-published-tabs.ts` 는 주석만 바꿨으니
영향이 없어야 정상이고, 실제로 없었다.

⚠ **경고 하나가 계속 켜져 있다** — 「판매엔 있는데 ERP 요금 0인 차 **7대**」.
정상 기준선 3대 · 임계 6대인데 7대다. 원산지·정제칸 구멍 신호다.
**오늘 이관 작업과는 무관**하지만(이관 전부터 켜져 있었다), `--apply` 대조 때 이 숫자가
그대로인지 봐야 한다. 늘면 우리 쪽이 만든 것이다.

⚠ 우리 dry-run 은 21분이었는데 aiops `--apply` 는 5~10분이다. 우리 쪽이 손오공 pull 을
매번 새로 하고, dry-run 도 읽기는 다 하기 때문으로 보인다 — `--apply` 실측 때 확인할 것.


## ⑤ 잠금 — 코덱스 6차가 요구한 «5분 초과» 실측 셋

5·6차에서 「5초로만 쟀다」고 지적받은 자리다. **실제 6분**으로 다시 쟀다.
막힌 단계는 1분짜리 자식 프로세스 6번으로 흉내냈다(그동안 메인은 매번 완전히 막힌다).

```
■ ① 긴 단계(6분) 동안 심장이 뛰나
  1분째 lock 나이 0초 · 2분째 0초 · 3분째 0초 · 4분째 0초 · 5분째 0초 · 6분째 1초
  → 6분 내내 최대 1초. 30초 주기로 계속 전진 ✓

■ ② 그 도중(3분째)에 두 번째 실행이 들어오면
  두 번째 실행(B) 시도 → ✓ 물러났다 (쓰기 단계에 들어가지 못한다)

■ ③ 심장이 멎은 lock 을 8개가 동시에 뺏으면
  이긴 것 1개 → ✓ 하나만 · 최종 주인 = 뺏기0
```

시험 코드는 `hourly-sync` 의 잠금과 **같은 방식**을 쓴다 —
`open(...,'wx')` 로 새로 잡고 · `rename` 으로 죽은 것을 뺏고 · 일꾼이 30초마다 만지고 · 쓴 뒤 되읽어 확인.


## ⑥ 잠금을 «주인 자리»로 바꾼 뒤 — 시험이 저장소에 들어왔다

★코덱스 7차: 「시험 코드·원시 로그가 저장소에 없어 독립 재실행을 못 했다」 — 맞다.
이제 **`npx tsx scripts/sim-hourly-sync-lock.mts`** 로 누구나 다시 돌린다(`--long` 이면 6분 시험까지).

```
✓ 새로 잡기 — 10개가 달려들어도 하나만 — 이긴 것 1개
✓ 죽은 잠금 뺏기 — 8개가 달려들어도 하나만 — 주인 [owner-뺏기0]
✓ 뺏긴 실행이 뒤늦게 박동해도 못 되살린다 — A 늦은박동=실패(정상) · 주인 [owner-B]
✓ 심장이 뛰는 잠금은 남이 못 가져간다 — 주인 [owner-살아있음]
```

`--long` (실제 6분, 1분짜리 막힌 단계 6번):
```
① 1분째 0초 · 2분째 0초 · 3분째 0초 · 4분째 0초 · 5분째 0초 · 6분째 0초
  → 6분 내내 주인 자리 나이 최대 0초 · 30초 주기로 계속 전진 ✓
② 3분째에 두 번째 실행 시도 → 물러났다 ✓
③ 심장 멎은 잠금을 8개가 동시에 뺏기 → 이긴 것 1개 ✓
```

**셋째 줄이 코덱스 7차가 짚은 인터리빙이다.** 파일 «내용»에 주인을 적던 방식에서는
A 가 뒤늦게 쓰면 B 를 덮어썼다. 이제 심장박동은 **시각만 갱신**하고 **만들지 않으므로**,
뺏긴 A 는 「자리가 없다」(ENOENT)를 받고 되살릴 방법이 없다.

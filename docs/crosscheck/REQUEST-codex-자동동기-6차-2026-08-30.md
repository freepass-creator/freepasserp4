## 1. 원자적 소유권 — 이렇게 했다

5차 지적: 「`lockHeldByLiveRun()` 확인과 `writeLock()` 사이에 배타적 생성·CAS 가 없다.
둘이 동시에 부재를 보면 둘 다 덮어쓴다. heartbeat 는 획득 «후»만 보장한다.」 맞다.

```
새로 잡기    open(LOCK, 'wx')                  이미 있으면 예외 — 만들기와 「내가 만들었다」가 한 번에
죽은 것 뺏기  rename(LOCK, LOCK.claim-표딱지)     이름 바꾸기도 원자적 — 한 놈만 성공, 진 쪽은 ENOENT
```

- 주인은 **PID 가 아니라 표딱지(`runId` = pid + 시작시각 + 난수)** 로 가린다.
  → 2차에서 지적한 **PID 재사용이 원천적으로 사라진다.**
- `touchLock`·`releaseLock`·일꾼 모두 `runId` 로 주인을 확인한다.

**실측(기록 ①)** — 10개가 동시에 달려드는 시험을 두 경우로 했다.
```
새로   · 10개 동시 → 이긴 것 1개 ✓
죽은것 · 10개 동시 → 이긴 것 1개 ✓   (6분 전에 멎은 lock 을 만들어 두고)
```

**봐 달라:**
- `open(...,'wx')` + `rename` 조합이 5차가 말한 **compare-and-set lease 와 같은 수준**인가?
- `rename` 으로 뺏은 뒤 `write()` 가 실패하면 lock 이 **없는 채로** 남는다(`return false`).
  다음 회차가 새로 잡을 테니 괜찮다고 봤는데 맞나?
- 뺏긴 실행(A)이 이미 하고 있던 «그 단계의 쓰기»는 여전히 못 막는다. 5차에서
  「fencing 은 로컬 단일 스케줄러의 필수 전제가 아니다」라고 했으니 이건 남겨도 되나?

## 2. heartbeat 검증 — 어디까지 됐고 무엇이 안 됐나

**된 것(기록 ②)**
```
메인 5초 막힘(spawnSync) · lock 5초 갱신 ✓
일꾼 타이머에 unref 를 걸면 · 0초 갱신 ✗  ← 처음에 그렇게 짰다가 실측으로 잡았다
```

**안 된 것 — 정직하게 적는다**
- 5차 조건은 「**5분 초과 `spawnSync` 시험**에서 mtime 이 30초 주기로 유지되고,
  **동시에 두 번째 실행이 시작하지 않음**을 기록으로 확인」이었다.
  나는 **5초** 로만 쟀다. 5분 초과 시험도, 두 번째 실행 차단 기록도 없다.
- 「worker 가 멎을 때의 takeover」도 안 쟀다.

**봐 달라:** §1 의 원자성 시험(죽은 lock 뺏기 10개 동시 → 1개)이 「두 번째 실행이 시작하지 않음」의
증거로 **충분한가**, 아니면 5분짜리 실측을 따로 해야 하나? 필요하면 그렇게 하겠다.

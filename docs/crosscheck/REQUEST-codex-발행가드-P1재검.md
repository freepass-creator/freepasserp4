# 코덱스 재검 — ⑥ 발행 0대 가드 «코드기반» 재설계 (P1-1·P1-2 해소 확인) 2026-09-07

검사만·고치지 마라. 판정은 tmp/codex-P1재검-verdict.md 에 GO/NO-GO 로.

## 배경
직전 판정에서 «표시명(companyAlias/SPELL_PAIRS) 기반 0대 가드»는 사전 밖 이름·대소문자·이름삭제를 못 덮어
근본 취약(에스에이→SA 3일 중단)이라 했고, «코드기반 스냅샷»으로 재설계를 권했다. 그 재설계에 대해
직전 코덱스가 **NO-GO 2건**을 냈다:
- **P1-1**: 스냅샷 탭을 4개 탭(상품리스트·손오공구독·픽업구독·오플구독)이 «공유»하면 마지막 발행이
  다른 탭 기준선을 덮어써 오발동/미감지.
- **P1-2**: 스냅샷 쓰기가 clear(updateCells)→PUT 2단계라, clear 성공·PUT 실패 시 «빈 스냅샷»이 남아
  다음 발행의 0대 가드가 통째로 무력화(진짜 소실을 놓침).

## 이번 수정 (scripts/publish-origin-tab.mts, HEAD 미커밋)
1. **P1-1 해소** — 스냅샷 탭을 탭별로 분리: `SNAP_TAB = @발행코드수-${TAB}` (line 849).
   hourly-sync 4회 호출이 각기 다른 --tab 을 주므로 탭마다 독립 기준선. 상품리스트=`@발행코드수-{상품리스트탭}`,
   손오공구독=`@발행코드수-손오공구독` … 서로 안 덮는다.
2. **P1-2 해소** — 쓰기를 «단일 PUT»로: clear 제거. `[header, ...dataRows]` 를 SNAP_PAD(250)까지
   빈 줄 `['','','']` 로 패딩해 한 번의 `values.update`(A1:C250, RAW)로 원자 갱신 (line 966~975).
   파트너 수(~64) « 250 이라 낡은 줄이 남지 않고, clear 단계가 없어 «빈 스냅샷» 중간상태가 생기지 않는다.
3. **읽기측 방어** — 스냅샷을 읽을 때 `headerOk = A1==='공급사코드'` 이고 데이터행이 하나라도 있어야
   «유효 기준선»으로 인정(`baseline.size>0`). 비었/헤더뿐/손상이면 기준선 없음으로 보고 이번 발행으로
   (재)생성, 코드 0대 가드는 다음 발행부터. 그동안은 총량(-20%)·시트못읽음 가드가 지킨다 (line 882~898).
4. gone 판정 = `baseline 의 코드 중 직전 n>=3 인데 이번 nowByCode 에 0` → throw. n<3(1~2대)은 노이즈로 제외.

## 확실히 답해 달라
1. **P1-1 완전 해소?** 4개 탭이 정말 서로 다른 스냅샷 탭을 쓰나. TAB 값이 같아질(충돌) 경로가 있나
   (예: --tab 미지정 폴백, --only 만 다르고 --tab 같음)? hourly-sync.mts 4회 인자를 실제로 대조하라.
2. **P1-2 완전 해소?** 단일 PUT 이 부분성공/실패로 «보호 무력화» 중간상태를 남길 수 있나. PUT 이 통째 실패하면
   직전 스냅샷이 그대로 남아 오히려 안전한가(맞으면 그렇다고). SNAP_PAD=250 이 파트너 수보다 항상 큰가
   (partners 총수 확인). 250 을 넘기면 낡은 줄이 남는 반례?
3. **첫 실행/시딩 안전?** 스냅샷이 없거나 손상됐을 때 기준선만 만들고 넘어가는 로직이, 진짜 소실을 놓치는
   창을 여나. 그 창 동안 총량·시트못읽음 가드로 충분한가.
4. **새 잠복 구멍?** 코드기반으로 바꾸며 생긴 새 오발동/미감지. nowByCode 는 rowCode(배열 객체 키)로 세는데,
   dedup 으로 rows[dupAt] 를 갈아끼울 때 rowCode.set 이 새 built 로 갱신되는지(line 647) 확인. 필터/중복 제거
   후에도 코드 복원이 정확한가.
5. **재발 차단 확신** — 공급사명을 한글↔영문 어떻게 손질해도 이 가드가 안 멈추나(코드는 불변이므로)?

## 2차 수정 (이번 재검 대상 — §3 대응)
직전 재검 NO-GO 중 §3(시딩/손상 창 소실) 대응으로 추가:
- 기준선 대수 파싱을 엄격화: `Number.isFinite(n) && n>=0` 아니면 그 줄을 «손상」으로 세고(`snapBad`) baseline 에 안 넣는다.
  `Number('oops')→NaN` 이 «0대→통과»로 새던 구멍을 막음 (line 888~899).
- «손상 줄이 하나라도 있으면»(`snapBad>0`) 부분정상 스냅샷을 유효 기준선으로 쓰지 않고 시딩모드로 (재)생성 (line 902).
- 시딩 창 로그를 ⚠ 경고로 승격 + 사유(없음/헤더손상/손상N/데이터없음) 명시 (line 910~912).
- 첫 실행 단일공급사 소실은 «비교할 기준선이 없어» 원리적으로 못 잡음을 인정 — 시딩은 «데이터 온전 확인된 상태에서 1회 통제 실행»으로 닫는다(운영). 그 창엔 총량(-20%)·시트못읽음 가드만 유효.

## §4 는 이 재설계 범위 밖(전제 확인 요청)
§4(공유문서 탭 소유권이 표시명 의존)는 코덱스도 «기존 앞단 문제, 이번 rowCode.set 누락 때문 아님»이라 했다.

⇒ 이번 판정은 «가드 재설계가 배포된 라벨기반 가드보다 엄격히 안전하고 P1-1·P1-2·§3-손상을 해소하는가»로 좁혀 달라.

## 3. 라벨 출처와 정확한 분기점

### 3.1 byCode는 실제로 무엇으로 채워지는가

`publish-origin-tab.mts:161–179`:

1. `t3`, `t4`는 실제 조회 결과가 아니라 각각 빈 객체 `{}`다.
2. 따라서 `partners`도 비어 있고, `172–179`의 파트너 병합 루프는 실행할 항목이 없다.
3. Firestore·RTDB의 한글 partner 레코드는 이 실행의 이름 출처가 아니다. 파일에 남은 Firebase URL 상수나 import만으로 사용 중이라고 판단하면 안 된다.

`274–292`에서 Sheets API로 문패를 읽고 처음으로 byCode를 채운다.

```text
문패 A열 r[0] = name
문패 B열 r[1] = code
문패 C열 r[2] = url
code와 http(s) url이 있는 행만 채택
partner_name = S(cur?.partner_name || cur?.name) || name
```

요청의 “문패 B열 이름”은 코드와 다르다. **현재 구현은 A=이름/B=코드/C=주소**다. 또한 API 범위는 탭 이름을 지정하지 않은 `values/A1:Z200`이다(`275`). 따라서 코드가 「공급사시트정리」라는 탭명을 찾아 읽는 것은 아니다. 문서의 기본 첫 시트를 읽는 구조이므로 탭 순서나 열 배치 변경도 잠복 위험이다.

같은 코드의 행이 여러 개면 **먼저 채택된 비어 있지 않은 이름이 유지**된다(`285`). 주소는 뒤 행의 주소가 후보 맨 앞으로 추가된다(`288`). 따라서 중복 문패에서는 이름과 실제 선택 주소가 서로 다른 행에서 올 수 있다. 처음 이름이 빈 경우에는 뒤 행의 이름이 채워진다.

### 3.2 표의 공급사 칸은 어떻게 만들어지는가

```text
문패 A열 name
  → byCode.get(code).partner_name                   278–289
  → who = companyAlias(name) || name || code        418
  → COLUMNS.map에서 공급사 칸에 who 직접 반환       561–562
  → 중복차량 선택·출고불가/번호/빈행 필터
  → 최종 rows의 공급사 칸으로 now 집계               897–910
```

- `companyAlias`는 법인격·렌터카/렌트카·모빌리티·일부 구두점만 제거한다(`identity.ts:120–131`). **한글을 영문으로 번역하지 않는다.**
- `who`는 explicit alias 인자를 주지 않으므로 Firestore의 alias/display_name도 사용하지 않는다.
- 공급사 원본 재고탭의 「공급사」 셀, 정책탭, `clean/SUBST`로부터 이름을 가져오는 경로가 아니다. `562`에서 먼저 반환한다.
- Drive에서 읽은 문서명은 `309–316`의 **정책 시트 후보 매칭**에 사용된다. 여기의 지역변수 `who`는 `418`의 발행 라벨 `who`와 다르며 byCode를 덮지 않는다.
- 실제 재고 문서명 `readTitle`은 `394,426`의 “우리 시트” 구분에 사용된다. 인접 `supplier-sheet-read.ts:149–150`에서는 generic 어댑터 선택에도 영향을 준다. 문서명이 공급사 표시명이 되는 것은 아니다.
- `648`에서 출력하는 공급사별 tally의 이름도 같은 `who`다. 다만 그 숫자 `n`은 중복차량 신규 추가 기준이며 뒤의 출고불가·번호·빈행 필터보다 앞이다. **tally 30대와 최종 now 30대는 별도 확인 사항**이다.

### 3.3 prev 한글 / now 영문이 되는 메커니즘

같은 코드 PT-0023의 문패명이 과거 `주식회사 에스에이렌터카`였다면 당시 출력은 `에스에이`다. 현재 채택되는 문패명이 `SA렌터카` 또는 `SA`이면 현재 출력은 `SA`다. 이전 표는 저장된 한글 라벨 그대로 읽고(`860–862`), 지금은 현재 문패로 새 행을 만든다. 가드가 과거 이름을 그때의 코드로 보존한 기록을 읽는 것은 아니다.

고침 전에는 **현재 문패의 companyAlias 한 개와 코드만** 역색인에 등록했다. 그러면 `SA → PT-0023`만 있고 `에스에이`는 없어서 이전은 문자열 `에스에이`, 현재는 코드 PT-0023으로 갈라진다. J&J도 동일하다. 고침은 이 기본 표기에 SPELL_PAIRS 다리를 추가한 것이다.

단, 이는 **코드로 확인한 발생 메커니즘**이다. 실제 9/4 원문과 수정이력을 열지 못했으므로 특정 사용자의 문패 수정, 중복행 순서 변경, 다른 발행기/수작업에 의한 과거 표 변경 중 무엇이 실제 방아쇠였는지는 못정함이다. “Firestore가 한글인데 tally가 영문”만으로 서로 다른 데이터 소스를 번갈아 읽었다고 결론 내릴 수 없다.

또한 총 331→330이라는 순감소만으로 **개별 차량 손실이 전혀 없었다고 입증할 수는 없다.** 다른 공급사 증가가 손실을 상쇄할 수 있다. 실제 차량 보존 판정에는 원본 차량 식별자 대조가 필요하다.

## 4. PR #89가 모든 divergence를 해결하지 못하는 이유

`identity.ts:138`의 SPELL_PAIRS는 정확히 **SA/에스에이, J&J/제이앤제이, KH/케이에이치 3쌍**이다. 일반 음역·번역·대소문자·전각 문자 변환기가 아니다. 생성된 키가 쌍의 한쪽과 **정확히 일치할 때만** 반대 기본 표기를 추가한다(`157–162`). 영문 접미사나 다른 약칭을 자동 해석하지 않는다.

가드의 형태는 다음과 같다(`888–896`).

```text
현재 각 코드 c와 현재 이름 N에 대해 {c} ∪ supplierNameKeys(N)를 수집
각 키가 현재 코드 하나에만 속하면 codeOf에 등록
ident(w) = codeOf.get(trim(w)) || trim(w)
```

**과거 라벨 w 자체에는 supplierNameKeys를 적용하지 않는다.** 양쪽 이름의 키 집합에 교집합이 있는 것과, 과거 라벨 원문이 현재 역색인에 들어 있는 것은 다른 조건이다. 유일성은 “등록해도 되는가”만 가리며, 사라진 과거 별칭을 복원하지 않는다.

아래는 실제 운영업체의 발생을 주장하는 것이 아닌 **합성 반례**다. 각 표의 이전/현재 행 수는 별도 표기 없으면 3행씩이며 동일 회사의 이름만 바뀐 상황이다.

| 변경 또는 입력 | 실제 gone 결과 | 의미 |
|---|---|---|
| SA↔에스에이, J&J↔제이앤제이, KH↔케이에이치 | 없음 | 3쌍 × 양방향 × 현재 렌터카 접미 유무 = 12건 연결 확인 |
| 에이비씨 → ABC (현재 ABC렌터카) | 에이비씨 3대→0 | SPELL_PAIRS 밖의 음역은 연결 안 됨 |
| 에스에이 → sa (현재 sa렌터카) | 에스에이 3대→0 | 대소문자에 민감 |
| 가 온 → 가온 (현재 가온렌터카) | 가 온 3대→0 | **현재 키끼리는 유일해도 과거 공백 라벨을 조회하지 못함** |
| 가온 → 가 온 (현재 가 온렌터카) | 없음 | 반대 방향은 short 키가 가온을 만들어 줌: 방향 비대칭 |
| 가온캐피탈 → 가온 (현재 가온렌터카, 같은 회사라고 가정) | 가온캐피탈 3대→0 | 양쪽 supplierNameKeys는 가온을 공유해도 과거 원문은 등록 안 됨 |
| 가온 → 가온캐피탈 | 없음 | 반대 방향은 연결됨 |
| 에스에이 → 코드 C1 (문패 이름 삭제) | 에스에이 3대→0 | 빈 이름에는 과거 별칭이 남지 않음 |
| 코드 C1 → SA (문패 이름 채움) | 없음 | 코드 등록으로 연결됨: 이름 채움/삭제도 비대칭 |
| 과거 전체 상호 주식회사 에스에이렌터카 → SA | 과거 전체 상호 3대→0 | 과거 표에 전체 상호를 다른 writer가 넣은 경우. 현재 who가 정상 출력하는 기본 라벨과 구별해야 함 |

따라서 **“양쪽 이름 모두 유일하지만 서로 다른 표기여서 안 이어지는” 반례는 있음**이며, 다른 공급사가 하나도 없어도 재현된다.

## 5. 남은 소실 미감지와 과잉 중단

### 5.1 현재 명단에서 충돌 키를 제외해도 동일 라벨 fallback은 합쳐진다

가상 A=`가온렌터카`, B=`가온모빌리티`는 `companyAlias` 결과가 둘 다 `가온`이다. 유일매핑은 가온 키를 제거하지만 `ident('가온')`은 원문 가온으로 돌아간다.

```text
이전: A 3행 + B 3행 → 화면 라벨은 모두 가온 → before['가온']=6
현재: A 소실, B 3행 → now['가온']=3
결과: gone=[]
```

현재 문패를 그대로 두어도 **실제 A 소실을 놓친다.** 이름만 저장한 과거 표에서는 어느 행이 A/B였는지 가드가 구별할 수 없다. “모호한 키를 안 써서 보호를 약화시키지 않는다”는 `885–886` 주석은 기존 가온렌터카/가온캐피탈 사례에는 맞지만 일반 보장은 아니다.

기존 반례 A=`가온렌터카`, B=`가온캐피탈`에서 두 코드가 현재 문패에 남아 있고 A만 소실하는 경우는 **현재 고침으로 감지됨**을 별도 확인했다. 과거의 덮어쓰기 버그가 그대로 남았다는 뜻은 아니다.

### 5.2 현재 명단의 유일성은 과거 소속을 보장하지 않는다

```text
이전: A=가온렌터카 3행(라벨 가온), B=가온캐피탈 3행
현재 문패: A 행 누락, B만 존재
현재 역색인: 가온 → B (이제 유일함)
현재 재고: B 3행만 존재
before[B]=6, now[B]=3 → gone=[]
```

삭제된 공급사·잘린 문패 범위·잘못된 URL로 탈락한 행 등은 현재 충돌 후보에 들어가지 않는다. 이름 재사용과 코드 변경도 같은 시간축 문제다. 이것은 위험한 **거짓 유일성**이며, 현재 명단 검사만으로 과거 공급사 정체성을 입증할 수 없다.

위 5.1·5.2 반례의 6→3만 보면 총량 20% 가드가 막는다. 그러나 영향 없는 공급사 30행을 양쪽에 더하면 **36→33(8.3% 감소)**으로 총량 가드도 통과한다. 해당 공급사 읽기 오류가 없다면 전체 보호가 이 두 가드만으로 보장되지 않는다.

### 5.3 코드와 이름이 같은 문자열 공간을 쓴다

`addKey(c,c)`도 뒤의 `codes.size===1` 필터를 받으므로 `886`의 “code 자신은 항상 등록”은 문자 그대로 참이 아니다. 다른 회사 이름이 A라는 코드 문자열과 같으면 A 키는 모호하여 codeOf에서 빠진다. 그런데 fallback 문자열 A는 다시 코드 A와 같은 집계 공간에 들어간다. A의 이전 코드 라벨과 B의 이름 라벨 A가 합쳐져 A 소실을 놓치는 합성 사례도 재현했다. 실제 운영에서 이런 상호/코드가 존재하는지는 미확인이다.

### 5.4 가드 자체의 범위 제한

- `912`: 이전 **3행 이상이고 현재 정확히 0행**인 집계만 감지한다. 1–2행→0, 10행→1은 감지 대상이 아니다. 부분 소실을 전수검사하는 가드가 아니다.
- `855`: `--force-shrink`는 총량뿐 아니라 공급사 소실 및 시트 통째 읽기 실패 보호도 우회한다.
- `858–863`: 직전 탭이나 「공급사」 헤더가 없으면 공급사별 대조를 하지 않는다. `831–832`는 제목 startsWith(TAB)로 이전 탭을 선택하므로 비슷한 제목의 복수 탭도 별도 위험이다.
- `856–857`: 실패 문자열 중 “시트를 못 읽었다”만 전체 중단한다. `407–416`의 일부 탭 실패는 직접 중단 사유가 아니므로 같은 공급사의 다른 탭에서 1행이라도 남으면 0대 가드가 못 잡는다.
- 신규 공급사는 이전 표에 없으므로 gone 검사 대상이 없다. 기존 공급사도 문패에서 빠져 읽기 자체를 시도하지 않으면 unread 기록이 생기지 않는다.
- 출고불가/번호/빈행 필터, @제외, 전역 차번 중복 선택 때문에 판매 대상이 정상적으로 0이 된 경우도 가드는 원인을 구분하지 않고 멈출 수 있다(`638–644,679–745`). 이는 공급사 원본 전체 재고수가 아니라 **발행 후보 표의 잔여 행 수**를 세는 설계다.
- 빈 공급사 라벨은 `901`에서 집계하지 않는다. 외부 writer가 과거 공급사 셀을 비운 경우 보호 근거가 사라진다.

### 5.5 문패↔시트명 divergence는 상류 배정에도 남는다

공유 문서의 탭 소유 판정 `364–377`은 supplierNameKeys를 쓰지 않고 정규화한 회사명 포함 여부를 본다. 예를 들어 공유 문서 코드 순서가 `[B, A]`, A의 현재 문패명이 SA, 실제 탭명이 에스에이재고라면 해당 탭에서 SA를 찾지 못한다. B의 이름도 없으면 첫 코드 B에게 배정한다. 기본 SA↔에스에이 가드 별칭이 있어도 **행 자체가 다른 회사에 배정되는 문제**는 고치지 못한다. 코드 추적 반례이며 라이브 발생을 주장하지 않는다.

Drive 문서명만 변경하면 직접 공급사 라벨은 바뀌지 않는다. 다만 정책 후보 매칭이나 문서명에 따른 어댑터 선택은 달라질 수 있으므로 “시트명 변경은 모든 발행 동작에 무영향”까지 보장해서는 안 된다.

## 6. 다음 이름 손질 때 재발하지 않는 정확한 조건

현재 역색인으로 정의한 `I(w)=codeOf.get(trim(w)) || trim(w)`라 하자. 코드가 실제 적용하는 gone 회피 조건은 **이전의 각 집계 키 k 중 3행 이상인 모든 k에 대해 현재 행 수가 1 이상일 것**이다. 이 조건은 통과 조건일 뿐, 올바른 회사끼리 이어졌다는 증거는 아니다.

안전한 이름 변경이라고 말하려면 최소한 다음을 확인해야 한다.

1. 문패에서 같은 공급사코드와 주소·읽기 범위가 유지되고 코드 재사용/누락/중복행 우선순위 변화가 없어야 한다.
2. **실제 과거 공급사 라벨 원문과 새 who 모두** 현재 역색인에서 같은 올바른 코드로 유일하게 해석되어야 한다. supplierNameKeys 두 집합의 단순 교집합만 확인하면 부족하다.
3. 그 라벨이 과거·현재의 다른 회사나 코드에 재사용되지 않아야 한다. 현재 키가 유일하다는 사실만으로는 부족하다.
4. 상류의 공유탭 배정·어댑터·필터·중복차량 선택 후에도 해당 코드의 발행 행이 남아야 한다. 모든 차가 정상적으로 판매 대상에서 빠진 경우라면 가드 중단은 별도로 판단할 일이다.
5. 직전 표/헤더를 정상적으로 읽고 동일 비교 범위에서 검사하며 가드를 우회하지 않아야 한다.

기본 SA/J&J/KH의 정확한 3쌍은 위 조건에서 양방향으로 연결된다. 임의의 한글→영문 손질은 **보장 불가**다. 근본적으로 지속 가능한 공급사 식별자를 과거·현재 비교 증거에 보존하고 표시명과 분리하는 설계가 필요하다. 과거 표에는 표시명만 남은 경우가 있으므로 전환 시의 확정 매핑/모호성 처리도 필요하다. **설계 제안만 남기며 이번에는 어떤 수정도 하지 않는다.**

## 7. 실행 증거·한계·교차검토

### 결정론적 검사

PowerShell의 `$OutputEncoding`과 콘솔 출력 인코딩을 UTF-8로 설정한 후, Node stdin에서 로컬 TypeScript transpile + VM을 사용했다. 파일을 새 테스트 코드로 고치거나 발행기 전체를 import하지 않았다.

- identity.ts에서 `export function companyAlias`부터 supplierNameKeys 끝까지 **실제 소스**를 추출했다.
- 발행기에서 `const keyToCodes =`부터 `if (gone.length)` 직전까지 **실제 소스**를 추출했다. companyAlias/supplierNameKeys 및 count/gone 규칙을 별도로 재작성하지 않았다.
- byCode·prevRows·rows에 합성 데이터를 주입했다. 네트워크/API·자격증명은 이 검사에 사용하지 않았다.
- **28 assertions passed**: 기본 3쌍 양방향·접미 12건, 위 표기차 및 비대칭 9건, 기존 충돌 수정 1건, 동일 표시명 미감지·누락 후 잘못 귀속 2건, 실제 0대 감지·2행 임계값·부분 소실 3건, 코드/이름 충돌 1건.
- “통과”는 예상한 연결/오발동/미감지 결과를 실제 코드가 재현했다는 의미다. 결함 반례도 포함하므로 제품 전체 합격을 뜻하지 않는다.

최소 재현 입력 예시:

```js
// run은 위 실제 소스를 추출한 가드에 인자를 주입하는 래퍼다.
// 내부 prevRows = [['공급사'], ...before], prevAt = supplierAt = 0
const three = s => [[s], [s], [s]];
run([['C1','ABC렌터카']], three('에이비씨'), three('ABC'));
// gone = ['에이비씨 3대→0']
run([['C1','가온렌터카']], three('가 온'), three('가온'));
// gone = ['가 온 3대→0']
run([['A','가온렌터카'],['B','가온모빌리티']],
    [...three('가온'), ...three('가온')], three('가온'));
// before = [['가온',6]], now = [['가온',3]], gone = []
run([['B','가온캐피탈']],
    [...three('가온'), ...three('가온캐피탈')], three('가온캐피탈'));
// before = [['B',6]], now = [['B',3]], gone = []
```

발행기 기본 dry-run은 `819`에서 종료하여 **이번 ⑥ 가드까지 실행하지 않는다.** 따라서 dry-run만 성공했다고 이 가드를 검증했다고 할 수 없다. 이번에는 쓰기 없이 해당 블록을 직접 격리 실행했다. 빌드·ERP 동기·운영 발행·전체 데이터 감사는 실행하지 않았으며 그 통과를 주장하지 않는다.

### 원본 접근 및 보조 AI

- `gws`로 코드가 지정한 문패 문서의 시트 메타데이터 읽기를 시도했다. 최초 JSON 인자 전달 오류를 바로잡고 재호출했으나 Google discovery API에서 **소켓 접근 거부(os error 10013)**로 실패했다. Google 원문을 로컬 캐시로 대체하지 않았다. 현재 업체 전체 이름/코드와 과거 표는 미검증이다.
- Claude Code: 읽기 도구만 허용한 비대화형 plan 검토를 요청했다. 대상 코드 범위만 지정했으나 응답 없이 대기하여 중단했다. 검토 의견 없음.
- Cursor Agent: `--print --mode ask`로 대상 코드 범위에 대한 읽기 전용 검토를 요청했으나 `uv_os_get_passwd returned ENOMEM`으로 실패했다. 검토 의견 없음. 이 오류만으로 실제 RAM 부족 원인을 단정하지 않는다.
- Gemini CLI: `--approval-mode plan`의 비대화형 검토를 시도했으나 신뢰되지 않은 디렉터리라는 이유로 종료했다. 검토 의견 없음.
- 세 도구 모두 문서·고객 원문이나 자격증명 전달 없이 코드 검토만 요청했다. **4-AI 교차검증 완료·합의·이견 해소를 주장하지 않는다.** 보조 AI 의견을 채택/기각한 항목은 없다.

최종 재감사: 기본 SA/J&J/KH 연결은 확인. 범용 재발 방지는 반례로 부정. 동일 라벨/현재 명단 누락에 따른 잠재 중대 미감지가 남으며 미수정이다. 요청한 코드 조사의 판정문은 작성했지만, 운영 안전성과 필수 교차검토가 통과한 것으로 완료 선언하지 않는다.

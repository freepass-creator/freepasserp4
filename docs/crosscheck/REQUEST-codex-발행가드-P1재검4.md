# 코덱스 재검 4차 — 발행 0대 가드: R1(낡은 사면)·R2(모호키 오차단) 대응 (2026-09-07)

검사만·고치지 마라. 판정 tmp/codex-P1재검4-verdict.md 에 GO/NO-GO.

## 3차 NO-GO(R1·R2)를 어떻게 받았나
- **R1(낡은 사면 다리가 실제 소실을 숨긴다)** — 스냅샷의 «이름→코드» 다리가 낡으면(과거 그 이름을 다른 회사가 쓴 뒤 개명),
  실제 소실을 엉뚱한 코드로 사면했다.
  **대응**: 스냅샷 헤더 D1 에 그 회차의 «탭 제목»을 도장으로 박는다(쓰기 967~1005). 읽을 때 `snapInSync = snapHeaderOk && D1===prevTitle`
  일 때만 ㉡ 다리를 쓴다(가드 895~902). 표는 써지고 스냅샷 PUT 만 실패해 낡으면 D1 이 옛 제목으로 남아 제목이 어긋나고 ㉡를 통째로 버린다
  → 임의 개명은 (보수적으로) 막힘 = 배포본과 동일. 「낡은 스냅샷이 보호를 약화」가 사라진다.
- **R2(모호 키를 현재 라벨로 비교하던 fallback 상실 → 무소실인데 오차단)** — 3차에서 gone 을 `nowByCode`(코드 전용)로만 봐서
  「가온」처럼 유일매핑 안 되는 라벨이 코드맵에 없어 3대→0 오차단.
  **대응**: 배포본처럼 직전·지금을 «둘 다 ident 로 환원해」 센다(`count()` — 903~917). 모호 키는 라벨 그대로 맞물려 무소실이면 통과.
  `nowByCode` 는 이제 gone 판정에서 안 쓴다(스냅샷 쓰기에만).

## 확실히 답해 달라
1. **R1 해소?** 낡은 스냅샷(D1≠prevTitle)일 때 ㉡ 다리가 완전히 버려져, R1 시나리오(과거 이름 재사용+개명)에서 실제 소실을
   «배포본과 동일하게» 차단하나? 반대로 스냅샷이 «동기(D1===prevTitle)»면 그 이름↔코드가 직전 표와 일치하므로 오사면이 없나?
2. **R2 해소?** 「가온렌터카/가온캐피탈」 무소실 정상 입력에서 새 가드가 배포본처럼 통과하나(오차단 없음)? 실제 소실이면 여전히 차단하나?
3. **원래 7종 반례 유지** — 스냅샷 없음/oops/빈대수/중복0/헤더손상/데이터없음/낡음에서 여전히 «차단»인가(회귀 없음).
   특히 «동기 스냅샷에 A가 있는데 A가 진짜 0대»면, ㉡로 A를 환원해도 now 카운트가 0이라 차단되나?
3. **도장 동기 로직** — D1 도장이 정말 «표 쓰기와 스냅샷 쓰기가 같은 회차에 둘 다 성공»했을 때만 일치하나?
   prevTitle(직전 탭 제목) 과 스냅샷 D1(직전 회차가 박은 title) 의 관계를 hourly-sync 4탭 각각에 대해 확인하라.
   표 PUT 성공 후 스냅샷 PUT 실패 시 D1 이 어긋나는가? 둘 다 성공 시 다음 회차에 일치하는가?
4. **엄격 배포 판정** — 이 4차가 «배포된 라벨+supplierNameKeys 가드」보다 회귀 없이 엄격히 안전한가.
   즉 배포본이 막는 실제 소실을 통과시키는 반례가 하나라도 있나? §4(공유문서 탭배정)는 별건.

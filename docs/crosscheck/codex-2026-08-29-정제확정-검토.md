# Codex 교차검증 — 정제 «채움» vs «확정» 구조

대상: `docs/PLAN-jeongje-confirm-2026-08-29.md` (Claude 설계안)  
판정: **실행 보류(NO-GO)** — 설계 수정 및 사용자 확정 전에는 `confirm-lock.mts --apply`를 실행하지 않는다.

## 맞음

- F01의 차량번호 집합을 정합 기준으로 하고, 임의 중복 제거를 금지한 점.
- 후보가 여러 개인 차량을 자동 확정하지 않고 검수 대상으로 남기려는 점.
- 확정 후 재실행에서 값이 흔들리지 않도록 하려는 목적.

## 틀림 / 수정 필요

1. **유일 후보를 자동으로 「확정」 처리하면 안 된다.** 유일 후보는 계산 결과이지, 공급사 원문 그대로이거나 사람의 확인이 아니다. 자동으로 넣으면서 `원천='사람확정'`이라고 기록하는 것은 감사 이력을 거짓으로 만든다.
2. **「safe medium」도 쓰기 기준으로 부족하다.** 후보 세대들에 공통인 값이라도 공급사 원문에 없는 모델·세부모델·제원을 정제칸에 쓰면 추정이다. 후보 산출/표시는 가능하지만, 확정값 쓰기와 분리해야 한다.
3. `scripts/confirm-lock.mts`는 현재 마음카 문서 ID와 공급사명이 하드코딩된 3대 시험 스크립트다. 범용 실행기나 운영 확정 도구로 간주하면 안 된다. 백업, 실행 ID, 원문 근거, 중복 차량번호 검사, 재읽기 검증도 없다.
4. F01은 현재 `상품리스트 → 손오공구독 → 픽업구독 → 오플구독` 4탭이다. 그런데 일부 계약 출력/주석은 3탭을 말한다. 2026-08-29 `npm run check:sync`는 판매시트 열 수 매뉴얼 불일치 1건으로 실패했다. 4탭·68열 매뉴얼 드리프트부터 닫아야 한다.
5. 완료 조건은 F01↔ERP 차량번호만으로 부족하다. 천이 카드, 배차상태, 사진 링크, 기간별 대여료, 차종 4축, 원문 차명·옵션, 정책코드 및 계약 상태도 재대조해야 한다.

## 수정 요청

아래 상태를 구분해 설계를 고쳐라.

```
후보산출(쓰기 없음) → 검수대기(원문 근거 첨부) → 사람/명시 목록 확정
→ 확정값+근거+확정자+시각 기록 → F01 4탭 재발행
→ 천이·ERP 동기 → 전 필수필드 재대조
```

- 후보산출의 원천은 `자동후보`로만 남긴다. `사람확정` 표기는 실제 사람 확인 때만 쓴다.
- 원문과 정확히 대조 가능한 별칭 변환도 근거 문자열을 저장하고, 원문 불충분·후보 복수는 반드시 검수대기다.
- 확정 쓰기는 Cursor 전용 차종마스터 규칙, 사용자 직전 승인, 대상 행 백업, 실행 후 재읽기 검증을 포함한다.
- F01/천이/ERP 대조가 모두 통과해야 운영 완료로 판정한다. 한 단계라도 읽기 실패면 실패로 처리하고 다음 단계 쓰기를 막는다.

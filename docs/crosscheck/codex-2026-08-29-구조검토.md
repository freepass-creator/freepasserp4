## 최종 판정: **NO-GO (구조 보강 전 구현 시작 금지)**

`AI합의 N/4`로 자동 이력을 정직하게 남기고, 원문 불충분 시 null로 남기며, 사람확정과 구분한 점은 맞다. 그러나 현재 3/4는 서로 다른 **판별기**일 뿐 서로 다른 **근거원**이 아니다. 같은 차종마스터·별칭·원문 결함을 공유하면 3개가 같은 오답을 내도 확정된다. 아래 7개 중 1·2·3·5·6·7은 구현의 사소한 빈칸이 아니라 확정 안전성의 구조 조건이다.

## Claude에게 전달 — 왜 지금은 자동 확정이 안 되는가

사장님 기준으로 아주 단순히 말하면, **"세 명이 같은 답을 냈다"와 "세 명이 원문으로 맞다고 확인했다"는 다르다.**

지금 네 판별기는 모두 같은 공급사 원문과 같은 차종마스터를 본다. 차종마스터의 별칭이나 코드가 틀리면 세 파서가 서로 다른 방식으로 계산해도 같은 틀린 코드를 낼 수 있다. 이 상태에서 3/4를 확정하면, 한 번 틀린 값이 상품마스터 잠금 → 정제칸 → F01 → ERP로 전파되고 다음 시간에는 잠금 때문에 다시 의심하기도 어려워진다.

또한 원문에 배기량·연료 등이 비어 있으면 감사기가 비교할 재료가 없다. 이때는 "문제 없음"이 아니라 "확인 못 함"이다. 확인 못 한 차를 자동 확정하면 추정 금지 원칙을 어긴다.

따라서 구조를 버리자는 뜻이 아니다. 아래를 넣으면 된다.

1. 같은 마스터를 쓰는 표들은 독립 3표가 아니라 한 근거 그룹으로 센다. 마스터 밖의 근거가 없는 차는 검수대기로 둔다.
2. 감사 결과를 통과/실패/미검사로 나누고, 미검사는 확정하지 않는다.
3. 철회된 차량은 같은 원문·같은 마스터·같은 판별기 버전으로 다시 자동 확정하지 않는다. 반복되면 사람 큐다.
4. 판별기별 null율·오류율·실행시각을 기록해 한 판별기가 죽으면 전체 확정을 멈춘다.
5. 확정 뒤 F01 4탭, 천이, ERP가 차량번호·상태·사진·대여료까지 모두 같은지 검사한 뒤에만 완료로 기록한다.

이 다섯 가지가 들어가면, 자동화는 사람을 대신해 "확실한 것만" 처리하고 애매한 차만 사람에게 올리는 구조가 된다.

| 가정 | 판정 | 근거 / 반례 / 구현 전 닫을 것 |
|---|---|---|
| 1. 독립성 | **구멍** | 4개 경로가 모두 같은 공급사 원문과 차종마스터를 읽는다. `snapToMaster`, playbook, 토큰화, 역인덱스는 파서만 다르며 마스터의 잘못된 별칭·제원·행키를 함께 믿는다. `3/4`를 독립 3표로 계산할 수 없다. 최소 하나는 차종마스터와 독립인 근거(공급사 상세 제원·OEM/엔카 식별값·사람 검수 결과)로 검증해야 하며, 같은 마스터 계열 표는 ‘상관 그룹 1표’로 묶어야 한다. |
| 2. 감사 ground truth | **구멍** | 감사기의 코드 제원도 마스터, 역검증의 표준차명도 마스터다. 원문 배기량·연료·구동·인승이 비면 모순 검사가 ‘통과’가 아니라 ‘검사 불가’다. 필드별 원문 근거율, 독립근거가 있는 확정 비율을 먼저 측정하고, 근거 없는 감사는 PASS가 아닌 `미검사/검수대기`로 처리해야 한다. |
| 3. 철회↔재확정 진동 | **구멍** | N회 철회 상한은 있으나, 같은 원문 버전·같은 마스터 버전·같은 판별기 버전으로 철회된 코드를 다시 확정하지 않는 불변키가 없다. 자동 철회 후 다음 시간에 같은 3표가 다시 확정될 수 있다. `evidenceHash + masterVersion + deriverVersion`별 재확정 금지와 시도 이력, N회 도달 시 즉시 사람 큐 전환을 집계기 계약에 넣어야 한다. |
| 4. 3+ 수확량 | **못정함** | 실측 분포가 없다. null은 표가 아니며 `3+`는 ‘4개 전체 중 같은 **non-null 코드** 3개’임을 명시해야 한다. 공급사별 총대수·각 판별기 non-null율·같은 non-null 3+/4 도달율·검수대기율을 드라이런으로 재고, 최소 수확 기준과 급락 경보를 정한 뒤 결정한다. |
| 5. 판별기 건강신호 | **구멍** | 현재 설계에는 판별기별 입력수·성공수·null율·오류율·실행시각·버전·전 회차 대비 변동·타임아웃이 없다. 한 판별기가 전부 null 또는 낡은 결과를 내도 합의율만으로는 조용히 고장 난다. 이 지표가 기준선에서 벗어나면 집계·확정 쓰기를 막는 health gate가 필요하다. |
| 6. 마스터 교정 전파 | **구멍** | 확정값은 fill 재추정을 막는다. 마스터의 이름/트림만 교정돼도 제원 감사가 안 울리면 기존 잠금은 계속 남는다. `마스터 행키/버전 → 확정 차량번호` 역참조를 저장하고, 마스터 변경 시 관련 확정 건을 `재검증대기`로만 되돌려 새 근거로 다시 합의시키는 경로가 필요하다. 자동 덮어쓰기는 금지다. |
| 7. 완료조건 배선 | **구멍** | 문서에는 F01↔천이↔ERP 전 필드 재대조가 있으나, 시간잡 순서에 실제 검사·같은 스냅샷 ID·실패 시 다음 쓰기 차단·이미 쓴 ERP의 보정/롤백이 정의되지 않았다. 4탭 F01, 천이 카드, ERP를 한 실행 ID로 읽고 대조 결과가 green일 때만 완료로 기록해야 한다. 읽기 실패/부분 실패는 PASS가 아니라 실행 실패다. |

## 구현 전 수정 요청

1. 합의 규칙을 ‘코드 3개 일치’에서 **상관 그룹이 다른 3개 근거의 일치**로 바꾼다. 독립 근거가 부족하면 자동 확정이 아니라 검수대기다.
2. 감사기는 `PASS / FAIL / 미검사` 3값으로 만들고 `미검사`는 자동 확정 불가로 취급한다.
3. 「AI합의」에 원문 스냅샷 해시, 마스터 버전, 각 판별기 버전·실행시각·근거필드, 철회횟수·격리사유를 추가한다.
4. 판별기 health gate와 수확량 기준선을 드라이런으로 수치화한 뒤에만 매시간 자동 확정을 켠다.
5. F01 4탭·천이·ERP의 대조를 집계 뒤 필수 게이트로 배선한다. `npm run check:sync`가 현재 매뉴얼 열 수 드리프트로 실패하므로, 그것부터 green으로 만든다.

## 유지할 원칙

- 자동 결과의 원천은 `AI합의 N/4`이며, 실제 사람 확인 전에는 `사람확정`으로 기록하지 않는다.
- 원문에 근거 없는 값은 null/검수대기다.
- 상품마스터·차종코드 쓰기와 철회 쓰기는 Cursor만 수행하며, 대상 백업·실행 ID·재읽기 검증과 사용자 직전 승인이 필요하다.

## 1-1. `Atomics.wait` 메인 스레드

- **확인함** — 이 로컬 Windows Node 실행 환경에서 메인 스레드 `Atomics.wait`는 허용된다.
  - 재현: `new Int32Array(new SharedArrayBuffer(4))`로 25ms 대기 → `timed-out`, 실제 경과 25ms, 예외 없음.
  - 근거 코드: `scripts/hourly-sync.mts:89`.
- **확인함** — timeout을 지정한 대기이며, 매 호출마다 새 `SharedArrayBuffer(4)`를 만드는 것은 이 사용 방식에서 유지되는 누적 객체가 아니다. 30초 대기는 OS 스케줄링 오차를 제외하고 timeout까지 잠든다.
  - 근거: `scripts/hourly-sync.mts:89,102`.

## 1-2. PID 잠금

- **확인함** — Windows Node에서 `process.kill(pid, 0)`은 현재 프로세스에는 성공하고, 존재하지 않는 PID에는 `ESRCH`를 낸다.
  - 재현: 현재 PID → `alive`; PID `2147483647` → `ESRCH`.
  - 근거 코드: `scripts/hourly-sync.mts:48-51`.
- **어긋남** — 죽은 PID JSON lock이 즉시 풀리지 않는다.
  - 근거: `scripts/hourly-sync.mts:48-53`에서 죽은 PID의 `process.kill(..., 0)`가 예외를 내면 catch로 빠지고, `:54`가 lock 수정시각 6시간 미만이면 여전히 `true`를 돌려준다. 따라서 비정상 종료 후 새 실행은 최대 6시간 건너뛴다.
- **어긋남** — PID 재사용을 구별하지 못한다.
  - 근거: lock에는 `pid`와 문자열 `startedAt`만 쓰지만(`scripts/hourly-sync.mts:57`), `lockHeldByLiveRun()`은 PID 생존만 보고 `startedAt` 또는 프로세스 생성시각을 대조하지 않는다(`:48-51`). OS가 같은 PID를 다른 프로세스에 재사용하면 자동동기라고 오인한다.
  - 조치 방향: lock에 heartbeat/lease를 두고 실행 중 갱신하거나, PID 생존과 프로세스 생성시각을 `startedAt`과 함께 대조해야 한다. 이 점검에서는 수정하지 않았다.
- **확인함** — `EPERM` 등 생존 판정 예외는 시간 판정으로 보수적으로 넘어간다. 다만 위와 같이 그 시간은 6시간이다.
  - 근거: `scripts/hourly-sync.mts:53-54`.
- **모르겠음** — PID 없는 옛 lock에 6시간이 운영상 적절한지는 실제 최장 실행시간·장애 복구 SLA가 정해져 있지 않아 판정할 수 없다.

## 1-3. 경고 후 exit 1

- **확인함** — aiops와 동일하게 실패 단계를 모두 계속 실행한 뒤 최종 exit 1을 내는 방식이다.
  - 근거: `C:/dev/aiops/scripts/손오공-매일.mjs:24-35,79-87`; 프리패스 `scripts/hourly-sync.mts:386-389`.
- **모르겠음** — 실제 Windows 작업 스케줄러가 exit 1에 대해 자동 재시도하도록 설정돼 있는지는 스케줄러가 아직 등록되지 않아 확인할 수 없다.
  - `scripts/hourly-sync.cmd`는 errorlevel을 그대로 반환할 뿐 재시도 정책을 정하지 않는다.
- **모르겠음** — 재시도 시 이미 반영한 발행·ERP·천이 전체를 재실행해도 항상 안전한지는 실제 `--apply` 재실행 결과와 각 하류 시스템의 멱등성 증거가 없어 확인할 수 없다.

## 1-4. 손오공 탭 발행 가드

- **확인함** — 계정이 있는데 ⓪ pull·정제·재고시트 중 하나가 실패하면 해당 `run()` 결과가 기록된 뒤 즉시 `stop()`하므로 손오공 탭 발행까지 도달하지 않는다.
  - 근거: `scripts/hourly-sync.mts:212-229`; `run()`의 단계 기록은 `:108-112`, 중단은 `:190-199`.
- **어긋남** — `--손오공없이`일 때 손오공·픽업 탭은 안 찍지만, ERP 동기와 천이는 그대로 실행된다.
  - 근거: 손오공 탭만 조건부다(`scripts/hourly-sync.mts:280-293`). ERP 동기는 무조건 실행(`:320-321`), 천이도 무조건 실행(`:363-364`)한다. 두 호출에 손오공 제외 범위를 넘기는 인수도 없다.
  - 따라서 기존 손오공 판매탭·손오공 정제시트가 낡아 있는 경우에도 하류 ERP·천이에 그 상태가 다시 반영될 경로가 남아 있다.

## 1-5. `steps[]`와 중단 상태

- **확인함** — `run()` 뒤 `stop()`되는 실패는 마지막 실패 단계가 `steps[]`에 먼저 기록된다.
  - 근거: `run()`이 `steps.push()`를 수행한 뒤 반환한다(`scripts/hourly-sync.mts:108-112`). 호출부는 반환 뒤 `stop()`한다(예: `:213-216`).
- **어긋남** — 계정 없음으로 ⓪에서 중단되는 경우는 `steps[]`에 ⓪ 실패 단계가 없다.
  - 근거: `scripts/hourly-sync.mts:230-239`은 `run()` 없이 바로 `stop()`한다. `stop()`은 경고·중단 사유만 쓰며(`:190-195`) `steps.push()`는 하지 않는다.
- **확인함** — 이 ⓪ 중단의 `커버리지` JSON 값은 숫자 0이 아니라 `null`이다.
  - 근거: 초기값 `null`(`scripts/hourly-sync.mts:72`)이고, 계정 없음 분기에서는 값을 설정하지 않은 채 `writeStatus()`한다(`:230-239`, `:182-187`).
- **모르겠음** — 상태로그 소비자가 `null`을 “모름”으로 표시하는지는 소비자 코드·실행 결과를 이번 점검 범위에서 확인하지 않았으므로 판정하지 않는다.

## 결론

**어긋남** — 1차 지적 중 429 대기·경고 실패 기록·계정 없는 기본 apply 차단·매뉴얼 상충은 반영됐다. 그러나 죽은 PID lock의 6시간 차단, PID 재사용, `--손오공없이`에서 ERP·천이를 계속 실행하는 경로, 상태로그 커버리지 필드 누락, 계정 없음 중단의 `steps[]` 누락이 남아 있다. 이 어긋남이 해소되기 전에는 스케줄러를 켜는 판정을 내릴 수 없다.

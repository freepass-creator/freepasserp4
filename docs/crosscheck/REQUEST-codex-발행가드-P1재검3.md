# 코덱스 재검 3차 — 발행 0대 가드 «게이트=직전표 / 스냅샷=사면보조» 재설계 (2026-09-07)

검사만·고치지 마라. 판정은 tmp/codex-P1재검3-verdict.md 에 GO/NO-GO 로.

## 2차 NO-GO 를 어떻게 받았나
2차에서 코덱스가 «코드 스냅샷을 유일 기준선으로 삼으면 스냅샷이 없/헐/낡을 때 보호를 건너뛰고 발행해
배포된 라벨 가드가 막던 소실을 통과시킨다»(반례 7개: 스냅샷없음·oops·빈대수·중복코드0·낡은스냅샷 등)고 했다. 맞다.

**⇒ 설계를 뒤집었다. 스냅샷을 «게이트»에서 완전히 뺐다.**
- **게이트 = 항상 «직전 발행 표»**(그 표는 발행 뒤 늘 존재 — 시딩 창 자체가 없다). 직전 표의 「공급사」 칸을 세되
  «표시명»이 아니라 «코드»로 환원해서 센다. 직전 코드가 이번 발행에 통째로 0대면 throw.
- **코드 환원 다리 둘** — ㉠ 지금 문패(supplierNameKeys·SPELL_PAIRS, 유일매핑만) ㉡ 스냅샷이 기억한
  «지난 발행 이름→코드»(지금 문패로 못 잇는 임의 개명까지 잇는다, 헤더 맞을 때만).
- **사면** — 직전 라벨이 코드 k 로 환원되고 그 k 가 이번 발행에 살아 있으면(nowByCode.get(k)>0) 개명으로 보고 0대 오발동을 사면.
- **스냅샷은 «사면 보조»일 뿐 게이트가 아니다** — 없/헐/낡/손상이면 다리 ㉡가 비어 사면이 덜 될 뿐,
  가드는 직전 표로 그대로 막는다. 즉 **엄격히 배포본(라벨+supplierNameKeys) 이상**이고, 소실 미감지 창이 없다.

관련 코드: `scripts/publish-origin-tab.mts` 가드 871~915(게이트=prevRows·환원=codeOf·사면=nowByCode), 스냅샷 쓰기 966~990, rowCode 329·640~652, nowByCode 851~852.

## 확실히 답해 달라
1. **2차 반례 7개 재검** — 아래 각 상황에서 새 코드가 «배포된 라벨 가드»와 «같거나 더 엄격»한가(즉 라벨 가드가 막는 걸 통과시키지 않는가):
   ① 스냅샷 없음 ② 스냅샷 oops(비숫자) ③ 빈/공백 대수 ④ 같은 코드 뒤에 0 중복행 ⑤ 낡은 스냅샷(직전 출력보다 오래) ⑥ 헤더 손상 ⑦ 데이터 없음.
   핵심: 게이트가 직전 표(항상 존재)로 옮겨졌으니 스냅샷 상태와 «무관하게» 소실이 잡히나?
2. **사면이 진짜 소실을 사면하나** — nowByCode.get(k)>0 사면이, 실제로 코드 k 가 0대가 된 진짜 소실을 잘못 사면하는 반례가 있나?
   (k 는 직전 라벨을 ident 로 환원한 코드. rowCode 로 센 nowByCode 가 코드 k 의 현재 유무를 권위 있게 답하나?)
3. **개명 재발 차단** — 공급사명을 ㉠SPELL_PAIRS(에스에이↔SA) ㉡임의 개명(문패로 못 잇는) 어느 쪽으로 바꿔도,
   코드가 이번 발행에 살아 있으면 발행이 «안 멈추나»? ㉡는 스냅샷 다리가 없으면 (보수적으로) 막히는데, 그게 «배포본과 동일하거나 더 나음»이 맞나?
4. **오·미스브리지** — 이름 유일매핑(codes.size===1)이 서로 다른 두 회사를 한 코드로 잘못 사면하는 반례가 있나(가온렌터카/가온캐피탈류)?
5. **엄격 배포 판정** — 이 재설계가 «현재 운영에 있는 라벨+supplierNameKeys 가드»보다 회귀 없이 엄격히 안전한가. §4(공유문서 탭배정 이름의존)는 별건.

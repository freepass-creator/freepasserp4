## ★1. 고치면서 «새로 생긴» 걱정 — 여기를 봐 달라

### 1-1. `Atomics.wait` 를 메인 스레드에서 쓴 것

- Node 의 메인 스레드에서 `Atomics.wait` 가 **허용되는가?**(브라우저는 막는다)
- 30초를 정확히 자고 깨는가? `SharedArrayBuffer` 를 매번 새로 만드는 것이 문제되지 않는가?

### 1-2. PID 잠금이 윈도우에서 맞게 도는가

```ts
process.kill(Number(held.pid), 0);   // 살아 있으면 예외 없음
```

- **윈도우에서 `process.kill(pid, 0)` 이 정말 «생존 확인»으로 동작하나?**
- **PID 재사용** — 죽은 PID 를 OS 가 다른 프로세스에 다시 줬으면 「살아 있다」고 오판해
  **자동동기가 영영 안 돈다.** 이게 제일 무섭다. 어떻게 막나?
- 권한 문제(EPERM)로 예외가 나면 `catch` 가 삼키고 시간 판정으로 떨어진다 — 그게 맞나?
- 옛 형식(시각 문자열) lock 의 6시간 판정이 적절한가?

### 1-3. 「실패해도 계속 간다」와 「exit 1」이 같이 있는 게 맞나

⑦~⑪ 은 실패해도 다음 단계로 간다. 그런데 마지막에 `exit 1` 이다.

- 스케줄러가 `exit 1` 을 보고 **재시도**하도록 설정돼 있으면, 이미 발행까지 끝난 회차를
  통째로 다시 돌게 된다. 그게 안전한가? (지금 `hourly-sync.cmd` 는 `exit /b %errorlevel%` 만 한다)
- aiops 는 어떻게 하고 있나? 같은 규격인가?

### 1-4. 손오공 탭 발행 가드가 «반쪽»은 아닌가

`손오공탭발행 = existsSync(손오공계정)` 로 판정한다.

- 계정은 **있는데 ⓪ 이 실패**하면? → `stop()` 이 먼저 걸리니 도달 못 한다고 봤다. 맞나?
- `--손오공없이` 로 돌면 손오공·픽업 탭을 안 찍는데, **⑦ ERP 동기와 ⑩ 천이는 그대로 돈다.**
  손오공 탭이 낡은 채로 ERP·천이에 반영되는 것 아닌가? **여기가 제일 자신 없다.**

### 1-5. `steps[]` 가 «중단된 단계»를 빠뜨리지 않나

`stop()` 은 `run()` 이 돌려준 뒤에 호출된다. 그러면 실패한 그 단계도 `steps[]` 에 들어간다고 봤다.

- 실제로 상태로그에 **마지막 실패 단계가 들어가는지** 확인해 달라.
- ⓪ 이 `stop()` 될 때 `커버리지` 는 `null` 인데, 그게 「모른다」로 읽히나 「0%」로 읽히나?

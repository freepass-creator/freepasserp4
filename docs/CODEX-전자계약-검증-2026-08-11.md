## 1. 되돌리지 마라 — 설계보다 나은 판단들

이건 칭찬이 아니라 **경계 표시**다. 나중에 리팩터링하다 지우면 실무 사고가 난다.

| 무엇 | 왜 남겨야 하나 |
|---|---|
| **정책 3중 BLOCK** (`esign-center.ts`) | 「정책이 다른 공급사 것」은 설계서에 없던 것이다. 남의 정책으로 계약서가 나가면 보험·면책·연령이 통째로 틀린다. 실무에서 실제로 나는 사고다 |
| **만 21세 미만 BLOCK** | 보험 운영 대상 밖이다. 계약이 성립해도 보험이 안 붙는다 |
| **연락처 «형식»까지 검사** (`\d{10,11}`) | 「있음」만 보면 「없음」이라 적힌 칸도 통과한다 |
| **대표자·입금계좌·예금주를 WARNING 으로** | 설계서 §6 은 「없으면 계약서가 미완성」이라 했지만 BLOCK 으로 막으면 아무도 못 보낸다. WARNING 이 옳다 |
| **`sign_status === '서명완료'` 재발송 차단** | 완료 계약서는 못 고친다는 원칙이 코드로 서 있다 |

## 2. 고칠 것 — 우선순위 순

### ★1. `contract_source` 를 클라이언트가 정한다

```ts
// lib/domain/esign-center.ts:17
export function esignContractSource(contract) {
  const explicit = S(contract?.contract_source);   // ← 계약 레코드의 값을 그대로 믿는다
  if (explicit === 'excel' || explicit === 'direct' || explicit === 'erp') return explicit;
  ...
}
```

서버 어디에도 `contract_source` 를 **쓰는** 코드가 없다. 클라이언트가 RTDB 에 직접 쓴다.
그러면 ERP 계약에 `contract_source: 'excel'` 을 넣어 **약정 단계를 건너뛸 수 있다.**

발송이 관리자 전용이라 외부 공격은 아니다. 문제는 감사다 —
**약정 없이 나간 계약이 ERP 계약과 구분되지 않는다.** 나중에 「왜 약정이 없냐」에 댈 것이 없다.

**고치는 방향 (둘 중 하나, 또는 둘 다)**

1. **RTDB 규칙에서 잠근다** — `contract_source` 는 생성 시 1회만 쓰이고 그 뒤 변경 불가.
   금액 필드를 동결한 것과 같은 방식(`!data.exists()`).
2. **서버가 발행 시점에 재판정한다** — 클라이언트 값을 참고만 하고,
   실제 판정은 `contract_origin`·생성 경로·`created_by` 로 서버가 다시 세운다.

어느 쪽이든 **발행 시점에 «이 계약이 왜 독립 발송인지»를 이벤트로 남겨라.**
`appendFreepassEsignEvent(code, 'issued', { source, reason })` 한 줄이면 된다.

### ★2. 검사가 자기충족일 수 있다 — 실제 발송을 한 번 돌려라

13종 sim 이 통과하지만, 그 검사는 코덱스가 자기 코드에 맞춰 썼다.
`sim-esign-source-gate` 가 통과한다고 «ERP 무관 발송이 실제로 된다»가 증명되지는 않는다 —
같은 함수를 불러 같은 답을 확인한 것일 수 있다.

**실제로 한 번 보내 봐야 안다.** 재료는 이미 있다.

```
계약   CT-TEST-01  (is_test: true · 실계약 목록에 안 섞인다)
도구   scripts/make-test-contract.mts  (--list · --remove 로 정리 가능)
```

확인할 것 넷:

```
1  contract_source='direct' 계약이 provider_agreement_done 없이 발행되는가
2  같은 계약을 source='erp' 로 두면 여전히 막히는가          ← 이게 더 중요하다
3  발행 뒤 원본 계약·정책·업체 고정값을 바꿔도 서명 링크의 내용이 그대로인가
4  BLOCK 이 하나라도 있으면 실제로 403/409 가 나는가
```

3번이 특히 중요하다. Snapshot 이 안 굳으면 **손님이 본 것과 보관본이 달라진다.**
그건 계약이 아니다. `sim-esign-snapshot` 은 통과하지만 그것도 같은 코드를 부른 결과다.

### ★3. 낡은 검사 2건 — 코드는 멀쩡하다

`sim-esign-compliance` 21/23. 둘 다 **오탐**이다.

```
✗ §3① 약관 전문이 실린다     sections.length === 22 로 개수를 박아 뒀는데 23 이 됐다
✗ 주민번호를 보내지 않는다     /ssn/i 가 단어 경계 없이 무관한 글자에 걸린다
```

payload 에 주민번호는 없다(`residentNumber`·`jumin`·`주민등록번호` 전부 없음).

**고치는 방향**

- 약관: 개수 고정 대신 **정본과 payload 가 같은지**를 본다.
  `p.agreement.sections.length === AGREEMENT.sections.length` 또는 본문 해시 비교.
  조문을 고칠 때마다 검사가 깨지면 아무도 안 고친다.
- PII: 짧은 토큰은 경계를 준다. `\bssn\b` · `resident_?number` 처럼.
  **오탐이 섞이면 진짜 유출을 발견해도 아무도 안 믿는다.** 그게 이 검사의 값을 없앤다.

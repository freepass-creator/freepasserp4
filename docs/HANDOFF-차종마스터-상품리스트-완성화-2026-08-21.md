# 차종마스터 → 공급사 정제 → 상품리스트 완성화 인수인계

작성: 2026-08-21 (Codex)  
목표: 공급사 원문이 불완전해도 현재 재고를 한 번 차종마스터에 흡수하고, 이후 신규분만 자동 보류·보강 대상으로 남겨 상품리스트에 안전하게 반영한다.

## 현재 판정

- **상품리스트 전체 반영 GO 아님.** 현재는 대표 시트 dry-run과 로직 수정까지만 끝났고, 차종마스터 신규·공급사 20개·상품리스트에는 이 작업으로 실제 write를 하지 않았다.
- 정제칸↔신규 차종마스터 읽기 전용 대조: 판매 가능 483대, 핵심 정제칸 빈 33대, 신규 엔카 원자 시트에 직접 없는 세부모델 표기 248건.
- 248건은 곧바로 248개 오류가 아니다. 신규 엔카 원자 시트(4075행/428 세부모델)와 앱 이름사전(`public/data/vehicle-master.json`, 1813 세부모델)의 범위·별칭이 다르므로, **현재 재고를 마스터 보강 입력으로 써야 한다.**

## 이번에 반영한 코드 개선

1. `scripts/stamp-encar-codes-on-supplier.mts`
   - 누락된 `fuelKey`, `canonMakerDisplay` import를 추가했다.
   - 검증: `npx tsx scripts/stamp-encar-codes-on-supplier.mts --who=경진카` dry-run 완료 (4대 M/SM/T 유지, 오류 0).

2. `lib/domain/vehicle-class.ts`
   - 원문/스냅에서 인승이 9 이상이면 정적 모델 분류보다 우선해 MPV를 반환한다.
   - 회귀: 팰리세이드 LX3 9인승=`대형 MPV`, 7인승=`대형 SUV`.

3. `scripts/fill-supplier-ai-columns.mts`
   - 분류값은 과거 규격채택의 낡은 값보다 현재 원문 신호 기반 스냅을 우선한다. 과거 값은 스냅 불가 시에만 fallback이다.
   - 분류에 `snap.seats`를 넘긴다.
   - 빌린카 dry-run 확인:
     - 그랑 콜레오스 `중형 MPV → 중형 SUV`
     - 팰리세이드 9인승 `대형 SUV → 대형 MPV`

4. `AGENTS.md`
   - 자동 작업은 수정이력·재검증·보류/실패 사유를 남기고, 개선/문제 시 `pyh@teamjpk.com`으로 메일 보고하도록 공통 규칙을 추가했다.

## Cursor가 구현할 작업 순서

### 1) 현재 재고 기반 마스터 보강 계획기

- 활성 공급사 **20개 물리 문서/23개 코드**만 고정 allowlist로 읽는다. Drive 이름 검색만으로 대상 선정하지 않는다.
- `[구버전·폐기]` 문서는 제외하고, `readSupplierSheet`의 숨김 행·숨김 탭·고정 gid·헤더 어댑터 규칙을 사용한다.
- 각 차량의 원문 차명·제조사·연식·연료·배기량·인승·구동·트림을 모아 다음 세 갈래로 출력한다.
  1. `ALIAS`: 이름사전에 이미 있는 세부모델의 표기 흔들림
  2. `ATOM_ADD`: 신규 엔카 차종마스터에 없는 세부모델/원자 제원
  3. `HOLD`: 후보 복수, 원문 축 부족, 서로 충돌하는 근거
- 결과는 먼저 `tmp/` 계획 JSON/CSV로만 쓴다. Google Sheet write 금지.

### 2) 차종마스터 보강 규칙

- 이름 정본은 `public/data/vehicle-master.json`; 엔카 신규 시트는 M/SM/T/U 원자·제원 정본이다. 옛 ERP 원천대장(`1T_Rr...`)의 이름/제원을 새 정본으로 되살리지 않는다.
- 동일 차량번호가 아닌 서로 다른 현재 재고에서 같은 원자 조합이 반복되고, 연료·배기량·인승·세대코드가 모순 없을 때만 자동 `ATOM_ADD` 후보로 올린다.
- 별칭은 세부모델의 개발코드/세대를 보존한다. `디 올 뉴`·`더 뉴` 등 광고 접두를 새 세대로 만들지 않는다.
- 전기차 배터리 kWh·2WD/4WD 숫자를 배기량으로 만들지 않는다.
- 9인승·7인승처럼 동일 세부모델에서 차체형태가 갈리면 인승을 원자 선택 축으로 보존한다.

### 3) 적용 파이프라인

1. 마스터 보강 계획 생성 → 사람이/사용자가 대상·행 목록 승인
2. 신규 차종마스터에 반영 후 즉시 재읽기
3. `fill-supplier-ai-columns` 전체 dry-run (`--include-mirror`)과 `stamp-encar-codes-on-supplier` 전체 dry-run
4. 확정 원자만 공급사 정제칸 및 M/SM/T에 반영
5. 재읽기 대조 후 상품리스트 발행 및 ERP/상품시트 parity 확인

## 금지/주의

- 마스터에 없는 차량을 비슷한 차로 강제 매칭하지 않는다.
- 분류를 모델명 하나로만 결정하지 않는다. 원문 인승·연료·배기량을 우선한다.
- 기존 `fill-supplier-ai-columns.mts`에는 다른 작업자의 미커밋 변경이 있다. 위 개선을 보존하고 덮어쓰지 말 것.
- 외부 Google Sheet 실제 write는 대상·범위·최신 재읽기 후 사용자 직전 승인에 한정한다.

## 완료 조건

- 현재 판매 가능 재고 전체에 대해 `AUTO`/`HOLD`가 빠짐없이 산출된다.
- `AUTO`는 정확히 하나의 원자 차종으로 재현 가능하고, `HOLD`에는 이유가 있다.
- 활성 공급사 전체 dry-run에서 구버전 문서·숨김 행이 섞이지 않는다.
- 상품리스트 반영 전후 차량번호·제조사·모델·세부모델·연료·배기량·차종분류·M/SM/T를 재읽기로 대조한다.
- 모든 개선/보류/실패는 수정이력과 `pyh@teamjpk.com` 메일 보고에 남긴다.

### 차단: 실제 반영 전 반드시 고칠 것

1. **기존 별칭을 `ATOM_ADD`로 잘못 분류한다.**
   - 계획 결과: `AUTO 425 / ALIAS 32 / ATOM_ADD 16 / HOLD 8`.
   - `ATOM_ADD 16`은 3개 기존 정본의 반복 행이다: `G80 RG3 FL → 더 뉴 G80 RG3`(4대), `GV80 JX1 FL → 더 뉴 GV80 JX1`(3대), `모델 Y FL → 더 뉴 모델 Y`(9대).
   - 원인: `genShift`가 원문 FL/엣지만 보고, 이미 high/medium으로 매칭된 `더 뉴 …` 정본을 같은 페이스리프트 표기로 인식하지 못한다.
   - 수정: **high/medium 스냅 + 기존 json 세부모델이면 `ALIAS`를 먼저 판정**한다. 진짜 신규 세대/원자는 기존 정본과 세대코드·연식·제원이 모두 다를 때만 `ATOM_ADD` 후보가 된다.

2. **배기량을 스냅 입력에 넣지 않는다.**
   - 계획기는 `배기량`을 읽지만 `snapToMaster` 호출 객체에는 `engine_cc`가 없다 (`scripts/plan-inventory-master-gap.mts` 152~165행).
   - 수정: 정규화한 cc를 `engine_cc`로 전달하고, 전기/수소는 cc 공란을 유지한다. 같은 세부모델의 가솔린·하이브리드·디젤 변형을 이름만으로 `AUTO` 처리하지 않는다.

3. **엔카 원자 호환을 실제로 검증하지 않는다.**
   - 현재 엔카 캐시는 세부모델 존재와 연료 집합만 읽고, `AUTO` 판정은 `inEncar` 존재 여부만 사용한다. 배기량·인승·구동·트림의 단일 원자 일치 검증이 없다.
   - 수정: 엔카 행을 `세부모델+연료+cc+인승+구동+트림` 후보로 보관하고, 정확히 하나일 때만 `AUTO`; 0개/복수는 `HOLD`다.

4. **후보는 행 단위가 아니라 원자 단위로 묶어야 한다.**
   - 동일 원자 9대(모델 Y FL)가 현재 `ATOM_ADD` 9행으로 나온다. 실제 마스터 보강 계획은 1개 원자 후보 + 근거 차량번호 목록이어야 하며, 같은 행을 여러 번 추가하면 안 된다.
   - `ALIAS`도 `원문 별칭 → 정본 세부모델` 단위로 중복 제거하고 차량번호·공급사 수만 근거로 붙인다.

### 재검증 게이트

수정 뒤 전체 계획에서 위 3개 별칭은 `ALIAS`가 되고, `ATOM_ADD`는 원자별 중복 0이며, 각 `AUTO`에 엔카 원자 ID 하나가 있어야 한다. 이 조건 전에는 신규 차종마스터·공급사·상품리스트 write 금지.

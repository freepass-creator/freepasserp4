## 2. ★고칠 것 — 약관 단(段)에 빈 공간이 남는다

사장님이 지적한 문제다. 5쪽 왼쪽 단 아래가 크게 빈다.

### 원인

두 규칙이 겹쳐서 생긴다.

**① 긴 문단을 쪼개는 장치가 정작 가장 긴 것을 건너뛴다**

```js
function splitFlowItem(el){
  if (el.classList.contains('t-art') || el.classList.contains('t-sub') || el.classList.contains('t-keep'))
      return [el];          // ← t-sub 를 통째로 둔다
  var txt = el.textContent || '';
  if (txt.length < 120) return [el];
  var ends = [], re = /[,;.!?](?=\s|$)/g;   // 쉼표·마침표에서만 끊는다
  …
}
```

약관에서 가장 긴 덩어리가 **`t-sub`** 다 — 제7조①(1~8호)·제15조 금지행위(1~8호)처럼
**호가 줄줄이 달린 항**. 그게 쪼개지지 않는다.

**② 조 제목은 첫 «문단 전체»와 같은 단에 두게 돼 있다**

```js
/* 조문 제목은 적어도 첫 문단과 같은 컬럼에 둔다. 제목만 하단에 남는 고아 제목 방지. */
if (items[idx].classList.contains('t-art') && items[idx+1]) {
  probe = items[idx+1].cloneNode(true);
  cols[ci].appendChild(probe);
}
```

제목 + 첫 항을 한 덩어리로 판정하는데, 그 첫 항이 안 쪼개지는 긴 `t-sub` 면
**둘이 통째로 다음 단으로 밀린다.** 앞 단에 남는 것이 그 여백이다.

실제로 5쪽은 왼쪽 단이 제6조에서 끝나고 여백이 남은 뒤,
오른쪽 단이 「제7조(회사의 계약 해지)」로 시작한다 — 제7조①이 8호까지 달린 가장 긴 항이다.

### 고치는 방향 — 권고 A

**A. `t-sub` 도 쪼갠다. 끊는 자리는 «호 번호 앞».**

```js
// 지금: 쉼표·마침표
var re = /[,;.!?](?=\s|$)/g;

// 권고: 호 번호 앞을 우선 경계로 삼는다. 「… 4. 차량을 …」 앞에서 끊는다.
//   법률 문서는 호 단위로 넘어가는 것이 자연스럽고 종이 약관도 그렇게 조판한다.
var re = /(?:^|\s)(?=\d{1,2}\.\s)/g;      // 1차: 호 경계
// 호가 없으면 지금처럼 문장 부호로 떨어뜨린다(2차).
```

`t-art`(조 제목)와 `t-keep` 은 지금처럼 쪼개지 않는다.

**B는 권하지 않는다** — 「제목 + 첫 두세 줄만 같은 단」으로 완화하는 방식.
제목 아래 한두 줄만 남고 넘어가서 오히려 읽기 나빠진다.

### 확인 방법

고친 뒤 각 단의 하단 여백을 재서, 한 단이라도 «다음 항목 하나가 들어갈 만큼» 비면 실패로 본다.
지금은 그 판정이 없어서 조판이 틀어져도 아무도 모른다.

## 3. 규격에서 어긋난 3건

`scripts/audit-contract-doc.mts` 가 잡은 것.

**① 계약서에 칸이 있는데 매핑이 없다 — 값이 영원히 안 붙는다**

```
engine_control_overdue_days   「청구일로부터 ○일 연체 시 시동제어」
auto_terminate_overdue_days   「○일 연체 시 계약 해지 및 차량 회수」
deposit_overdue_rounds        보증금 미납 회차
```

세 값 모두 **정책에 이미 들어 있다**(2026-08-12 32개 정책에 3일·10일·2회차로 채움).
`FIELD_MAP` 에 세 줄만 더하면 공급사마다 다른 기준일을 쓸 수 있다.
지금은 HTML 에 3·10 이 고정으로 박혀 있어 공급사가 달라도 같은 숫자가 인쇄된다.

**② 매핑에는 있는데 계약서에 칸이 없다**

```
vehicle_price       차량가 — 만기인수 계산 근거인데 문서에 안 보인다
deposit_round_4·5   5회 분납을 지원하는데 칸은 3회차까지
```

**③ 밖에서 오는 값인데 원자 지정이 없다**

```
payment_bank · payment_account_no · payment_account_holder   (파트너)
insurer_name                                                  (정책)
```

파트너에 **대표자·입금계좌** 칸 자체가 없다는 것은 별건으로 남아 있다.

## 4. 문서 채움 — 별개 작업

실계약으로 조립해 보면 **값이 필요한 117칸 중 38칸만 채워진다.**

| 출처 | 빈칸 | 성격 |
|---|---|---|
| 미정 | 32 | 담을 칸이 없다(인도·반납 기록 · 연대보증인 · 추가운전자 2·3) |
| 입력 | 18 | 화면에 칸은 있는데 안 받는다(보증금 회차 · 출금계좌 · 운전자 범위 · 만기인수) |
| 본인확인 | 10 | 주민번호·면허번호 — **우리가 안 받기로 한 것. 정상이다** |
| 파생 | 7 | 계약시작·종료일 · 보증금 총액 · 중도해지율 — **계산이 안 돈다** |
| 정책 | 5 | 승계 · 초과주행 · 사고다발 · 보험사 |
| 파트너 | 3 | 대표번호 · 임대인 주소 · **자동차대여사업 등록번호** |

**우선순위 셋**

1. **계약시작일·종료일** — 계약서에 기간이 없으면 문서가 성립하지 않는다(약관 제2조가 그 날짜를 부른다)
2. **중도해지율** — 약관이 「계약서에 정한 해지수수료율」을 곱하라는데 계약서에 없다. 위약금 근거가 사라진다
3. **자동차대여사업 등록번호** — 여객자동차법상 대여사업자 표시사항이다

**초과주행 요금**은 키가 갈려 있다. `FIELD_MAP` 은 `over_mileage_rate_per_km` 을 가리키는데
실제로 읽는 `overMileageRateFor()` 는 `over_mileage_rate_domestic` / `_imported` 를 본다.
정책에 채운 값과 읽는 키가 달라 계약서에 안 나온다.

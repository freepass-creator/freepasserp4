# Cursor 작업 오더 — 착한거래 ②·③ → 프리패스 ③·④

작성: Codex · 2026-08-10  
대상 저장소: `C:\dev\chakhandeal` + `C:\dev\freepasserp4`

> **최종 정정(사용자 원문 우선):** “비슷한 기능을 프리패스 UI로 새로 만들라”가 아니다.
> 착한거래 `ContractStudio`의 실제 ②·③ 패널을 착한거래 소유의 전용 embed 화면으로 분리하고,
> 그 화면 자체를 프리패스 ③·④에 표시한다. 현재 프리패스의 자체 `ChakhandealPane`·`ProgressPane`는
> 최종 결과물이 아니며, 이 정정과 충돌하는 아래의 ‘프리패스 UI로 렌더링’ 문장은 폐기한다.

## 0. 사용자 요구사항 — 이 문장이 완료 기준

- **최우선은 화면이다.** API·저장 흐름이 덜 끝났더라도 착한거래 ②·③의 화면을 프리패스 ③·④에 먼저 보이게 한다.
- `/esign` 최초 진입 즉시 ③·④에 착한거래 화면이 보여야 한다. 계약 선택, `계약서 신규 생성`, 데이터 저장을 기다리지 않는다.
- 착한거래 전자계약 스튜디오의 **② `데이터연동·링크`**를 프리패스 계약서관리의 **③ `착한거래 연동 및 발송`**으로 가져온다.
- 착한거래 스튜디오의 **③ `진행상황`**을 프리패스의 **④ `착한거래 진행상황`**으로 가져온다.
- 착한거래 ① 발송목록은 프리패스 ① 목록과 중복이므로 가져오지 않는다.
- 착한거래 ④ 고객 계약화면은 패널에 복제하지 않고 `열어보기` 링크로만 연다.
- `계약서 신규 생성`을 누르면 모달이 아니라 프리패스 **② 데이터 패널**에서 시작한다.
- ②의 정상 흐름은 **공급사 → 정책 → 표준계약서 3종 → 인수/반납 → 차량 입력방식 → 임차인 정보 → 최종 확인**이다.
- 차량 입력방식은 `재고 차량 선택`과 `신규 차량 직접 입력` 두 가지다.
- `재고 차량 선택`에서는 기존 재고와 가격을 재사용한다. 차량의 실제 가격기간을 고르면 대여료·보증금이 자동 확정돼야 한다.
- `신규 차량 직접 입력`에서는 재고에 없는 차량과 계약금액을 새로 입력해 계약할 수 있다. 이 입력을 기존 재고 데이터처럼 위장하거나 재고를 자동 생성하지 않는다.
- ③은 ②에서 확정한 데이터를 다시 선택하는 곳이 아니다. **연동값 검증 → A4 초안/PDF → 착한거래 발송 링크 생성·복사·열기**만 담당한다.

### 0-1. 화면 우선 구현 — 지금 먼저 완료

- 기준 화면은 `C:\dev\chakhandeal\components\ContractStudio.jsx`의 ②(약 830행 이후)와 ③(약 989행 이후), 스타일 기준은 `ContractStudio.module.css`다.
- 위 JSX를 프리패스에서 눈대중으로 다시 만들지 않는다. 착한거래 저장소에서 실제 ②·③을 재사용 가능한 컴포넌트로 추출한다.
- 착한거래 ② 전용 embed 화면을 프리패스 ③에, 착한거래 ③ 전용 embed 화면을 프리패스 ④에 표시한다.
- 프리패스 ①·②와 착한거래 ④ 고객 화면은 가져오지 않는다.
- 계약 미선택, 신규 작성 전, 신규 작성 중, 프리패스 저장 전, 착한거래 발행 전에도 화면 골격은 항상 보여야 한다.
- 데이터가 아직 없으면 `—`, `0/8`, `아직 발행 전`을 표시하고 실행 버튼만 비활성화한다. 큰 빈 여백과 중앙 안내문 한 줄로 대체하지 않는다.
- **`프리패스 데이터 저장`을 화면 연동의 시작 조건으로 삼지 않는다.** ②에서 입력·선택하는 값은 저장 전 draft 상태로 즉시 ③에 전달돼 연동값과 누락값을 확인할 수 있어야 한다.
- ④도 처음부터 실제 진행상황 화면을 `0/8 · 발행 전` 상태로 보여준다. 링크가 발행되면 같은 화면에 상태만 채워진다.
- 저장은 ②·③에서 확인한 프리패스 계약 데이터를 확정하는 동작이다. 저장 때문에 ③·④가 처음 마운트되거나 빈 화면에서 화면으로 바뀌면 안 된다.
- `/esign` 최초 진입의 기본 상태는 ③ `연결됨 · 계약 미선택`, ④ `발행 전 · 0/8`이다.
- 목록에서 기존 계약을 고르면 이미 열린 ③·④에 해당 계약 데이터와 상태를 바꿔 끼운다.
- `계약서 신규 생성`을 누르면 이미 열린 ③에 ②의 draft 값을 실시간으로 바꿔 끼우고 ④는 `발행 전 · 0/8`을 유지한다.
- 1차 완료 기준은 사용자가 화면만 보아도 `착한거래 ②가 프리패스 ③에, 착한거래 ③이 프리패스 ④에 들어왔다`고 바로 알 수 있는 상태다.
- 화면 배치가 끝난 뒤 현재 회원사 API를 각 버튼과 상태에 연결한다. API가 덜 된 항목 때문에 화면 전체 구현을 미루지 않는다.
- embed 내부 화면의 글자·구조·스타일은 착한거래가 소유한다. 프리패스 디자인 토큰으로 다시 그리지 않는다.

### 0-2. 전용 embed 구조

착한거래에 운영용 전용 화면을 만든다. 이름은 기존 라우팅 규칙에 맞추되 역할은 아래 두 개로 고정한다.

- `link` 화면: 기존 ContractStudio ② `데이터연동·링크`만 렌더링
- `progress` 화면: 기존 ContractStudio ③ `진행상황`만 렌더링

필수 조건:

- 계약이 없어도 두 화면은 각각 빈 상태로 렌더링된다.
- 프리패스는 ③·④에서 두 embed를 `/esign` 최초 진입부터 항상 마운트한다.
- 선택 계약이나 신규 draft가 바뀌면 iframe을 없앴다 다시 만드는 대신 명시적인 메시지/세션 입력으로 같은 화면의 데이터만 갱신한다.
- `postMessage`를 쓰면 송수신 origin을 양쪽의 설정된 정확한 origin으로 검증하고 메시지 스키마를 검증한다. `*` 사용 금지.
- API Key를 URL·브라우저·postMessage에 넣지 않는다. 실제 계약 접근은 프리패스 서버가 만든 짧은 수명의 제한된 embed session 또는 서버 프록시를 사용한다.
- embed URL에는 장기 토큰, 고객 개인정보, 계약 원문을 query string으로 넣지 않는다.
- iframe에는 필요한 최소 `sandbox`/`allow` 권한만 주고, 팝업·다운로드·클립보드는 실제 버튼에 필요한 범위로 제한한다.
- 로컬은 `localhost:4004 ↔ localhost:3000`, 운영은 환경설정 origin만 허용한다.

## 1. 절대 금지

- `http://.../labs/...` 전체 페이지나 API를 프리패스 운영 코드에서 호출하지 않는다. `/labs`는 데모 전용이다.
- `/labs/contract-studio` 전체를 iframe으로 넣지 않는다. 목록 ①·고객화면 ④까지 섞인 데모 페이지다.
- 대신 착한거래에서 ②·③만 재사용하는 운영용 embed route/component를 만든다. 이 전용 embed 화면은 허용하며 이번 요구사항의 핵심이다.
- API Key를 브라우저에 노출하지 않는다. 프리패스 서버 라우트만 `Authorization: ApiKey ...`를 사용한다.
- 신분증·셀카·서명 파일의 내부 경로나 원본 URL을 회원사 상태 응답에 넣지 않는다.
- v3 write, `database.rules.json`, 운영 데이터, 배포 설정을 건드리지 않는다.
- `재고 차량 선택` 경로에 차량명·기간·대여료·보증금 수기 덮어쓰기나 임의 가격 fallback을 만들지 않는다.
- 직접입력은 사용자가 `신규 차량 직접 입력`을 명시적으로 고른 경우에만 연다. 재고 조회 실패를 직접입력으로 조용히 전환하지 않는다.
- 공급사·정책·차량·가격기간이 맞지 않으면 조용히 보정하지 말고 생성 불가 사유를 표시한다.
- 새 raw `<input>/<textarea>/<select>/<button>`을 만들지 않는다. 프리패스 UI는 기존 `Input`·`Textarea`·`Btn`·`Badge`·`ListGroup`·`DetailRow` 등 공용 원자만 사용한다.
- 현재 양쪽 저장소가 dirty다. **수정 직전에 파일을 다시 읽고 기존 작업을 보존한다.** 대량 치환·파일 전체 덮어쓰기 금지.

## 2. 현재 사실

### 착한거래에 이미 있음

- 보완 링크 생성
- 보완 이력·활성 보완항목 반환
- 발행 당시 `templateFields` 스냅샷을 프리패스 ③에서 읽을 안전한 응답

### 프리패스에 이미 있음

- `/api/chakhandeal/contracts/send`, `/status`, `/document`, `/template-fields`
- 서버 API Key 연동과 URL 검증
- ③ 계약서 3종·인수/반납 확정 및 링크 발행 로직
- ④ 8단계·본인확인·서류·완료 PDF
- 신규 계약서 생성 시 ② 패널 입력 흐름의 골격

- 계약서 3종·인수/반납 선택이 현재 ③에 있다. 신규계약에서는 ②로 옮겨 계약 저장 전에 확정해야 한다.
- ③·④가 저장 전 안내문만 보이는 것은 비정상이다. `/esign` 진입 즉시 착한거래 전용 embed 화면이 보여야 한다.

## 3. 착한거래 구현 오더 (`C:\dev\chakhandeal`)

### 3-1. 회원사 상태 응답 보강

`lib/server/contractInstances.js::toMemberStatus`에 아래만 추가한다.

- `templateFields`: 발행 때 굳은 필드 스냅샷. 객체가 아니면 `{}`.
- `supplements`: `{ items: string[], message: string, requestedAt: number|null }[]`
- `supplementActive`: 같은 공개 필드만 포함하거나 `null`

제외: `staff`, 신분증/셀카/서명/문서 저장 경로, 원본 파일 URL, 내부 감사정보.

`openSupplement`는 서명 완료 계약에서 허용 키(`identity_verified`, `documents`)를 **이력 저장 전에** 검증한다. 현재처럼 `requestSupplement`로 이력을 먼저 쓰고 오류를 내면 안 된다.

### 3-2. 보완 링크 회원사 API

신규:

`POST /api/v1/contract/{contractId}/supplement`

- `requireApiKey` 필수.
- 계약이 없거나 API Key의 `memberCompany`와 다르면 404.
- body: `{ items: string[], message?: string }`
- `openSupplement(contractId, { items, message, staff: 'member:<company>', origin })` 호출.
- 응답: `{ ok, supplementUrl, items, message, supplements }`
- rate limit 적용.
- 다른 회원사·무인증·허용되지 않은 키·서명 완료 뒤 제한을 테스트한다.

### 3-3. 서명 전 A4 초안 회원사 API

신규:

`GET /api/v1/contract/{contractId}/preview?save=0|1`

- `requireApiKey` 필수, 자기 회원사 계약만 허용.
- `signing`은 409, 이미 `signed`면 완료 PDF 사용 안내와 409.
- 착한거래의 현재 A4 템플릿과 발행 당시 `templateFields`를 사용한다. 새 계약서 HTML을 만들거나 프리패스 템플릿을 복사하지 않는다.
- `lib/server/contractDocument.js`의 렌더러를 재사용하되 초안 툴바 문구는 `서명 전 초안 · 서명 없음`으로 표시한다.
- `save=1`이면 값 주입 후 `window.print()`를 호출해 A4 PDF 저장창으로 이어지게 한다.
- `Content-Type: text/html; charset=utf-8`, `Cache-Control: private, no-store`, `X-Robots-Tag: noindex...`, `Referrer-Policy: no-referrer`.
- 서명 완료 문서의 무결성 검증 로직은 변경하지 않는다.

### 3-4. 템플릿 섹션 정보

착한거래 ②의 `연동 데이터` 접기/펼치기를 그대로 재현할 수 있게 기존
`GET /api/v1/templates/{templateId}/fields` 응답에 템플릿이 가진 섹션 순서와 field 목록을 추가한다.

- 기준은 기존 `lib/rentalContractSections.json` / `RENTAL_SECTIONS`.
- 프리패스에서 손으로 새 섹션 분류표를 만들지 않게 한다.
- 기존 `fields` 응답은 호환 유지한다.

### 3-5. 착한거래 테스트

기존 Vitest 패턴을 따라 추가한다.

- 무인증 401
- 다른 회원사 API Key 404
- 자기 계약 preview 200, 초안 문구, `no-store`
- 자기 계약 supplement 200, URL에 선택한 보완 키 반영
- 상태 재조회에서 supplements/supplementActive 확인
- 서명 완료 후 `identity_verified`·`documents` 외 키 차단
- 차단 요청은 supplements 이력을 남기지 않음
- 기존 issue/status/document 테스트 전부 유지

`npm test`와 `npm run build`를 실행한다.

## 4. 프리패스 구현 오더 (`C:\dev\freepasserp4`)

### 4-0. 신규계약 ② 패널 교정 — 먼저 처리

`app/esign/page.tsx`의 신규계약 입력부를 다음 계단식 선택 흐름으로 교체한다.

   - 표준 구독계약서(보험 별도)
4. 인수/반납 선택
5. 차량 입력방식 선택: `재고 차량 선택` / `신규 차량 직접 입력`
6. 선택한 방식의 차량·가격 입력
7. 임차인 정보 입력
8. 고정된 계약조건 요약 확인 후 저장

#### A. 재고 차량 선택

- 선택한 공급사·정책으로 계약 가능한 기존 재고 차량을 고른다.
- 선택 차량의 실제 가격기간을 고른다.
- 선택 결과로 대여료·보증금을 자동 표시한다.

#### B. 신규 차량 직접 입력

- 재고에 없는 차량의 차량명·차량번호 등 계약에 필요한 차량정보를 직접 입력한다.
- 기간·대여료·보증금을 직접 입력한다.
- 직접입력 계약임을 화면과 저장 데이터에서 구분한다. 이 동작으로 재고 상품을 새로 만들거나 기존 재고를 수정하지 않는다.

구현 기준:

- 입력방식 선택 없이 곧바로 노출되는 자유입력 `vehicleName`, `rentMonths`, `rentAmount`, `depositAmount` 필드는 제거한다.
- 재고 경로의 차량 선택값은 `productCode`이며, 이미 로드한 재고/상품 SSOT에서 실제 `EntityRecord`를 찾는다.
- 직접입력 경로는 `product_code`를 비워 두고 직접입력 차량임을 구분한다. 임의 상품코드나 가짜 재고를 만들지 않는다.
- 공급사를 바꾸면 정책·차량·가격기간 선택을 초기화한다. 정책을 바꾸면 차량·가격기간을 초기화한다. 차량을 바꾸면 가격기간을 초기화한다.
- 재고 경로의 차량 목록은 선택 공급사와 일치하고 현재 계약 가능한 재고만 보여준다. 기존 가용성 판정과 중복계약 잠금 로직을 재사용한다.
- 차량 표시는 기존 `contractVehicleLabel` 및 차량명 규칙을 재사용한다. 새 이름 조합기를 만들지 않는다.
- 재고 경로의 가격기간은 `lib/domain/product.ts::priceList(selectedProduct)`의 실제 항목만 칩으로 보여준다.
- 재고 경로에서는 선택한 기간과 정확히 일치하는 항목의 `rent`·`deposit`을 읽기 전용으로 표시한다. 가장 가까운 기간 fallback, 0원 대체, 수기 덮어쓰기는 금지한다.
- 재고 경로에서 가격기간이 없거나 선택값이 정확히 존재하지 않으면 저장 버튼을 비활성화하고 이유를 표시한다.
- 정책에 이미 고정된 연령·추가운전자·보험·기본조건은 다시 입력받지 않고 확인 요약으로 보여준다.
- 표준계약서/인수·반납은 `lib/domain/esign-templates.ts`, `lib/domain/esign-contract-kind.ts`의 기존 helper와 식별자를 재사용한다.
- 재고 경로 저장 시 `product_code`, 차량번호 및 제조사/모델/세부모델/트림/연식/연료 등 기존 상품 스냅샷, 공급사/정책, 선택한 가격기간·대여료·보증금, 표준계약서 ID, 인수/반납을 한 계약에 함께 고정한다.
- 직접입력 경로의 `createDirectEsignContract`는 유지하되, 명시적인 직접입력 모드에서만 호출한다. 직접 입력한 차량·기간·금액과 공급사/정책·표준계약서·인수/반납을 최초 write에 함께 고정한다.
- 저장 직전에 공통 계약조건을 검증한다. 재고 경로는 공급사-정책-차량 소속, 재고 가용성, 정확한 가격기간을 추가 검증하고, 직접입력 경로는 필수 차량정보·기간·금액의 유효성을 검증한다.
- `provider_agreement_done: 'yes'`는 위 계약조건이 전부 확정된 계약에만 기록한다.
- 두 입력방식의 form state와 검증을 섞지 않는다. 방식을 전환하면 반대쪽 차량·가격 입력값을 초기화해 숨은 값이 저장되지 않게 한다.

### 4-1. 서버 클라이언트

`lib/server/chakhandeal-esign.ts`에 기존 `callJson/getJson/safeUrl` 규칙을 재사용해 추가한다.

- 초안 HTML fetch: 크기 상한, `text/html` 확인, timeout, redirect 차단.
- 보완 링크 POST: `ApiKey`, idempotency key, `supplementUrl`의 https(로컬 dev만 http) 검증.
- 상태 응답의 `templateFields`, `supplements`, `supplementActive`는 타입·길이·배열을 정규화한다.
- 외부 오류 본문·API Key를 브라우저 응답과 로그에 노출하지 않는다.

### 4-2. 관리자 전용 프록시

신규:

- `GET /api/chakhandeal/contracts/{contractCode}/preview?save=0|1`
- `POST /api/chakhandeal/contracts/{contractCode}/supplement`

공통 조건:

- `getChakhandealConfig()` fail-closed.
- `verifyActiveBearer`, 실제 플랫폼 `admin`만 허용.
- v3+v4 계약 이중읽기 tolerance 유지.
- 계약코드 검증 후 저장된 `esign_id`만 사용. 브라우저가 외부 contractId를 직접 보내지 못하게 한다.
- preview는 착한거래 HTML을 그대로 프록시하되 private/no-store·nosniff 헤더 유지.
- supplement는 착한거래 응답을 받은 뒤 `/status`와 같은 투영기로 v4 계약 오버레이의 보완 메타를 갱신한다.

### 4-4. 프리패스 ③ = 착한거래 ②

`app/esign/page.tsx`의 ③ 제목은 계속 `착한거래 연동 및 발송`.

- 프리패스가 만든 `ChakhandealPane`을 최종 UI로 사용하지 않는다. 패널 body에는 착한거래 `link` embed 화면을 항상 마운트한다.
- 착한거래 `link` 화면 안에서 카드 구조(`연동값 검증`·`계약서 저장/미리보기`·`서명 링크`·`연동 데이터`)를 그대로 표시하고, 아직 실행할 수 없는 버튼만 비활성화한다.
- ②의 draft 입력값을 착한거래 `link` 화면의 `연동값 검증`과 `연동 데이터`에 실시간으로 전달한다.
- 저장 전에도 값 매핑·누락 검증·템플릿 섹션 확인은 가능해야 한다. 실제 계약 ID가 필요한 링크 발행과 서버 PDF만 비활성화한다.
- 비활성화 사유는 `연동값 확인 후 프리패스 데이터를 저장하세요`, `저장 후 착한거래 링크를 만들 수 있습니다`처럼 해당 카드 안에 표시한다.
- iframe 바깥 프리패스에는 착한거래 카드·버튼을 중복 구현하지 않는다. 로딩·연결실패·재시도 UI만 프리패스가 담당한다.

②에서 저장된 계약을 선택하면 아래 순서로 표시한다.

1. `연동값 검증`
   - 공급사·정책·차량·가격기간·대여료·보증금·임차인·표준계약서·인수/반납을 요약한다.
   - 착한거래 필드 매핑 누락·불일치를 섹션별로 표시한다.
   - 오류가 있으면 발행하지 않고 어떤 값이 문제인지 알려준다.
   - 계약서 종류나 인수/반납을 여기서 다시 고르게 하지 않는다. 기존 `TemplatePicker` 선택 UI는 ②로 이동하고 ③에서는 읽기 전용 요약만 표시한다.
2. `계약서 저장 (손님 미리보기)` 카드
   - `계약서 저장` → preview `save=1`
   - `미리보기` → preview `save=0`
   - 관리자 Bearer로 fetch한 HTML을 Blob URL 새 창으로 열어 API Key를 노출하지 않는다.
3. `서명 링크`
   - URL, 링크 복사, 열어보기, 자동 문자·카카오 발송 없음 안내.
4. `연동 데이터 (채움/전체)`
   - 착한거래 템플릿 섹션 순서 사용.
   - `쓸 것만 열기 / 모두 접기 / 모두 펼치기`.
   - ②의 확정 데이터를 기준으로 보여주며, 발행 후에는 **발행 스냅샷 읽기 전용**.

발행은 ②에 저장된 표준계약서 ID와 인수/반납 값만 사용한다. ③에서 다른 조합으로 바꿔 발행할 수 없어야 한다.

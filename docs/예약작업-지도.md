## 규칙 — Claude · Codex · Cursor · 사람 공통

1. **프리패스 시트·원장을 쓰는 예약은 GitHub Actions(이 저장소 main) 한 곳에만 둔다.**
   PC 작업 스케줄러 · Codex 자동화 · Claude 예약 작업 · Vercel cron 에 «새로» 만들지 않는다(읽기 전용 점검도 여기 먼저 적는다).
2. **운영 판매시트 F01 · 하허호 F86 에 쓰는 것은 아래 표에서 「운영 쓰기 허용」인 워크플로뿐이다.**
   발행기가 스스로 막는다 — `lib/server/production-sheet-write-gate.ts`(`GITHUB_WORKFLOW` 허용 목록).
   로컬·다른 AI 는 미리보기 사본만 쓴다(F86 `--시트=<사본 id>` · F01 `SAMPLE_SHEET_ID`).
   긴급 수동 발행은 **사장님 허락을 받고** `FREEPASS_MANUAL_PUBLISH_APPROVED="YYYY-MM-DD 사유"` 로 연다.
3. **발행 엔진은 하나** — 통합 워크플로가 `ref:` 로 고정한 커밋. 다른 가지 코드로 운영에 쓰지 않는다.
4. **예약을 더하거나·끄거나·cron 을 바꾸면 이 표를 «같은 커밋»에서 고친다.**
   `npm run check:schedules` 가 표와 `.github/workflows/*.yml` cron · `vercel.json` crons 를 맞대 어긋나면 exit 1(CI).
5. **GitHub 에서 켜고 끄는 것(disable/enable)은 파일에 안 남는다** — 바꾼 사람이 아래 「상태」 칸과 날짜를 고친다.

**통합 워크플로 엔진** = `erp5-ssot-refresh.yml` 의 `ref:` 고정 커밋 — 현재 운영 후보는 `3c98e1b616392ee6d47e07c7d08dbb30320f67ff`다. 손오공 API와 오플 원천을 새 정본으로 보며, 과거 보완 시트는 차이를 기록할 뿐 발행을 막지 않는다. 이 revision은 원문에 `슈팅브레이크`가 없는 차량이 과거 슈팅브레이크 확정값을 재사용하지 못하게 하고, 손오공 중고렌트의 ERP `RENT_*` 보증금 원문 숫자를 반올림 없이 발행하며, 구독·픽업의 보증금 규칙 문구와 분리한다. 또한 F86 레트로 글꼴·배치를 유지하면서 상품구분 7값의 정본 색(신차렌트 `FF00FF`)과 배차상태/장기요금 파랑을 보존하며, 폐기된 종합 탭 생성 경로를 제거하고 기본 4탭 뒤에는 회사명 탭만 허용한다. 운영 전환 여부는 main의 실제 ref로 확인한다. 엔진을 바꾸면 미리보기/감사 후 pin과 `VALIDATED_ENGINES`를 같은 변경에서 전진시킨다.

2026-09-22 후보는 freepass-data `4005c5f995451c1b4332c8c0aaf82633a58b14f3`의 동일 JSON/검사기를 사용한다. `MM.DD HH:mm 상품리스트 N대`와 나머지 전체 탭명·대수, 색, 차명(원문) 260px, 옵션(원문) 360px, 세부트림 100px, 픽업구독 보증금 설명 열 180px, F86 단기 숨김을 양쪽 발행기의 마지막 서식에 적용하고 실제 시트 readback을 검사한다. F01/F86 쓰기 전에는 오플 `재고`, 손오공 `구독재고`·`픽업재고`를 보완참조로 새로 읽어 차량번호 집합과 대수를 비교한다. 허용 차이는 참조 대수의 10% 또는 5대 중 큰 값이며, 빈 참조·중복키·허용범위 초과는 발행 HOLD다. 보완 시트는 Firestore를 자동 복구하거나 삭제하는 권한이 없다. 원천 수집/상품 분류/원자 내용/예약 시각/기존 동시실행 잠금은 유지한다.

읽기 전용 검증 run `35576634024`에서 F01 4탭/F86 20탭 차이 0 PASS(2026-09-21 17:12 KST). 이는 표시 규격의 온라인 읽기 검증이며 전체 원천 재발행 성공을 뜻하지 않는다. 검증 전용 `codex/f01-f86-online-readonly-20260921` 가지의 workflow 파일은 단발 GET 감사용으로, 운영 main에 병합하지 않는다. 스케줄과 신규 writer는 없다. 필수 검토 및 운영 전환 승인 전에는 후보를 운영 완료로 보고하지 않는다.

### 2026-09-19 안전 자동화 흐름

```text
09:05~18:05  settlement-intake-sync
              계약접수 시트 → 정산원장 접수
                    ↓
```

`contract-status`·`sales-erp-hourly`·`mirror-sync`는 자동 writer가 아니다. 운영 쓰기 책임은 위 두 자동화와 canonical ERP5 engine에만 둔다.

**하허호 F86 지키기**(사장님 2026-09-16 「하허호 시트는 제일 중요하게」) — 통합 워크플로 한 회차에서 스냅샷만 제대로 떴으면
오플·손오공 보완참조까지 통과한 같은 검증 스냅샷이면 F01 이 실패해도 F86 은 **백업**(`backup-f86` · 최근 48개) → **발행** → **F86 감사·신선도 120분**(`audit-f86-vs-atom`, 첫 관문) 까지 간다. 수동 준비(`apply=false`)는 원천→ERP5→검증 스냅샷만 만들고 시트에 쓰지 않는다. 수동 적용(`apply=true`)은 원천과 Firestore를 다시 계산하지 않는다. `ready_run_id`를 지정하면 그 회차를, 비우면 최근 성공 회차 중 만료되지 않은 스냅샷 artifact가 정확히 있는 최신 회차를 자동 선택한다. 적용 가능한 스냅샷이 없으면 HOLD한다.
되돌리기 = `restore-f86-from-backup --from=<백업 id> --apply`(사장님 허락 플래그). 장치가 빠지면 `check:schedules` 가 막는다.

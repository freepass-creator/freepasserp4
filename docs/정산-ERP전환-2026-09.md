> 「현재 이걸 어떻게 구현하고 **영업채널·공급사에도 어떻게 보여줄까**를 고민해야 해」

| | 정함 |
|---|---|
| 보여줄 범위 | **시트와 똑같이** — 줄별 금액 + 확인·정정요청·정정금액·메모 |
| 시트 끊는 때 | **2026-09 정산부터 ERP 만.** 8월은 이미 시트로 나갔으니 그대로 둔다 |

---

## 1. 왜 옮기나

공급사 정산서는 «공급사 재고 시트(F5x)» 안의 달 탭에 살았다. 그래서 **재고 시트가 없는 곳은
정산서도 없다** — 2026-09-10 에 빌린카·엘씨렌트(LC)가 딱 그 꼴로 걸렸다.
시트를 새로 파는 대신 ERP 를 정본으로 삼으면 거래처가 늘어도 이 일이 안 생긴다.

## 2. 옮길 게 없다 — 원자에 이미 있다

```
settlement_rows (원자 · 정본)
  ├ 돈        claimWritten(청구) · payWritten(지급)
  └ 상대가 적는 넉 칸 ×2   ← 시트의 그 칸들이 원자에 «이미» 자리를 갖고 있다
      공급사  supplierOk · supplierFix · supplierFixAmt · supplierMemo
      채널    channelOk  · channelFix  · channelFixAmt  · channelMemo
```

## 3. 무엇이 없었나 — 「돈이 실리는 문」

기존 `/contract`(정산확인)은 **돈을 한 칸도 안 싣는다**(`PublicRow`).
사장님 2026-08-26 「대여료 기간 보증금같은것들만 확인하고 **정산금액은 거기에서는 안 보이게**」 —
그때는 정산서를 시트로 보냈기 때문이다. 이제 그 길이 없어지므로 문을 하나 낸다.

★**`/contract` 에 얹지 않는다.** 계약진행은 「내 계약이 어떻게 되나」(건별)이고
정산서는 「이번 달 얼마」(달별 돈)라 묻는 것이 다르다. 그리고 **돈 없는 꼴과 돈 있는 꼴을
한 라우트에 섞으면 언젠가 샌다.**

## 4. 누가 무엇을 보나

```
                  settlement_rows (원자)
                          │
         ┌────────────────┴────────────────┐
   공급사가 보는 꼴                    채널이 보는 꼴
   ───────────────                  ───────────────
   청구액          ○                 청구액          ✕
   지급액          ✕ ★★              지급액          ○
   영업채널·영업담당자 ✕ ★★            공급사          ○
   확인·정정·정정금액·메모 ○            확인·정정·정정금액·메모 ○
```

★★ 는 **절대 규칙**이다 — 사장님 「절대 영업자 지급 수수료가 얼만지 공급사시트에는 반영되면 안 돼」.
**화면에서 가리는 게 아니라 서버가 «안 싣는다».** 타입에 칸이 없으면 개발자도구로도 못 본다
(`publicRowOf` 가 쓰는 그 수법 그대로).

★**덮지 않는다** — 상대가 적은 정정은 `supplierFix*`/`channelFix*` 에 담기고 **우리 청구액은 안 바뀐다.**
관리자 화면에 「정정요청 N건」으로 떠서 사람이 판단한다(정산시트 매뉴얼의 그 규칙 그대로).

## 5. «누구인가»는 이름이 아니라 코드로 맞춘다

토큰(`ActiveBearer`)에 `companyCode`·`agentChannelCode` 가 **코드로** 들어 있다.

⚠ 그런데 2026-09-10 실측에서 원자에는 코드가 **430줄 중 16줄**만 차 있었다.
코드로 맞추면 대부분 0줄이 된다. ⇒ `scripts/backfill-party-codes.mts` 로 채웠다.

```
채운 뒤   공급사코드 408/430 · 채널코드 385/430
못 푼 곳  공급사 5(오토셀렉션·JPK·AMR·금탑·빌림) · 채널 13(카핑·위너스올오토·원드림카…)
```

★★**못 푸는 상호는 «비워 둔다».** 짐작으로 채우면 **그 줄이 남에게 보인다** — 그건 못 되돌린다.
  풀려면 `lib/domain/partner-ci.ts` 에 그 거래처를 등록한다(코드 정본은 거기 하나다).
★**이름으로 맞추지 않는다** — 사장님 2026-08-26 「각각 영업자한테 코드를 부여해야 할 거 같어,
  동명이인 거르려면」. 이름은 「웰릭스/웰릭스모빌리티」처럼 줄여 적히고 겹치지만 코드는 안 겹친다.

## 안 하는 것

- **8월을 ERP 로 다시 내지 않는다** — 이미 시트로 나갔다. 두 곳에서 같은 달을 내면 어느 것이 맞는지 갈린다.
- **수금·지급 실행 표시** — 통장을 봐야 아는 것이라 화면에서 켜면 거짓말이 된다.
- **상대가 고친 값을 자동 반영** — 받아 놓고 사람이 정한다.

## 7. SSOT 사슬 — 어디가 정본이고, 무엇이 규칙이고, 무엇이 사고인가

> 사장님 2026-09-10 「**ssot 명확하게 해서 정산할 수 있어야 해**」

```
   ┌─ 2026-07 까지 ────────────────────────────────────────┐
   │  시트가 기록이다. 원자에 없는 것이 «정한 것»이다.        │
   └───────────────────────────────────────────────────────┘
   ┌─ 2026-08 부터 ─ ATOM_FROM_MONTH ──────────────────────┐
   │  정산원장 F04  ⇄  원자 settlement_rows  →  계산서·화면 │
   └───────────────────────────────────────────────────────┘
```

⚠ **원장과 원자는 여태 «양방향»이었다.**
`atomize-settlement-month` 가 원장→원자로 붓고, `run-settlement-sheet` 가 원자→원장으로 다시 세운다.
한쪽만 돌면 다른 쪽이 뒤처진다 — 2026-09-10 에 원장에 청구월이 박혔는데 원자가 빈 줄이 셋 있었다.

★**경계를 코드에 못 박았다** — `ATOM_FROM_MONTH` · `isAtomMonth` (`lib/domain/settlement-atom.ts`).
  여태 이 경계가 «문서에만» 있어서 검사마다 각자 판단했고, 대조기가 2026-01~07 을 통째로
  «사고»로 불렀다(37건). 지난 달이 원자에 없는 것은 사고가 아니다.
  ⚠ **거짓 경보가 한 번 뜨면 그 검사는 그날로 안 믿게 된다.**

### 검사 둘이 «각자» 맡는다

| 검사 | 무엇을 | 언제 |
|---|---|---|
| `npm run check:ssot` | 원장 ↔ 원자가 **줄 수·지급**에서 같은가 | 원자 구간 **전부** |
| `npm run check:chain` | 원장 → 원자 → 계산서가 **청구 축**에서 다리를 넘어 이어지는가 | 그 달 |

⚠ **지급 축에는 다리가 없다.** 갈리면 규칙이 아니라 사고다(영업자에게 줄 돈이 틀린 것).
청구 축은 「그 달 공급사에 청구하지 않는 줄」 같은 다리가 있어 `check:ssot` 에서는 △ 로만 찍는다.

### 2026-09-10 실측

```
2026-01~07   시트가 기록 (재지 않는다)
2026-08      △ 청구만 6,367,450 차이 = 미청구 다리 · 지급은 원 단위로 같다
2026-09      ✕ 원장에만 3줄 — 전부 «청구 0»(금액이 아직 안 적힌 접수)
2026-10      ✕ 원장에만 1줄 — 청구 0
```

**진짜 사고는 없다.** 갈린 넷은 모두 원장에 청구월만 박히고 금액이 아직 안 적힌 줄이다.

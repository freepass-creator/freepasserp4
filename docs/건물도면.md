# 건물도면 — 이 ERP 는 몇 층이고, 층마다 문·창문이 어떤가

> 사장님 2026-08-30
> 「십 층짜리 건물을 지었으면 **문은 다 동일해야 되고 창문 다 동일해야** 되는 거지.
>  근데 **일 층은 로비니까 로비 나름 뭐가 있는 거고 옥상은 옥상 나름** 뭐가 있는 거잖아.
>  이게 구성이 돼야 되는데 지금 그렇게 되질 않아서 내가 너무 힘든 거야.」

이 문서가 **그 구성표**입니다. 층이 몇이고, 어느 층이 어느 규격을 따르고,
**로비·옥상처럼 달라도 되는 곳은 왜 다른지**를 한 장에 적습니다.

확인 명령 — `npm run check:building`

```
docs/건물도면.md          도면 (정본 · 사람이 읽는다 · 예외 근거가 여기 있다)
scripts/check-building.mts  줄자 (도면과 실물이 같은지만 잰다)
```

**★고쳐서 좋아졌으면 도면도 같이 낮춥니다** — `npm run check:building -- --tighten`.
(2026-08-29 전자계약 화면은 raw 버튼을 14개→0개로 없앴는데 기준표를 안 고쳐서 «좋아졌는데 빨간불»이 떴습니다.
좋아진 것까지 빨갛게 뜨면 아무도 그 불을 안 믿게 됩니다. 그래서 이 줄자는 **늘 때만** 빨간불입니다.)

## 1. 동(棟) — 층마다 «어느 규격을 따르는가»

| 동 | 무엇 | 규격 |
|---|---|---|
| **업무** | 우리 식구가 하루 종일 쓰는 ERP 콕핏 | `CLAUDE.md` 원자 사전. 껍데기는 `Page`/`WorkPage`. raw 컨트롤·하드코딩 높이 **0** |
| **로비** | 앱에 들어오기 전·상품을 고르는 첫 화면 | 앱 셸 밖이라 «폼 섬»을 허용. 대신 예외를 이 도면에 적는다 |
| **손님** | 우리 식구가 아닌 사람이 보는 곳 | 착한거래 규격(`docs/ESIGN-UIUX-SPEC.md`). **ERP 얼굴을 쓰지 않는 게 규격** |
| **별관** | 소노공·웰릭스 등 남의 브랜드를 담는 액자 | `EmbeddedApp` 하나만 쓴다 |
| **신관** | `erp5` — 아직 공사 중인 새 동 | 완공 전까지 규격 유예. **기한을 적는다** |
| **기계실** | 손님이 못 보는 개발·진단·설정 | 원자만 쓰면 된다 |

**★같은 동이면 문·창문이 같아야 합니다.** 다르면 그건 임기응변이고, 줄자가 잡습니다.

# 상품리스트 연동 — 서사와 계약

> **누가 읽나** — 이 파이프라인을 처음 만지는 AI(코덱스·커서·클로드)와 사람.
> **왜 서사부터인가** — 여기 규칙은 대부분 «사고가 한 번 난 뒤에» 생겼다. 이유를 모르면 «불필요해 보이는 것»을 지우고 같은 사고를 다시 낸다.
> **지금 코드가 진짜로 하는 일**은 `npx tsx scripts/print-sync-contract.mts` 가 찍는다. 이 문서와 다르면 **코드가 정답**이고, 문서를 고쳐라.
> 마지막 갱신 2026-08-23. **§3‴ 「사장님이 그린 구조」부터 읽어라** — 나머지는 그 구조가 왜 이렇게 됐는지의 내력이다.

## 0. 한 줄 요약

```
렌터카사 원본 ─▶ 공급사 시트(정제/제공) ─▶ 중앙 판매시트 3탭 ─▶ ERP(v4/products) ─▶ 화면(웹·모바일·손님 링크)
                    ▲ 사람이 고치는 곳                   ▲ 영업자가 보는 표      ▲ 사본. 여기서 고치면 다음 발행에 사라진다
```

**정본은 언제나 왼쪽이다.** 오른쪽에서 고친 값은 다음 발행이 덮는다.

## 1. 어쩌다 이 구조가 됐나 — 히스토리

### ① 처음엔 «상품마스터»를 거쳤다 (~2026-08)
공급사 시트 → **상품마스터 시트** → ERP. 상품마스터가 검수·확정을 하는 자리였다.
문제: 단계가 하나 더 있으니 «시트는 맞는데 ERP 는 틀린» 상태가 계속 생겼고, 어디서 갈렸는지 추적이 오래 걸렸다.

### ② 「영업자가 보는 표 = ERP」로 직행 (2026-08-20)
사장님 「영업자가 보는 거랑 우리 ERP 랑 바로 연동하자 · 일단 상품마스터 안 거치고」.
**ERP 는 중앙 판매시트 3탭만 읽는다.** 상품마스터·차종마스터 fallback이나 `--with-product-master` 선택지는 없다.
→ 그래서 **판매시트에 열이 없으면 그 값은 ERP 에 영영 안 들어간다.** 이 문서에서 제일 중요한 한 줄이다.

### ③ 차종마스터로 이름을 «맞히던» 시절 (~2026-08-22)
유입할 때마다 차종마스터에 스냅(`snapToMaster`)해서 제조사·모델·세부모델·트림·파워트레인을 마스터 값으로 갈아끼웠다.
문제가 셋이었다:
- 마스터가 트림을 못 찾으면 **트림을 빈칸으로 만들었다** → 시트엔 있는데 ERP 만 비는 차가 쌓였다(실측 세부트림 19%).
- 트림에 엔진 이야기가 섞였다 — 「2.5 T 가솔린」·「프레스티지 디젤 2.2 9인승」.
- 「한 번 마스터로 확정된 값은 시트가 못 덮는다」는 방어가 있어 **219대가 영구 빈칸**으로 굳었다.

### ④ 정제칸이 정본이 되다 (2026-08-22 · 현재)
사장님 「**ERP 에는 정제를 쓰는 게 맞고 정제만 잘해 두면 되니까 · 정제시트만 바라보는 거야 · 정제칸은 내가 확실하게 챙길게**」.
- 차종마스터 **참조 중단**(재고관리 선택기·매칭 근거 UI 제거).
- 유입 스냅이 정제값을 덮지 못하게 막고, 「마스터 확정값 우선」 가드를 제거.
- **파워트레인 폐지** — ERP 잔재 3,737대 삭제, 스냅이 다시 채우던 코드도 끊음.
- 판매시트 열을 «축 그대로»로 재편: 차명 한 칸 → **세부모델 · 세부트림** 두 칸.

결과(실측): ERP 세부모델 33%→100% · 세부트림 19%→82% · 트림에 엔진 섞인 차 0대.

## 2. 시트가 세 종류다 — 헷갈리지 마라

| 종류 | 무엇 | 원본을 매번 따라가나 | 고치는 곳 |
|---|---|---|---|
| **정제시트** (4곳: 아이카·오토플러스·이안카·아이언) | 우리가 만든 **원본 미러**. 왼쪽 차명·옵션은 렌터카사 원본(홈페이지·그쪽 시트)에서 매번 다시 가져온다 | **예** — 정제시트에서 왼쪽을 고쳐도 다음 미러가 되돌린다 | 렌터카사 원본 |
| **제공시트** (17곳) | 공급사가 직접 적는 시트. 우리가 양식만 준다 | 아니오 | 공급사(또는 우리가 대신) |
| **중앙 판매시트** | 위 21곳을 한 표로 모은 **출력**. 영업자가 보는 화면이자 ERP 의 입력 | — | **고치지 마라** — 다음 발행에 사라진다 |

두 종류 모두 **오른쪽에 「정제칸」**(구분선 `│` 뒤)이 있다. 거기가 우리가 채우는 자리다.

## 3. 정제칸 — 지금의 정본

차례는 **이름 축 → 제원 축 → 분류 축**이다(사장님 2026-08-22 「차종크기 앞에 그냥 모을 수 있는 정보를 모으는 거야」).

```
정책코드 │ 모델행키 · 세부모델행키 · 세부트림행키 · 원산지
        │ 제조사(정제) · 모델 · 세부모델 · 세부트림          ← 이름 축
        │ 배기량(정제) · 연료(정제) · 구동방식 · 인승          ← 제원 축
        │ 차종크기 · 차종구분 · 차종코드 · 선택옵션 · 외장색상 · 내장색상 · 차종분류 · 차종분류코드 · 차명(정제)
```

**차명 축은 넷이다 — 제조사 · 모델 · 세부모델 · 세부트림.**
화면에서 「차명」이라 부르는 것은 **세부모델 + 세부트림**이고, 제조사는 제목 줄이 든다.
**파워트레인 칸은 없다.** 엔진 이야기는 「연료」·「배기량」이 든다 — 이름에 섞지 마라.

정본 정의: `lib/domain/supplier-template-sheet.ts` `AI_TAIL_COLUMNS`

### 3″. 이름을 바꾸는 곳은 「AI 정제」 사전 한 자리다

정제칸을 채우는 `fill-supplier-ai-columns` 는 이름을 **지어내지 않는다.** 차종마스터·정본이 준 글자를
판매시트 숨은 탭 **「AI 정제」**(`@제조사`·`@모델`·`@세부모델`·`@세부트림`·`@외장`·`@내장`)에 대고 바꿔 적을 뿐이다.
발행기도 같은 사전을 읽는다 — **여기 한 줄이면 정제칸도 판매시트도 같이 따라온다.**

> ⚠ **시트 값을 손으로 고치지 마라.** 다음 `fill` 이 마스터 값으로 도로 덮는다. 사전을 고쳐야 남는다.

**프로젝트 코드는 이름이 아니다**(사장님 2026-08-23 「109호5391 이상하다 · 아직도 정제 안 된 게 있는 거 같음」).
차종마스터 세부모델명에는 개발 코드가 붙어 있어 — 「디 올 뉴 싼타페 **MX5**」·「그랜저 **GN7**」·「G80 **RG3**」 —
그대로 두면 손님 화면 차명이 「디 올 뉴 싼타페 MX5 익스클루시브」가 된다(실측 648대 중 487대가 그랬다).

```bash
npx tsx scripts/add-submodel-code-strip-rules.mts           # 무엇이 들어갈지 보기만
npx tsx scripts/add-submodel-code-strip-rules.mts --apply   # 「AI 정제」에 규칙을 붙인다
```

- 규칙 근거는 **차종마스터 + 지금 시트에 적혀 있는 값** 둘 다다. 마스터만 보면 시트에만 남은 옛 이름이 빠진다.
- 코드 판정은 `lib/domain/submodel-code.ts` `stripModelCode` **하나뿐**이다. 스크립트마다 따로 적지 마라.
- 모델 이름에 들어 있는 토큰은 안 뗀다(`K8`·`G80`·`EV6`·`XM3`). 뜻이 있는 낱말도 남긴다(`EV`·`FL`·`GT`).
- 코드를 떼면 세대가 겹치는 이름(「그랜저 GN7」·「그랜저 IG」)도 **뗀다** — 이름은 손님이 읽는 딱지이지 열쇠가 아니고
  (열쇠는 차종코드), 세대는 화면에서 **연식**이 가른다. 남기고 싶으면 「AI 정제」에서 그 줄만 지우면 된다.

판매시트를 안 거치는 차(`EXT_*` 옛 웹 등록분 · 출고불가)는 사전이 못 닿아 옛 이름이 굳는다. 한 번만 털면 된다:

```bash
npx tsx scripts/normalize-erp-submodel-codes.mts --apply    # ERP sub_model 에 굳은 코드 제거
```

## 3‴. 사장님이 그린 구조 (2026-08-23) — 여기부터 읽어라

> 「공급사가 편하게 입력 → 그걸 **차종마스터와 연동해서 정제칸에 반영**하고 →
>  ERP 는 정제칸과 공급사가 올린 것을 **보여주기로 그대로 활용**한다 →
>  **정제칸은 차종마스터를 그대로 가져온 것**이고 → **ERP 직접입력도 차종마스터 기준으로 설계**한다」
>
> 「**오류를 없게 하는 것이 관건**」 · 「차종마스터는 계속 늘려 갈 거야 — **네가 판단하지 말고 구글시트를 반영하는 것일 뿐**」

```
   ┌───────────────┐        ┌──────────────────────────┐
   │ 공급사 원문     │        │ 차종마스터 (구글시트)       │  ← 사장님이 계속 늘린다. 코드는 판단하지 않는다
   │ «편하게» 적는다 │        │  = 이름의 유일한 기준       │
   └───────┬───────┘        └────┬───────────────┬──────┘
           │   연동(fill)        │               │
           └──────────┬──────────┘               │
                      ▼                          ▼
              공급사 시트 «정제칸»          차종사전(vehicle-catalog.json)
              = 마스터 글자 그대로                 │
                      │                          ▼
                      ▼                   ERP 직접입력 드롭다운
                중앙 판매시트 3탭          (재고관리 상품등록)
                      │
                      ▼
                    ERP  ── 정제칸 + 공급사 원문을 «보여주기»로 그대로
                      │
                      ▼
                    화면
```

**왜 이 모양인가.** 공급사에게 우리 양식을 강요하면 시트가 안 채워진다. 그러니 공급사는 자기 말로 적게 두고
**맞추는 일은 우리가 차종마스터로** 한다. 그리고 **기준이 하나**이므로 정제칸과 ERP 입력이 저절로 같아진다 —
갈릴 대상이 없으니 오류가 안 난다. 그게 「오류를 없게 하는 것이 관건」의 답이다.

### 걷어낸 것은 «마스터»가 아니라 «맞히기»다

혼동하기 쉬운 대목이라 못 박는다. 2026-08-22~23 에 끊은 것은 **마스터로 이름을 추측하던 짓**(`snapToMaster`)이지
마스터 자체가 아니다.

| | 끊은 것 (추측기) | 남긴 것 (기준) |
|---|---|---|
| 언제 | 유입할 때마다 자동으로 | 사람이 고를 때 |
| 무엇 | 이름을 «맞혀서» 갈아끼움 | 목록을 보여줌 |
| 사고 | 트림 못 찾으면 빈칸(19%) · 확정값을 시트가 못 덮음(219대) | — |
| 지금 | `sheet-import`·`ironrentcar-source` 에서 제거 | 정제칸·차종사전의 뿌리 |

### 차종사전 — 마스터를 그대로 반영한다

`public/data/vehicle-catalog.json` (`scripts/build-vehicle-catalog.mts`).

| 출처 | 무엇 | 대수 |
|---|---|---|
| `마스터` | 차종마스터 시트에 있는 줄 — **뿌리** | 정제칸 실적에서 셈 |
| `정제칸` | 마스터엔 아직 없는데 굴러가는 조합 — **마스터에 채울 목록** | 〃 |
| `손추가` | 판매시트 숨은 탭 「차종사전」에 사람이 적은 줄 | 0 |

```bash
npx tsx scripts/build-vehicle-catalog.mts --apply --write-tab   # 사전 갱신 + 시트에 비추기
```

- 마스터 이름은 **「AI 정제」 치환 사전을 태워** 담는다(§3″). 안 태우면 드롭다운엔 「디 올 뉴 싼타페 MX5」,
  정제칸엔 「디 올 뉴 싼타페」가 들어가 **둘이 갈린다.**
- ⚠ `--write-tab` 은 파생분까지 시트에 비춘다. 다시 읽을 때 **「출처」가 「손추가」인 줄만** 읽는다 —
  안 그러면 파생분이 손추가로 둔갑해 마스터에서 지운 차종이 되살아난다(실측 212줄이 그랬다).
- ⚠ **닫힌 목록이 아니다.** 재고관리에서 목록에 없는 이름도 그대로 칠 수 있다 — 새 차는 언제나 목록 밖에서 온다.

### 공급사 원문은 「2중 보관」 · 기타항목에 참고용

정제칸이 정본이 된 뒤 **공급사가 적은 글자가 버려지는 구멍이 둘** 있었다:
- 「옵션」은 정제칸 「선택옵션」을 먼저 집어 원문이 통째로 사라졌다.
- 「차명」은 `HEADER_ALIASES.차명 = 'model'` 과 겹쳐 왼쪽의 「모델」이 먼저 자리를 잡는 바람에 **ERP 로 아예 못 갔다.**

판매시트에 **「차명(원문)」·「옵션(원문)」** 두 칸을 세우고 ERP `supplier_vehicle_name`·`supplier_options` 로 나른다.
상세 **「기타」에 참고용**으로 서고(사장님 「공급사 원문은 기타항목에 참고용으로 넣는 거지」),
재고관리에서는 **보여주기만 하고 못 고친다**(`Field.readOnly`). 고칠 곳은 공급사 시트다.

### 재고관리 상품등록

- 차명 축 넷은 **차종사전 드롭다운**(`type: 'catalog'`) — 앞 축을 고르면 뒤 축이 좁아진다.
- **필수는 차량번호 · 모델명 둘뿐**(사장님 「필수입력은 차량번호야 모델명인 거지」).
  필수를 늘리면 등록이 막히고, 막히면 사람이 아무 값이나 적는다.
- 차대번호(VIN)는 **ERP 전용 부가입력** — 판매시트엔 안 올라간다(관리자 칸에만).
- 폐지: 파워트레인(variant) · 추가표기(trim_extra) 편집 칸.

### 재고관리 내보내기 시트도 같은 축

`lib/domain/inventory-sheet-export.ts` — 「파워」 폐지, 「트림」→「세부트림」, 공급사 원문 두 칸 추가(2026-08-23).
`check-sales-axes` 가 **판매시트와 재고관리 시트 둘 다** 폐지 축을 보므로, 한쪽만 치우고 넘어갈 수 없다.

### 구동 표기는 별칭으로 흡수한다

규격은 `2WD` · `AWD` · `4WD`(`entities.DRIVE_TYPES`).
`FWD`·`RWD`·`전륜(FF)`→`2WD`, `xDrive`·`콰트로`·`4MATIC`·`4모션`→`AWD` 로 **비우지 않고 옮긴다**(`canonDriveType`).
유입에서도 같은 함수를 태워 재유입을 막는다. ⚠ 규격에도 별칭에도 없는 말은 **그대로 둔다**.

## 3′. 어떤 값이 어디서 입력되어 어떻게 ERP 까지 가나

한 축을 따라가 보면 이렇다(예: **세부트림**):

```
① 렌터카사 원본(홈페이지·그쪽 시트)           ─ 정제시트 4곳은 왼쪽 「차명(세부모델+트림)」을 여기서 매번 다시 가져온다
      │                                        제공시트 17곳은 공급사가 직접 적는다
      ▼
② 공급사 시트 «정제칸»  「세부트림」            ─ 우리가 채운다(fill-supplier-ai-columns · 사람이 손으로도)
      │                                        ★여기가 정본. 틀리면 여기를 고친다
      ▼
③ 중앙 판매시트 「세부트림」 열                 ─ publish-origin-tab 이 ②를 그대로 옮긴다
      │                                        열이 없으면 여기서 값이 죽는다 → ERP 로 못 간다
      ▼
④ ERP  products.trim_name                    ─ run-sheet-daily-sync-local 이 ③을 읽어 넣는다
      │                                        빈 값은 기존 값을 안 덮는다(soft-merge)
      ▼
⑤ 화면 — 목록 「차명」 · 상세 · 손님 공유 링크 미리보기
```

**축마다 이 다섯 지점이 같은지 보는 명령**(값이 새면 어디서 새는지 바로 보인다):

```bash
npm run audit:axes      # 정제칸 ▶ 판매시트 ▶ ERP 채움률을 축마다 한 줄로
```

읽는 법 — 정제칸이 낮으면 **정제시트를 채워라**. 정제칸은 찼는데 판매시트가 비면 **발행기**(열이 있나·별칭이 맞나).
판매시트는 찼는데 ERP 가 비면 **유입**(`sheet-import` 스냅이 덮나 · `sheet-merge` 가 막나).

### 축 선언은 한 곳에서 — `lib/domain/sales-axis-registry.ts`

열 하나를 세우려면 예전엔 여섯 곳을 고쳐야 했고, 실제로 2026-08-22 하루에만 두 번 빠뜨렸다
(세부모델·세부트림이 **조용히 가운데 정렬**로 나갔고, 차종코드는 ERP 별칭이 없어 **6,605대 중 0건**이었다).
지금은 축을 **한 줄로 선언**하고, `npm run check:axes` 가 여섯 곳이 그 선언과 같은지 대조해서 **다르면 실패**시킨다.

```ts
{ column: '인승', erpField: 'seats', align: 'right', fromRefined: true,
  minFillSheet: 60, minFillErp: 60, why: '원장 값을 옮기는 칸(정제해서 만드는 값이 아니다)' }
```

`minFill*` 은 **«이 밑으로 떨어지면 사고»의 선**이다(목표치가 아니다). `npm run audit:axes` 가 이 문턱으로 판정한다.

## 5. ERP 담당이 돌리는 차례 (`scripts/hourly-sync.mts` 기본은 읽기 감사)

```
① 판매시트 3탭 사전감사       audit:sales-sync-preflight
② ERP 반영 diff 미리보기      audit:sales-erp-plan
③ 사용자 직전 승인
④ ERP 일일 동기               run-sheet-daily-sync-local --apply
⑤ 시트↔ERP 재대조             audit:sales-erp-parity
```

공급사 원본·정제/제공시트·판매시트 발행은 별도 담당 정본이다. ERP 작업이 그 시트를 임의 수정하거나
재발행하지 않는다. 판매시트 3탭이 완료됐다는 전제에서 아래 명령만 쓴다.

```bash
npm run audit:sales-sync-preflight
npm run audit:sales-erp-plan
npx tsx --require ./scripts/lib/server-only-shim.cjs scripts/run-sheet-daily-sync-local.mts   # dry-run
npx tsx --require ./scripts/lib/server-only-shim.cjs scripts/run-sheet-daily-sync-local.mts --apply
npm run audit:sales-erp-parity
```

> `run-sheet-daily-sync-local` 은 `server-only` import 때문에 **shim 없이는 못 돈다**. 위 `--require` 를 빼지 마라.
> 기본은 dry-run 이다. `--apply` 를 줘야 쓴다. 실제 반영은 영향 상품의 RTDB 공개 노드를
> `v4/sheet_sync_backups/{runId}`에 먼저 보관하고, 백업 실패 시 제품 쓰기를 시작하지 않는다.
> 되돌릴 때도 먼저 `npm run rollback:sales-erp -- --run=<runId>`로 미리 보고, 별도 직전 승인 뒤에만
> `npm run rollback:sales-erp -- --run=<runId> --apply`를 실행한다. 후속 수기/동기화 변경이 닿은 키가 하나라도
> 있으면 전체 롤백을 중단한다.

## 6. 열을 바꾸려면 — 순서를 지켜라

1. `lib/domain/sales-sheet-mapping.ts` `SALES_MAPPING` 에 줄을 넣는다(**차례가 곧 열 차례**).
   - 뺄 때는 줄만 지우지 말고 `SALES_RETIRED_COLUMNS` 에 이름을 적어라 — 안 그러면 시트 @매핑에 남아 **맨 뒤로 옮겨 붙는다**.
2. 글자 칸이면 `sales-sheet-format.ts` `LEFT_COLUMNS`, 숫자면 `RIGHT_COLUMNS` 에 이름을 넣는다.
   **안 넣으면 경고 없이 가운데로 떨어진다**(세부모델·세부트림이 실제로 그랬다).
3. ERP 로 보내려면 `sheet-import.ts` `HEADER_ALIASES` 에 그 열 이름 → 필드가 있어야 한다.
4. `npx tsx scripts/publish-handover-tab.mts --apply` — 시트 「AI 인계」 @매핑을 갱신한다(**런타임 정본은 이 표다**).
5. 3탭 재발행 → ERP 동기.
6. 검사 두 개를 돌린다.

정제칸을 새로 만들 때:

```bash
npx tsx scripts/add-supplier-ai-columns.mts --include-mirror --apply    # 24곳에 칸 생성 — ⚠ 표 맨 뒤에 붙는다
npx tsx scripts/move-ai-column.mts --col=인승 --before=차종크기 --apply   # 제자리로 옮긴다
npx tsx scripts/fill-supplier-ai-columns.mts --include-mirror --apply   # 값 채우기
```

## 8. 하지 말 것 (전부 한 번씩 사고가 났다)

- **판매시트·ERP 에서 값을 고치지 마라.** 사본이다 — 다음 발행에 사라진다. 고칠 곳은 공급사 시트(정제시트는 그 원본).
- **차종마스터를 다시 끌어오지 마라.** 참조를 끊은 뒤에도 `snapToMaster` 는 남아 있다(원산지 폴백·연료/배기 보정용). 그 결과로 이름 칸을 덮으면 정제칸이 무력해진다.
- **파워트레인을 되살리지 마라.** 차명에 「2.2 디젤」이 끼면 목록·상세·공유 문구가 전부 지저분해진다.
- **하이픈으로 코드를 쪼개지 마라.** 상품키 599건이 하이픈을 품고 있다(`PD-260506-020`). 손님 링크 파서는 «통째로 먼저 찾고, 못 찾을 때만» 쪼갠다.
- **`publish-handover-tab --reset-map` 을 함부로 쓰지 마라.** 사람이 시트에 더한 줄이 날아간다.
- **열을 코드에서만 지우지 마라.** `SALES_RETIRED_COLUMNS` 를 같이 고쳐야 실제로 사라진다.

## 9. 아직 안 이어진 것 (알고 있는 빈 곳)

- **구동 정제칸 절반이 빈칸**(50%). 값 자체는 `2WD`·`AWD` 두 값으로 **이미 규격화돼 있어 규격을 새로 정할 필요는 없고 채우기만** 하면 된다.

  덩어리 큰 곳(출고불가 제외): 이안카 82대 중 50 · 아이카 101대 중 56 · 빌린카 47대 중 26 · 경진카·센트로 전부.
- **세부트림 12%** 는 정제칸 자체가 비어 있다. 채우면 다음 동기에 그대로 올라간다.

## 1. 사용자 요구사항과 판단 기준

사용자가 설명한 구조는 **데이터 받는 곳 → Firestore 원자 → ERP·판매시트·손님 화면**이다. 판매시트는 원자를 내보내는 소비처이며 원자를 거꾸로 규정하는 최상위 정본으로 취급하지 않는다.
수집 가능한 데이터와 구현에 사용할 수 있는 데이터는 구분한다. 외부에서 새 칸이 들어왔다는 사실만으로 확정된 기능·계산·출력 범위가 넓어지는 것은 아니다. 반대로 원문 보관과 명시적으로 허용된 projection(필드 선택·표현 통일)을 그 자체로 위반이라 하지 않는다.
Firestore라는 저장소 선택이나 원자 방식 자체가 틀렸다는 근거는 없다. 검증할 것은 **어떤 문서를 어떤 버전/규칙으로 확정하고, 누가 갱신하며, 각 소비처가 무엇을 읽고 변환하는가**다.

## 2. 이번에 확인한 범위와 증거의 한계

- 로컬 코드, 규칙 문서, 워크플로 선언, 명명된 Windows 작업 등록을 읽었다. 운영 DB/Google 셀과 배포본·실행 로그의 전 구간은 읽지 않았다.
- 기존 순수 검사: 축 18개, 파이프라인 회귀, 매뉴얼 25항목, 원자 발행기 3곳 모두 통과. 단 검사의 범위를 전체 SSOT 인증으로 확대하지 않는다.
- 발행기 검사 우회와 projection 선택은 SSOT 작업 폴더의 가상 입력으로 재현했다. 실제 발행/수집 스크립트는 실행하지 않았다.
- 로컬 '프리패스-자동동기'가 Running으로 표시되고 hourly-sync.cmd가 같은 저장소의 hourly-sync.mts --apply를 호출하는 것은 확인했다. 특정 단계 완료·사용한 코드 버전·실데이터 일치는 이 정보만으로 확정할 수 없다.
- 소스는 작업 중 변경될 수 있어 이 보고의 줄 번호와 함께 source-manifest.json의 SHA-256을 사용한다. 같은 이름의 미래 파일에 이 결론을 무조건 적용하지 않는다.

## FP-SSOT-01 · 우선순위 높음 · 두 판매표 생성 경로의 전환 경계

**근거:** hourly-sync ⑥은 publish-origin-tab을 실행하고 실패하면 stop한다. ⑯은 Firestore 원자를 읽는 발행기로 같은 판매표를 재발행한다. ⑯ 실패 시 ⑥ 값을 유지한다는 경고가 있다. 마지막은 allOk에 따라 exit 1을 낼 수 있으므로 실패를 성공으로 숨긴다는 주장은 하지 않는다.

**왜 중요하나:** 사용자가 검토한 원자와 다른 경로의 값이 소비처에 남을 가능성이 있는 구조다. 또한 ⑥ 실패가 ⑯ 실행도 막는다. 어느 경로가 최종 산출물을 소유하는지 불명확하면 원자 하나를 고쳐도 모두 따라온다고 보장할 수 없다.

**현재 확정하지 않은 것:** 실제로 두 표의 값이 다르다는 것, 현재 운영에 옛 값이 남았다는 것, ⑯ 실패 시 표가 항상 온전히 보존된다는 것은 미검증이다. 일부 쓰기 후 실패도 별도 확인해야 한다.

**수정 후보:** 기존 단계의 필요 기능을 수집/원자 생성 단계로 옮길 수 있는지 먼저 분해한다. 최종 판매표 writer를 한 경로로 정하고, 실패 시 마지막으로 검증된 동일 계약의 산출물을 유지할지 발행을 HOLD할지 정책을 확정한다. ⑥부터 바로 삭제하지 않는다.

**완료 조건:** 선행 산출물로 단일 최종 writer와 실패 시 HOLD/마지막 검증 산출물 유지 정책을 사용자 기준에 맞게 확정한다. 그 뒤 동일한 원자 snapshot으로 ERP·본시트·채널의 차량 ID/필드값을 대조한다. 원자 읽기 실패·부분 표 쓰기 실패·앞 단계 실패를 각각 주입하여 결과 상태와 실제 잔존 데이터가 정책대로인지 확인한다. 실제 소비처 대조 없이 코드 검사만 통과하면 완료가 아니다.

## FP-SSOT-02 · 우선순위 높음(조건부 검증 과제) · writer 보호장치는 존재하지만 대상 판정의 정본이 다르다

**기존 보호장치:** mirror-to-firestore:88–100은 DIRECT에 속한 공급사를 아예 건너뛴다. :170–189는 그 밖에 _direct_ingest_at이 있는 문서의 OWNED_BY_INGEST 필드 중 이미 채워진 값도 쓰기 payload에서 제거한다. 따라서 '두 writer가 무조건 서로 덮는다'는 의견은 기각한다.

**남은 경계:** 직접수집 대상은 Firestore partner의 sheet_url을 sheetIdFromUrl로 검사해 더한다(ingest-all-suppliers:33–40). 미러 제외 대상은 RTDB v4/partners의 sheet_url을 /docs\.google\.com/으로 검사해 더한다(mirror:87–90). 공통 기본 목록이 있어도 동적 추가 공급사의 자료원과 URL 판정 방식은 다르다.

**조건부 위험:** Firestore에만 등록되거나 양쪽 목록/URL 판정이 다르면 직접수집 집합과 미러 제외 집합이 달라질 수 있다. _direct_ingest_at 보호는 후속 안전장치지만 빈 칸 채움 및 읽기→쓰기 사이의 동시 변경까지 모두 막는다는 증거는 없다. 실제 집합 차이나 충돌은 아직 관측하지 않았다. 우선 재현할 사례는 Firestore에만 추가된 공급사, _direct_ingest_at이 아직 없는 최초 직접수집 전후, 빈 칸을 미러가 채우는 경우다. 추가 사례: 변동 모드(:634)는 _var_polled_at을 기록하고 전체 모드(:729)가 _direct_ingest_at을 기록한다. 기존 문서가 변동 모드만 거쳐 직접수집 표시가 계속 없고, 동시에 미러 DIRECT 제외 집합에서도 빠진 조건이라면 표시 기반 보호가 작동하지 않을 수 있다. 실제 해당 문서 존재는 미확인이다. DIRECT로 완전히 제외된 공급사를 무조건 경합 사례로 세지 않는다. 이 목록이 모든 동시 변경 가능성을 소진한다는 뜻도 아니다.

**수정 후보:** 공급사별 수집 소유권을 한 등록부/공통 함수에서 판정하도록 제안한다. 단 저장소 통합이 선결 조건은 아니며 버전 고정된 동등성 검사로 시작할 수 있다. 직접수집이 소유한 필드의 빈값이 '지움'인지 '미수집'인지도 명시한다.

**완료 조건:** 먼저 공급사/필드 소유권과 빈값·삭제·경합 정책을 확정한다. 정책 확정 전에는 동시 쓰기 테스트를 합격 처리하지 않는다. 이후 Firestore/RTDB 대상 집합 차집합, 같은 supplier/document/field의 쓰기 대상, 변경 전후 버전을 읽기 전용으로 비교한다. 가상 partner가 한쪽에만 존재하는 경우와 두 수집기가 동시에 갱신하는 경우를 재현하여 이중 쓰기/누락이 정책대로 처리돼야 한다.

## FP-SSOT-03 · 우선순위 높음(의미 확인) · 데이터 품질 확정과 사용자 승인 확정을 분리해야 한다

**근거:** ingest-supplier-to-firestore:425–446은 기존 pin이 확정이면 보존하고 새 후보는 canon 존재와 conf==='high'로 confirmed를 정한다. :488–493은 불변식 block이 없으면 이 confirmed와 결합해 atom.확정 및 검수상태를 기록한다. atom-invariants는 모순 검사이며 사용자 승인 원자 ID/버전을 직접 대조하는 함수는 아니다.

**판단:** 이 '확정'은 읽은 코드상 자동 매칭/품질 게이트의 상태다. 이를 사용자가 특정 의미·범위·값을 승인했다는 증거로 그대로 사용할 수 없다. 그렇다고 데이터 한 행마다 반드시 사람 승인이 필요하다고 새 규칙을 만들지도 않는다. 사용자가 승인한 자동확정 정책이 있을 수 있으므로 그 근거를 연결해야 한다.

**수정 후보:** 기존 필드를 즉시 개명하기보다 quality_status, approval_basis, contract_version처럼 필요한 개념을 먼저 정의한다(이 이름은 제안). 사람 승인/승인된 자동정책/후보를 구분하고 소비처가 요구하는 수준을 명시한다.

**완료 조건:** 고신뢰 매칭이지만 승인 정책/원자 버전이 없는 가상 사례와, 승인된 자동정책으로 확정 가능한 사례를 분리해서 검사한다. 소비처가 어떤 기준의 확정을 요구하는지 추적한다. 필드명만 바꾸거나 항상 true로 채우는 것은 해결이 아니다.

## FP-SSOT-04 · 우선순위 중간 · 발행기 검사기의 검증 공백(재현됨)

**근거:** check-publishers-read-atoms.mts는 세 파일에 대해 !A1:... 패턴을 찾고 products 읽기 유무는 파일 전체의 collection('products') 문자열로 판단한다. 범위 검사에서는 주석을 건너뛰지만 products 검사에서는 주석이 남는다.
**재현:** 별도 가상 디렉터리의 세 파일에 주석으로만 collection('products')를 넣고 !B2:C9 범위 문자열을 두어도 원본 검사기가 exit 0으로 '모두 원자에서 읽는다'고 출력했다. 발행기는 실행하지 않았고 네트워크 요청도 없었다.
**권고:** 주석 제거/다양한 범위 처리만으로 완전성을 선언하지 않는다. 실제 발행 entrypoint 목록과 공통 I/O 경계, 외부 읽기를 거부하는 가상 의존성 테스트를 결합한다. legacy publish-origin-tab의 포함/예외는 FP-SSOT-01의 확정 범위를 따른다.
**완료 조건:** 주석만 있는 원자 읽기, B2/A2부터 시작하는 범위, 변수로 만든 범위, helper를 통한 우회 읽기는 실패해야 한다. 허용한 머리글/문패 읽기는 통과해야 한다. 전체 발행을 실행하지 않는 안전한 테스트로 먼저 입증한다.

## FP-SSOT-05 · 우선순위 낮음/후보 · projection의 확인 필요 선택 규칙

**근거:** product-list-atom.ts:80–96은 '주행 낮은 것' 선택과 단기/장기보증 기간 선택에 사용자 확인 필요 주석을 두고 실제로 실행한다. 가상 12개월·2만km 50만원/보증100만원, 3만km 40만원/보증200만원에서 50만원/100만원을 반환했다.

| 같은 시점인가 | 수집 회차/관측 시각/입력 버전·변경 이력 | 단순 개수 일치로 합격 금지 |
| 무엇이 실제 배포됐나 | 배포 커밋과 스케줄러 action/실행 로그 | 로컬 코드 결과로 한정 |

| 오류 때 무엇이 남나 | 오류 주입 후 상태·출력 재읽기·재시도 이력 | 보존/복구 성공 주장 금지 |

우선순위는 관측된 사고의 심각도 판정이 아니라 다음 검증의 순서다. 01·02·03은 정책/경계 검증 과제이며 04는 재현된 검사 결함이다. 04의 회귀 테스트 보강은 소유권 조사와 병행할 수 있다.

## 5. 실행 순서와 책임 제안

1. Codex: 위 경로·해시·재현 근거 관리, 실제 writer/consumer 대조표 작성.
2. Claude PM: 원자 계약과 구 경로 전환 범위 제안, 승인 의미/실패 정책의 이견 조정. 사용자 확정을 대신하지 않는다.
3. Cursor: 확정된 범위에서 호출/참조/예외 경로 독립 검토. 이번 의견은 구현 오더가 아니다.
4. Gemini: 출처·필드·버전 대응 독립 대조. 민감 원문은 제공하지 않는다.
5. 네 AI 의견이 갈리면 원문·재현을 우선하고 중요한 미해결은 사용자 판단/HOLD. 합의만으로 데이터가 맞다고 하지 않는다.

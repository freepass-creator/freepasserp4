# 관리자 응대 — 계약문의(`/chat`)의 관리자 화면

2026-08-07 사장님 지시(여러 영업자·여러 차 문의를 편하게) → **2026-08-08 결정: 별도 페이지를 두지 않는다.**
관리자가 계약문의에 들어가면 **관리자에게 맞는 화면**이 나온다.

관련: `docs/ROLE_NAVIGATION.md`(역할별 동선) · `features/chat/admin-queue.ts`(큐 판정) · `features/chat/room-filter.ts`

---

## 1. 별도 페이지(`/desk`)를 만들었다가 걷어낸 이유

처음엔 새 라우트로 만들었다. 같은 방을 다루지만 문법이 다르다고 봤기 때문이다.

| | 영업자·공급사 | **관리자** |
|---|---|---|
| 무엇의 목록인가 | 내 대화 | **내가 처리해야 할 일** |
| 정렬의 뜻 | 최근에 온 것 | **오래 기다린 것** |
| 다 본 상태 | 읽었다 | **큐가 비었다** |

문법이 다른 건 맞다. 그런데 **화면을 하나 더 만들면 같은 방을 두 곳에서 관리하게 된다.**
입구가 둘이면 어느 쪽이 정본인지 흐려지고, 목록 규칙·행 표기·뱃지가 곧 어긋난다
(실제로 탭만 바꾸고 햄버거 메뉴를 빠뜨려 «메뉴에 없다»가 바로 나왔다).

그래서 **화면은 하나, 얼굴만 역할별로** 간다. 판정 로직(`admin-queue.ts`)은 그대로 살렸다 —
버릴 것은 페이지였지 규칙이 아니었다.

**공급사는 시트로 관리한다(앱에 안 들어온다).** 그래서 계약 5단계의 «공급 몫»은
실제로 운영자가 처리한다 — 관리자의 큐는 곧 **공급 몫 대기열**이다.

## 2. 실제로 바뀐 것 — 계약문의 화면이 역할을 안다

화면·부품은 전부 그대로다. 관리자일 때만 **기본값과 한 줄 표기**가 달라진다.

| 자리 | 관리자 | 그 외 |
|---|---|---|
| 첫 필터 | **내 차례 N** | 전체 |
| 기본 정렬 | **오래 기다린 순** | 없음(최신) |
| 상단 KPI | **내 차례** (+보조로 미확인) | 문의 미확인 |
| 행 한 줄 | 상대 · **다음 할 일**(서류확인·입금확인…) | 상대만 |
| 탭·메뉴 뱃지 | **내 차례 수** | 안읽음 수 |
| 「지우기」 | 역할 기본값(내 차례)으로 복귀 | 전체 |

신규 파일은 큐 판정 하나뿐 — `features/chat/admin-queue.ts`(순수 함수) + `scripts/sim-admin-queue.mts`.

## 3. 큐 판정 — 이 페이지의 전부

`deskQueue(rooms, contracts, role)` = **순수 함수**. 방마다 계약을 찾아 다음 미완 체크를 본다.

| 상태 | 판정 | 행에 뜨는 «다음 할 일» |
|---|---|---|
| 계약 없음 + 마지막 말이 영업자 | **내 차례** | `첫 응답` |
| 다음 미완 체크 `actor === 'provider'` | **내 차례** | 출고응답 / 서류확인 / 입금확인 / 약정발송 / 출고완료 |
| 다음 미완 체크 `actor === 'agent'` | 영업자 대기 | `영업자 대기` |
| 계약 완료·취소 | 종료 | — |

**안읽음은 별도 축이다.** 내 차례가 아니어도 «말이 왔다»는 따로 뜬다.
(안읽음 = 말 걸었나 / 내 차례 = 일이 걸렸나. 섞으면 둘 다 못 쓴다.)

**정렬 = 오래 기다린 순** (마지막 영업자 발화 시각 오름차순).
최신순으로 두면 오래된 건이 영원히 목록 아래에 깔린다 — 응대의 정의에 어긋난다.

## 4. 화면

계약문의 화면 그대로다. 관리자에게만 목록이 **대기함**으로 열린다.

```
계약문의            내 차례 7 · 미확인 3      ← 상단 KPI(역할별 뜻이 다름)
[내 차례 7] 전체 미확인 문의 완료 취소       ← 필터 칩(관리자만 «내 차례»가 맨 앞·기본)
┌──────────────────────────┬──────────────────────┐
│ 그랜저 · 123가4567         │                      │
│ A1 · 서류확인              │   대화 · 계약 · 서류   │  ← 기존 3칸 그대로
├──────────────────────────┤                      │
│ K5 · 45나6789 · A7 · 첫 응답│                      │
└──────────────────────────┴──────────────────────┘
```

행 한 줄에 **상대 · 다음 할 일**이 같이 온다. 목록만 훑고 우선순위가 잡혀야 한다.

## 5. 진입

입구는 하나다 — 계약문의 탭·메뉴 그대로. 역할이 화면을 고른다.
뱃지만 뜻이 갈린다: 관리자 = **내 차례 수**, 그 외 = 안읽음 수(`lib/domain/menu-badges.ts`).

## 6. v1에서 하지 않는 것 — 이유와 함께

- **담당 잡기(claim)**: 안읽음이 «편» 단위라 A가 읽으면 B에게도 사라진다. 관리자가 여럿이면
  중복 응대가 생긴다. 다만 지금 인원(1~2명)에선 과잉이라 안 만든다. 늘면 방에 `handled_by`.
- **목록에서 바로 승인 버튼**: 오클릭 하나가 계약 단계를 넘긴다. 승인은 계약 칸에서.
- **브라우저 알림**: 폴링 5초 + `fp:unread` 로 충분. 알림은 권한·소음 문제가 따로 붙는다.

## 7. 데이터

**새 필드 0 · 보안규칙 변경 0.** 전부 기존 `rooms`·`contracts` 에서 파생한다.
계약은 Map 1회(`contract_code`·`product_code` 색인) → 방당 O(1).

## 8. 완료 판정

- 관리자로 계약문의 진입 → 첫 화면이 「내 차례」 목록이고, 처리하면 그 건이 목록에서 빠진다.
- 영업자가 새 문의 → 「내 차례」 +1, 탭 뱃지 +1.
- **영업자·공급사 화면은 종전 그대로**(필터·정렬·행 표기·뱃지 무변화).
- `npx tsc --noEmit` 0 · `npm run check:tokens` 통과 · `npx tsx scripts/sim-admin-queue.mts` 15/15.

# 원자 원천 지도 — 「한 번만 잘 만들고, 다음엔 검수만」

> 사장님 2026-09-04 「이 원자를 확보해야 하는 그 원천이 어디인가를 파악해서 «한 번만» 원자를 잘 만들어 놓고,
> 대여료도 만들어 놓고, 다음엔 검수만. 차량번호 좌우 한 줄에 있는 게 그거니까 그게 달라지면 안 되고,
> 그게 ERP에도 구글시트에도 반영된다.」

## 큰 그림

```
원천(공급사 원본·차종마스터·정산원장·정책·파트너)
      │  «한 번» 원자화(불변) + 매시간 연동(변동)
      ▼
원자 = v4/products  (차번 = 키, 구조적 유일)   ──미러──▶  Firestore products
      │                                                      │
      ▼                                                      ▼
   ERP(파인더가 읽음)                                    구글시트(make-sample 발행)
```
★**ERP와 구글시트는 «같은 원자»를 읽는다.** 화면이 시트를 다시 읽거나 따로 세지 않는다 → 갈라질 수 없다.
Firestore = v4/products 미러(매시간). 그래서 「한 원자 = ERP = 시트」.

## 셋으로 나뉜다

| 갈래 | 뜻 | 언제 |
|---|---|---|
| **② 불변** | 차의 «정체»와 스펙 — 한 번 제대로 박으면 안 바뀐다 | 한 번(once) · 새 차 뜰 때 |
| **③④ 변동** | 상태·주행·대여료·보증금 — 매번 공급사를 따른다 | 매시간(live) |
| **⑤ 정책·계좌** | 공급사별 정책·계좌 — 거의 고정, 확인되면 박음 | 준정적(오버라이드) |

## ③④ 변동 — 매시간 연동 (`columnOwner='live'`)

| 시트 칸 | 원천 | |
|---|---|---|
| 배차상태(출고상태) | 공급사 상태 + **정산원장**(`mark-contract-in-listings` ⑤′) | 계약중/계약서/접수 → 계약중 · 인도완료 → 출고불가 |
| 주행거리(Km) | 공급사 원본 | **변동**(2026-09-04 — 재입고 때 늘어남, 대여료·보증금과 한 묶음) |
| 단기·장기보증(보증금) | 공급사 원본 기간별 | live |
| 1·6·12·24·36·48·60개월(대여료) | 공급사 원본 기간별 | live · 손오공/픽업은 반납형·인수형 두 벌 |

★출고상태만 바뀌지 스펙·요금은 상태와 «무관하게» 늘 노출한다(계약중이어도 다 보여줌). 데이터를 상태로 안 가린다.

## ★★원자 = 실시간 단일정본, 모든 소비처가 «그대로» 뿌린다 (사장님 2026-09-08)
사장님이 원자를 실시간 확인(샘/`/spring`)하고, **ERP·구글시트·손님이 그 원자를 «그대로» 뿌린다.** 화면·시트가 따로 세거나 정제칸을 다시 읽지 않는다 → 갈라질 수 없다.
**«바뀌는 값 = 차량상태 · 상품구분» 둘만**(사장님 2026-09-08 「차량상태 상품구분으로 하자 · 자꾸 바꾼다는 컴플 있음」). 이 둘이 바뀌면 세 소비처에 다 따라가야 한다.
- **차량상태(배차상태)** — 매시간 + 정산원장.
- **상품구분** — 라이프사이클(픽업구독→오공구독 · 신차렌트→중고렌트).
★그 밖(세부모델·색·제원·대여료)은 **«한 번 원자화하면 안 바꾼다»** — 세부모델은 불변(데이터가 «틀렸을 때만» 예외적 정정, 자꾸 바꾸지 않는다). 대여료는 공급사 기간값을 따르되 «상태값»은 아니다. ★★**자꾸 바뀌는 게 컴플의 핵심이다 — 바뀌는 건 상태·상품 둘뿐, 나머지는 고정.**
⚠ **그래서 판매발행(⑥ `publish-origin-tab`)이 지금 «공급사 시트 정제칸»을 읽는 것은 이 모델과 어긋난다** — 원자를 고쳐도 시트가 옛 정제칸 값(빈칸 포함)을 뿌린다(2026-09-08 실측: 원자=BMW 320i인데 시트는 빈칸). ⇒ **판매시트도 «원자»에서 발행해야** 이 넷이 다 따라온다(원천지도 #5 「원자→시트」로 일원화). 정제칸 폐기 방향과 한 몸.

## ★★소비처별 원자(projection) — «상품리스트용 원자»가 따로 있다 (사장님 2026-09-08)
raw 원자(products·policy) = **슈퍼셋**(다 갖고만 있음, 형식 섞여도 됨). 각 소비처는 그 위에 **«자기용 원자» = projection**을 둔다:
- **① 칸을 «고른다»** (그 화면이 쓸 필드만) · **② 형식을 «규격대로 통일»**.
- **상품리스트용 원자** = 그 ~70칸(배차상태·구분·차번…자차·정책UID…공급사)으로 투영 + 형식통일. **판매시트는 raw 원자가 아니라 이 «상품리스트용 원자»를 뿌린다.**
- 손님용·견적기용도 각자 projection(카탈로그 화이트리스트·견적 필드).
★**돈 형식 = 한글 단위**(사장님 2026-09-08 「1억원 5천만원 이런 식으로 · 근데 100만원부터는 100만원 이렇게」):
  - **1천만원 이상 = 천만/억** — `1억원`·`1억5천만원`·`5천만원`·`1천만원`
  - **1천만원 미만 = 만원** — `900만원`·`500만원`·`100만원`·`50만원`·`10만원` (★「백만원」 표기 안 씀 — 1,000,000은 «100만원»)
  면책금·대여료·보증금·소비자가·승계료 다 이 형식. raw 원자가 `1000000`이든 `"100만원"`이든 섞여도 projection 층에서 `100만원`으로 통일 → 「10만원 vs 100000」 사고 종결.
⚠ 지금 실측 불일치: `succession_fee=1000000`(맨숫자) vs `own_damage_max_deductible="100만원"`(한글) — 이걸 projection이 잡는다. 구현 = `lib/domain` 「상품리스트 원자 빌더」(raw 원자 → 상품리스트 칸+형식).

## 아직 원천이 «없는» 칸 (공급사가 안 줌)

- 면허기간·최소연령·최대연령·추가운전·추가운전 요금·긴급출동·사고·정비 대차·GPS 장착·탁송비·사고다발 해지기준 = 대부분 비어 있음.
  → 사장님이 알게 되는 대로 **오버라이드에 박는다**(정책 오버라이드와 같은 방식).
- **원문 자체가 없는 차** = 팔 수 없으니 목록에서 내린다(`listable=false`).

## 남은 검수 (원천은 있는데 자동으로 못 박은 것)

- **매칭실패 3대** — 매처가 신호 부족/보수적이라 못 박음: 아이오닉5(맞게 봤으나 low)·쏘렌토(연식 있으면 MQ4 high)·벤츠200(모호). → **식별 오버라이드**로 사람이 한 번 확인해 박음.
- **마스터 갭 트림 75대** — 원문 트림이 그 세부모델 마스터 `trims[]`에 없음(K5 스탠다드 등). → 마스터 보강하거나 원문칸(차명(원문))으로 충분.

---
**정리:** 원천을 이 지도대로 «한 번» 박으면, 그 원자가 그대로 ERP·시트로 나가고, 다음부터는 변동(상태·주행·요금)만 따라가며 **검수만** 하면 된다.

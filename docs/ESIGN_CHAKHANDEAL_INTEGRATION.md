## 왜 이렇게 갈랐나

**① 판단은 데이터를 가진 쪽이 한다.**
원자 정의(`entities.ts`)와 값(계약·재고·정책)이 전부 우리에게 있다. 착한거래에 스키마를 복제하면
필드를 하나 늘릴 때마다 양쪽이 어긋난다. 그래서 **저쪽은 렌더러**다.

**② 봉인은 서명을 가진 쪽이 한다.**
서명 순간에 PDF 를 만들어 해시·타임스탬프로 굳혀야 한다. 우리가 나중에 만들면
「어느 게 원본이냐」가 생기고, 그 사이 데이터가 바뀌었는지 증명할 수 없다.
**서버에서 만든다** — 서명자 기기가 만든 문서는 증명이 안 된다(erp3 의 html2canvas 방식이 그렇다).

**③ PII 는 한 곳에만 둔다.**
주민번호·면허번호·신분증·셀피·서류·서명이미지는 **착한거래에만** 남는다.
우리가 보내는 PII 는 `signer`(이름·생년·연락처)뿐이고, 받는 것도 **제출 여부와 해시**뿐이다.
우리가 원본을 받으면 파기 의무·유출 책임이 따라온다.

**④ 사본은 우리도 갖는다.**
착한거래가 사라져도 계약서는 5년 이상 남아야 한다. 단 **본문만** — 서명·신분증 이미지는 빼고.
봉인 원본은 착한거래가 단일 진실이고, 우리 사본은 열람용이다(`sealHash` 로 대조).

## 경계에서 하지 말 것

- 착한거래가 **섹션을 다시 나누거나 합치지 않는다.** 특히 「보험」과 「사고·면책」을 합치면
  손님이 보상한도와 자기부담금을 둘 다 보상으로 읽는다.
- 착한거래가 **없는 값을 채워 넣지 않는다.** 값 없는 보험 행은 우리가 일부러 뺀 것이다.
  `insuranceSide=고객직접` 이면 한도가 아예 없다 — 회사가 안 든 보험이다.

- 프리패스가 **서명·신분증 원본을 요구하지 않는다.** ③이 무너진다.
- 프리패스가 **PDF 를 따로 만들지 않는다.** ②가 무너진다.

## 1. 왜 옮기는가 — 모두싸인이 아니라 «이행 이력»

서명만 놓고 보면 모두싸인과 같다. **다른 것은 그다음이다 — 그 계약을 어기면 이력으로 등록된다.**

```
계약 체결 → 이행 기간 → 불이행 → 위반 등록(그 계약을 근거로) → 본인 이력에 축적
                                                                    ↓
                                            다음 거래 상대가 «본인 제출»로 확인
```

저신용·무심사 렌터카는 미납·잠적 위험이 커서 이 고리가 곧 심사 자료가 된다.
**서명은 수단이고 목적은 이행 기록이다.**

착한거래의 현재 위반 등록(`lib/server/risks.js`)은 회사가 `type` + `evidence`(자유 텍스트)를
넣는 구조라 근거가 회사 주장뿐이다. 계약이 붙으면 근거가 **본인이 서명한 조항 + 본인확인을 거친
서명자 + 봉인된 서명 시점**이 된다. 이의제기가 들어와도 다툴 거리가 다르다.

그 외 이점:

- 서명·본인확인 인프라를 회원사마다 만들지 않는다.
- **계약서 문구·법적 정합·버전 관리가 한 곳에 모인다.** 회원사마다 템플릿을 들면 조항이 갈라져
  위반 등록의 근거로 쓸 수 없다.
- 주민번호·주소·면허번호를 착한거래가 직접 받아 **우리 PII 보관 면적이 줄어든다.**

## 2. doctrine — 계약서는 «2차 전달물»이 아니다

착한거래 `docs/platform-principles.md` §"왜 증명서가 아닌가":

> **2차 전달물**은 검증 링크만 허용한다. 파일·캡처·복사 문구·PDF 는 위조·재배포가 쉽다.

여기서 금지 대상인 2차 전달물은 **«이용자가 자기 신뢰를 상대에게 증명하는 산출물»** — 증명서다.
**계약서는 그 범주가 아니다.** 계약서는 증명 산출물이 아니라 거래 당사자 간 문서다.

따라서 착한거래가 계약서 템플릿·서명본을 보관하는 것은 원칙 위반이 아니다. 지킬 선은 셋뿐이다.

- 계약서·서명본은 **당사자(본인·해당 회원사)만** 접근한다.
- **증명서에 계약서를 넣지 않는다.** 제3자에게 나가는 것은 여전히 검증 링크이고,
  링크가 보여주는 것은 「본인확인 완료 · 계약 N건 · 확정 위반 N건」 같은 사실 요약이다.
- 계약서 원문을 증명 수단으로 카톡·메일에 첨부하지 않는다.

## 3. 연동 인터페이스

```
① 템플릿 목록  GET  /api/v1/contract/templates?memberCompany=freepass
   → [{ templateId, name, version, kind:'standard'|'custom', fields:[…] }]
   ※ 표준 + 우리 커스텀만. 타사 커스텀이 보이면 그 자체로 영업정보 유출이다.

② 계약 발행    POST /api/v1/contract/issue      Authorization: ApiKey <우리 키>
   { templateId, externalRef,                    // externalRef = 우리 contract_code
     signer: { name, birth, phone },
     data:   { 차량번호, 차종, 기간, 월대여료, 보증금, 인수·반납 조건 … } }
   → { contractId, signUrl, previewUrl, expiresAt }
   ※ 착한거래가 템플릿에 data 를 채워 계약서를 만든다. 우리는 렌더링하지 않는다.

③ 발송        POST /api/v1/contract/{contractId}/send   { channel:'kakao'|'sms' }
   ※ 우리 화면의 «발송» 버튼이 이걸 부른다. signUrl 을 우리가 직접 보내도 된다.

④ 손님 여정   signUrl → §3.1 (본인확인 → 원자별 동의 → 서류 → 약관 → 서명)

⑤ 완료 통보   POST /api/webhooks/chakhandeal/sign   ← 우리 쪽 신설
   X-Chakhandeal-Signature: HMAC-SHA256
   { contractId, externalRef, status:'signed'|'rejected'|'expired',
     signedAt, verifyUrl, sealHash, obligationId }
   ※ 웹훅 서명 검증 필수 — 이 통보가 계약 상태를 바꾼다. 웹훅 전엔 폴링으로 시작해도 된다.

⑥ 위반 등록   POST /api/v1/obligation/{obligationId}/breach   { type, occurredAt, note }
   ※ obligationId = ⑤에서 받은 이행 대상. 계약 근거가 붙은 위반으로 기록된다.
```

**우리가 보내는 PII 는 `name`·`birth`·`phone` 뿐이다.**
주민등록번호·주소·면허번호는 착한거래가 본인확인 과정에서 직접 받는다 — 우리를 거치지 않는다.

## 3.1 손님 여정 — 「계약서를 읽는다」가 아니라 「원자를 하나씩 확인한다」

2026-08-08 결정 ③의 핵심: 손님이 긴 계약서를 스크롤하게 하지 않는다.
**계약을 이루는 원자를 묶음별로 한 화면씩 보여 주고, 묶음마다 동의를 받는다.**
조항 문구는 약관 한 페이지로 몰아 마지막에 통독시킨다.

```
①  본인확인    신분증(면허증) 촬영 → OCR → 셀피 → 얼굴 대조
                 ★두 사진은 계약서에 첨부되어 남는다(결정 ④)
②  본인정보    이름·생년·연락처·주소  ................. [확인했습니다] ☑
③  차량정보    차량번호·차명·연식·연료·주행거리 ....... [확인했습니다] ☑
④  대여조건    대여기간·월대여료·보증금·인수/반납 ..... [확인했습니다] ☑
⑤  보험        대인·대물·자손·자차·면책금·연령 ........ [확인했습니다] ☑
⑥  서류제출    가족관계증명서 등 필수서류 촬영 업로드(결정 ⑤)
⑦  약관        전문 통독(스크롤 끝까지) ............... [동의합니다] ☑
⑧  서명        서명 패드 → 봉인 → 검증링크 발급
```

**②~⑤ 의 값은 전부 이미 계약에 동결돼 있다.** 새로 만들 데이터가 없다 —
`②` = `customer_*`, `③` = `*_snapshot`, `④` = `rent_month/rent_amount/deposit_amount_snapshot`,
`⑤` = 매물 `policy_code` 로 이어지는 정책 원자(`lib/domain/public-catalog.ts`의 `PUBLIC_POLICY_FIELDS` 와 같은 축).

### 묶음 정의는 어디에 두나 — **우리 쪽 SSOT**

원자 정의(`lib/intake/entities.ts`)와 값이 모두 우리에게 있다. 묶음 정의를 착한거래에 복제하면
스키마가 두 벌이 되어 필드를 하나 추가할 때마다 양쪽이 어긋난다.
→ **발행 payload 의 `data` 를 «묶음 배열»로 보낸다. 착한거래는 렌더러다.**

```jsonc
"consentGroups": [
  { "key": "identity",  "title": "본인정보",
    "rows": [{ "label": "이름", "value": "홍길동" }, …],
    "confirmLabel": "위 본인정보가 정확함을 확인합니다", "required": true },
  { "key": "vehicle",   "title": "차량정보",  … },
  { "key": "terms",     "title": "대여조건",  … },
  { "key": "insurance", "title": "보험",      … }
],
"requiredDocs": [
  { "key": "family_register", "label": "가족관계증명서", "required": true },
  { "key": "id_card_back",    "label": "신분증 뒷면",    "required": false }
],
"agreementText": { "version": "v1", "sections": [{ "t": "제1조 …", "b": "…" }] }
```

`rows` 는 **표시용 문자열까지 우리가 만들어 보낸다**(금액 콤마·개월 표기 등).
착한거래가 다시 포맷하면 화면과 계약서의 숫자가 달라 보일 수 있다.

### 동의 결과

```jsonc
"consents": { "identity": 1754… , "vehicle": 1754…, "terms": 1754…, "insurance": 1754…, "agreement": 1754… }
```

웹훅으로 돌아와 계약의 기존 예약 필드 `sign_consents`·`sign_consent_version` 에 그대로 들어간다.

### 서류·사진은 착한거래가 보관한다

면허증·셀피·가족관계증명서는 **우리가 받지 않는다.** §1 의 이점(«우리 PII 보관 면적이 줄어든다»)과
§3 의 원칙(«우리가 보내는 PII 는 name·birth·phone 뿐»)을 유지하려면 수집·보관 주체가 착한거래여야 한다.
우리에게는 **제출 여부와 해시만** 웹훅으로 온다.

```jsonc
"documents": [
  { "key": "family_register", "submittedAt": 1754…, "sha256": "…" },
  { "key": "id_license",      "submittedAt": 1754…, "sha256": "…" },
  { "key": "selfie",          "submittedAt": 1754…, "sha256": "…" }
]
```

> ⚠ 우리 Storage 에 받고 싶어지면 `storage.rules` 의 `contract-files/{contractId}/` 가 이미 있다.
> 그러나 그 순간 민감정보 보관 주체가 우리로 바뀐다 — 파기 의무·유출 책임이 따라온다.
> **기본은 착한거래 보관.** 바꾸려면 §7 PII 최소화와 함께 다시 판단할 것.

## 9. 계약서 관리 페이지 (결정 ②)

발송이 관리자만이므로 **관리자 전용 화면**이다. 계약 진행(`/contract`)과 축이 다르다 —
저기는 «5단계 업무», 여기는 «손님이 어디까지 서명했나».

```
목록 열   계약번호 · 고객 · 차량 · 발송일시 · 진행 · 상태 · 검증링크
진행 표시  ●●●●○○○  4/7   ← §3.1 의 여정 단계
```

| 상태 | 뜻 | 근거 필드 |
|---|---|---|
| 미발송 | 약정까지만 됨 | `esign_id` 없음 |
| 발송 | 링크 나감 | `sign_status='발송'`, `sign_sent_at` |
| 열람 | 손님이 링크 열었다 | 웹훅 `opened` |
| 진행 | n/7 단계 | 웹훅 `progress` |
| 서명완료 | 봉인·검증링크 발급 | `sign_signed_at`, `esign_verify_url`, `esign_seal_hash` |
| 반려 | 손님이 거절 | `sign_reject_reason`, `sign_rejected_at` |
| 만료 | 기한 지남 | `sign_expires_at` |

**필드는 이미 예약돼 있다**(§4). 새로 필요한 것은 진행 단계뿐 — `esign_progress`(0~7)·`esign_progress_at`.

> ⚠ **지금 넣어야 한다.** 출시 후보 Rules 가 계약 하위키를
> `!data.parent().exists() || newData.val() === data.val()` 로 잠근다.
> 규칙 게시 뒤에는 기존 계약에 새 필드를 못 쓴다 — §4 가 예약 필드를 미리 박은 이유와 같다.
> (2026-08-08: `rent_*_snapshot` 3개가 정확히 이 문제로 계약 진행을 막아 `!data.exists()` 로 완화했다.)

### 상태 동기화 — 웹훅 우선, 폴링 폴백

착한거래에 웹훅이 없으므로(§5) 순서는 이렇다.

1. **1단계(웹훅 전)**: 관리 페이지를 열 때 `GET /api/v1/contract/{id}` 를 서버에서 조회해 갱신.
   목록이 N건이면 N번 호출이므로 **관리자가 «새로고침»을 누를 때만**. 자동 폴링 금지.
2. **2단계(웹훅 후)**: `POST /api/webhooks/chakhandeal/sign` 수신 → 계약 갱신.
   HMAC 서명 검증 필수 — 이 통보가 계약 상태를 바꾼다.

**웹훅은 Admin SDK 로 쓴다(규칙 우회).** 그래야 `sign_*` 계열을 클라이언트 쓰기 금지로 잠글 수 있다 —
`check:release` 가 지적하는 «계약 전자서명 제어필드 영업자 전용 Rules 누락» 이 이걸로 닫힌다.

## 4. 지금 넣어 둔 «이음매»

서명 로직이 `lib/domain/sign.ts` 한 파일에 모여 있어 파급이 작다.

| 현재 | 전환 후 |
|---|---|
| `createSignToken(contract)` | → `POST /contract/issue` → `signUrl` |
| `getContractByToken(token)` | 불필요 — 손님이 착한거래 화면에 있다 |
| `submitSign(...)` (우리가 PII 수집) | 불필요 — 착한거래가 수집 |
| `approveSign` / `rejectSign` | 그대로 — 업무 판단은 우리 몫 |

**오픈 전에 해야 하는 것은 필드 예약 하나뿐이다.** ✅ 완료(커밋 `22cd393`)

`esign_provider`(`self` | `chakhandeal`) · `esign_id` · `esign_verify_url` · `esign_seal_hash`.

지금 안 하면 나중에 못 넣는다 — 출시 후보 Rules 가 계약 하위키를
`!data.parent().exists() || newData.val() === data.val()` 로 잠그기 때문에,
규칙 게시 뒤에는 기존 계약에 새 필드를 쓸 수 없다.

문서 해시 함수는 **불필요해졌다** — 렌더를 착한거래가 하므로 해시도 그쪽에서 만든다.
`POST /api/chakhandeal/contracts/send`가 로그인 사용자와 계약 귀속을 서버에서 다시 확인하고,
`CHAKHANDEAL_API_*` 서버 환경변수가 모두 설정된 경우에만 착한거래 계약 발행→SMS 발송을 수행한다.
API 키는 브라우저에 노출하지 않으며 외부 발행 식별자는 `v4/contracts/{contract_code}`의 예약 필드에 기록한다.
완료 웹훅과 계약 단계 자동 반영은 착한거래의 실제 응답·서명 검증 규격 확정 후 추가한다.

## 6. 예약시스템과의 경계

```
예약(착한거래) → 계약 발행·서명(착한거래) → 이행 기간 → 이행/불이행 등록(착한거래)
                        ↑
        프리패스는 매물·재고·요금·정산을 갖고 «어떤 차를 얼마에» 를 데이터로 넘긴다
```

**경계를 흐리지 말 것**: 매물·재고·요금·정산은 우리 몫, 신원·문서·이행 기록은 착한거래 몫이다.
예약을 착한거래가 받더라도 **재고 판단은 우리에게 물어야 한다** — 예약 가능 여부 조회 API 가
별도로 필요하다. 이번 범위 밖이지만 설계 시 자리를 남겨 둘 것.

## 7. 보안 — 착한거래 불변식과의 정합

- **교차검색 금지(불변식 2)**: 우리가 「이 사람 다른 회사 계약 있나」를 물을 수 없다.
  조회는 우리가 만든 `contractId`/`externalRef` 로만. 템플릿 목록도 우리 것 + 표준만 본다.
- **회사별 가명토큰(불변식 3)**: 같은 손님이라도 회사마다 토큰이 완전히 다르다.
  이 연동이 그 격리를 우회하는 통로가 되면 안 된다.
- **본인 제출 모델(불변식 5)**: 착한거래 이력을 우리가 당겨오는 게 아니라
  **손님이 우리에게 제출**하는 방향이다. 심사에 쓰려면 Phase 4 `consent_grant` 흐름을 타야 한다.
  **서명 연동과 이력 제출은 별개 기능이다 — 섞지 말 것.**
- **PII 최소화**: 지금 `signSubmissionPatch` 가 주민번호를 계약에 쓰는데, 전환 후 그 경로가 사라진다.

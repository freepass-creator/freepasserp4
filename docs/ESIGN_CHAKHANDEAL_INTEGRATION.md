## 1. 왜 옮기는가 — 모두싸인이 아니라 «이행 이력»

서명만 놓고 보면 모두싸인과 같다. **다른 것은 그다음이다 — 그 계약을 어기면 이력으로 등록된다.**

```
계약 체결 → 이행 기간 → 불이행 → 위반 등록(그 계약을 근거로) → 본인 이력에 축적
                                                                    ↓
                                            다음 거래 상대가 «본인 제출»로 확인
```

저신용·무심사 렌터카는 미납·잠적 위험이 커서 이 고리가 곧 심사 자료가 된다.
**서명은 수단이고 목적은 이행 기록이다.**

착한거래의 현재 위반 등록(`lib/server/risks.js`)은 회사가 `type` + `evidence`(자유 텍스트)를
넣는 구조라 근거가 회사 주장뿐이다. 계약이 붙으면 근거가 **본인이 서명한 조항 + 본인확인을 거친
서명자 + 봉인된 서명 시점**이 된다. 이의제기가 들어와도 다툴 거리가 다르다.

그 외 이점:

- 서명·본인확인 인프라를 회원사마다 만들지 않는다.
- **계약서 문구·법적 정합·버전 관리가 한 곳에 모인다.** 회원사마다 템플릿을 들면 조항이 갈라져
  위반 등록의 근거로 쓸 수 없다.
- 주민번호·주소·면허번호를 착한거래가 직접 받아 **우리 PII 보관 면적이 줄어든다.**

### 문서의 주인이 바뀐다 (초기 구상 수정)

| | 초기(2026-07-31) | **확정(2026-08-04)** |
|---|---|---|
| 계약서 템플릿 | 우리가 보유 | **착한거래가 보유·관리**(표준 + 렌트사별 커스텀) |
| 계약서 렌더 | 우리가 만들고 해시만 전달 | **착한거래가 데이터로 렌더** |
| 우리가 보내는 것 | 문서 해시 | **템플릿ID + 계약 데이터** |
| 발송 | 우리 | 우리 화면의 «발송» → 착한거래가 실제 발송 |

초안의 «계약 원문은 회원사가 보관» 은 **철회한다.** 근거는 §2.

## 2. doctrine — 계약서는 «2차 전달물»이 아니다

착한거래 `docs/platform-principles.md` §"왜 증명서가 아닌가":

> **2차 전달물**은 검증 링크만 허용한다. 파일·캡처·복사 문구·PDF 는 위조·재배포가 쉽다.

여기서 금지 대상인 2차 전달물은 **«이용자가 자기 신뢰를 상대에게 증명하는 산출물»** — 증명서다.
**계약서는 그 범주가 아니다.** 계약서는 증명 산출물이 아니라 거래 당사자 간 문서다.

따라서 착한거래가 계약서 템플릿·서명본을 보관하는 것은 원칙 위반이 아니다. 지킬 선은 셋뿐이다.

- 계약서·서명본은 **당사자(본인·해당 회원사)만** 접근한다.
- **증명서에 계약서를 넣지 않는다.** 제3자에게 나가는 것은 여전히 검증 링크이고,
  링크가 보여주는 것은 「본인확인 완료 · 계약 N건 · 확정 위반 N건」 같은 사실 요약이다.
- 계약서 원문을 증명 수단으로 카톡·메일에 첨부하지 않는다.

## 3. 연동 인터페이스

```
① 템플릿 목록  GET  /api/v1/contract/templates?memberCompany=freepass
   → [{ templateId, name, version, kind:'standard'|'custom', fields:[…] }]
   ※ 표준 + 우리 커스텀만. 타사 커스텀이 보이면 그 자체로 영업정보 유출이다.

② 계약 발행    POST /api/v1/contract/issue      Authorization: ApiKey <우리 키>
   { templateId, externalRef,                    // externalRef = 우리 contract_code
     signer: { name, birth, phone },
     data:   { 차량번호, 차종, 기간, 월대여료, 보증금, 인수·반납 조건 … } }
   → { contractId, signUrl, previewUrl, expiresAt }
   ※ 착한거래가 템플릿에 data 를 채워 계약서를 만든다. 우리는 렌더링하지 않는다.

③ 발송        POST /api/v1/contract/{contractId}/send   { channel:'kakao'|'sms' }
   ※ 우리 화면의 «발송» 버튼이 이걸 부른다. signUrl 을 우리가 직접 보내도 된다.

④ 손님 여정   signUrl → 본인확인(신분증·OCR·셀피) → 계약서 확인 → 서명

⑤ 완료 통보   POST /api/webhooks/chakhandeal/sign   ← 우리 쪽 신설
   X-Chakhandeal-Signature: HMAC-SHA256
   { contractId, externalRef, status:'signed'|'rejected'|'expired',
     signedAt, verifyUrl, sealHash, obligationId }
   ※ 웹훅 서명 검증 필수 — 이 통보가 계약 상태를 바꾼다. 웹훅 전엔 폴링으로 시작해도 된다.

⑥ 위반 등록   POST /api/v1/obligation/{obligationId}/breach   { type, occurredAt, note }
   ※ obligationId = ⑤에서 받은 이행 대상. 계약 근거가 붙은 위반으로 기록된다.
```

**우리가 보내는 PII 는 `name`·`birth`·`phone` 뿐이다.**
주민등록번호·주소·면허번호는 착한거래가 본인확인 과정에서 직접 받는다 — 우리를 거치지 않는다.

## 4. 지금 넣어 둘 «이음매»

서명 로직이 `lib/domain/sign.ts` 한 파일에 모여 있어 파급이 작다.

| 현재 | 전환 후 |
|---|---|
| `createSignToken(contract)` | → `POST /contract/issue` → `signUrl` |
| `getContractByToken(token)` | 불필요 — 손님이 착한거래 화면에 있다 |
| `submitSign(...)` (우리가 PII 수집) | 불필요 — 착한거래가 수집 |
| `approveSign` / `rejectSign` | 그대로 — 업무 판단은 우리 몫 |

**오픈 전에 해야 하는 것은 필드 예약 하나뿐이다.** ✅ 완료(커밋 `22cd393`)

`esign_provider`(`self` | `chakhandeal`) · `esign_id` · `esign_verify_url` · `esign_seal_hash`.

지금 안 하면 나중에 못 넣는다 — 출시 후보 Rules 가 계약 하위키를
`!data.parent().exists() || newData.val() === data.val()` 로 잠그기 때문에,
규칙 게시 뒤에는 기존 계약에 새 필드를 쓸 수 없다.

문서 해시 함수는 **불필요해졌다** — 렌더를 착한거래가 하므로 해시도 그쪽에서 만든다.
나머지(API 클라이언트·웹훅 라우트)는 착한거래 준비 후.

## 6. 예약시스템과의 경계

```
예약(착한거래) → 계약 발행·서명(착한거래) → 이행 기간 → 이행/불이행 등록(착한거래)
                        ↑
        프리패스는 매물·재고·요금·정산을 갖고 «어떤 차를 얼마에» 를 데이터로 넘긴다
```

**경계를 흐리지 말 것**: 매물·재고·요금·정산은 우리 몫, 신원·문서·이행 기록은 착한거래 몫이다.
예약을 착한거래가 받더라도 **재고 판단은 우리에게 물어야 한다** — 예약 가능 여부 조회 API 가
별도로 필요하다. 이번 범위 밖이지만 설계 시 자리를 남겨 둘 것.

## 7. 보안 — 착한거래 불변식과의 정합

- **교차검색 금지(불변식 2)**: 우리가 「이 사람 다른 회사 계약 있나」를 물을 수 없다.
  조회는 우리가 만든 `contractId`/`externalRef` 로만. 템플릿 목록도 우리 것 + 표준만 본다.
- **회사별 가명토큰(불변식 3)**: 같은 손님이라도 회사마다 토큰이 완전히 다르다.
  이 연동이 그 격리를 우회하는 통로가 되면 안 된다.
- **본인 제출 모델(불변식 5)**: 착한거래 이력을 우리가 당겨오는 게 아니라
  **손님이 우리에게 제출**하는 방향이다. 심사에 쓰려면 Phase 4 `consent_grant` 흐름을 타야 한다.
  **서명 연동과 이력 제출은 별개 기능이다 — 섞지 말 것.**
- **PII 최소화**: 지금 `signSubmissionPatch` 가 주민번호를 계약에 쓰는데, 전환 후 그 경로가 사라진다.

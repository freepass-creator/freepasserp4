# 전자계약 — 착한거래 외부 연동 설계

작성: Claude, 2026-08-04
전제: 2026-07-31 확정 방향 — **전자계약·전자서명은 착한거래(chakhandeal)에 «서비스»로 구축하고
회원사(freepasserp4·renman 등)는 «연동만» 한다.** 여러 회원사가 같은 서명 인프라를 공유하고
증명 신뢰가 플랫폼에 쌓이는 구조.

---

## 0. 결론 먼저 — 지금은 못 붙인다

착한거래가 **실데이터 오픈 금지 상태**다. `docs/SECURITY-DESIGN.md` D2 결정:

> 본인확인은 당장 스텁 유지, Phase 1~2 는 토큰 구조만,
> **실데이터 오픈은 실 IdV(본인확인) 전까지 보류**(데모는 계속).

현재 본인확인이 전부 mock 이고 `DEMO_MODE` 기본 true 다. 얼굴 매칭 엔진이 없어 콘솔 육안 대조다.
여기에 **주민등록번호를 받는 실계약**을 태우면 안 된다.

따라서 순서는 이렇다.

```
지금(B2B 오픈)   freepasserp4 자체 서명 그대로 사용
                 ↑ 이미 동작하고, 후보 Rules 가 sign_* 를 영업자 전용으로 잠근다
                 ↑ 단 §4 의 '이음매'만 미리 넣어 둔다(작업량 작음)

착한거래 P4~P6   consent_grant·불변감사·관리자 마스킹 + **실 IdV 도입**
                 ↑ 이게 끝나야 실데이터를 받을 수 있다

그 다음          freepasserp4 서명 경로를 착한거래로 전환(§3)
                 ↑ 이음매가 있으면 어댑터 교체 수준
```

**오픈을 미룰 이유는 없다.** 지금 붙이려 하면 오히려 오픈이 막힌다.

---

## 1. 왜 착한거래로 옮기는가

- 서명·본인확인·해시봉인 인프라를 회원사마다 만들지 않는다.
- **증명 신뢰가 플랫폼에 쌓인다** — "이 해시의 문서를 이 사람이 언제 서명했다"를 제3자가 검증.
- freepasserp4 는 계약 원문·업무 흐름에 집중하고 신원·증거는 위탁.

## 2. doctrine 충돌과 해소 (그대로 유효)

착한거래 `docs/platform-principles.md` 는 **«PDF·파일 증명 금지, 2차 전달물은 검증 링크만»** 을 못박는다.
계약서 PDF 를 착한거래가 다루면 정면 충돌이다.

**해소안**: 계약 원문은 **회원사(freepasserp4)가 보관**하고, 착한거래는 네 가지만 한다.

1. 본인확인(신분증 촬영 + OCR + 셀피)
2. 서명 수집
3. **문서 해시 + 타임스탬프 봉인**
4. `/v?id=` 검증 링크 발급

파일을 배포하지 않고 사실만 링크로 증명 → doctrine 위반이 아니라 정석이다.

## 3. 연동 인터페이스

### 3-1. 서명 요청 (freepasserp4 → 착한거래)

```
POST /api/v1/sign/request
Authorization: ApiKey <회원사 M2M 키>

{
  "documentHash": "sha256:...",         // 계약서 원문 해시 (원문은 안 보낸다)
  "documentMeta": { "title": "렌터카 대여 계약서", "carNumber": "12가3456", "term": 36 },
  "signer":       { "name": "홍길동", "birth": "900101" },
  "memberCompany": "freepass",
  "externalRef":  "TMP-260727-01-yvjf"   // 우리 contract_code — 상관관계 키
}
→ 200 { "signId": "...", "signUrl": "https://…/sign/…", "expiresAt": 1790000000000 }
```

### 3-2. 손님 여정 (착한거래에서)

`signUrl` → 신분증 촬영 → OCR → 셀피 → 문서 확인 → 서명

### 3-3. 완료 통보 (착한거래 → freepasserp4)

```
POST /api/webhooks/chakhandeal/sign     ← freepasserp4 에 신설
X-Chakhandeal-Signature: <HMAC-SHA256>

{ "signId", "externalRef", "status": "signed|rejected|expired",
  "signedAt", "verifyUrl": "https://…/v?id=…", "sealHash": "sha256:..." }
```

웹훅이 없으면 폴링으로 시작해도 된다(`GET /api/v1/sign/{signId}`).
**웹훅 서명 검증은 필수** — 이 통보가 계약 상태를 바꾼다.

## 4. 지금 넣어 둘 «이음매» (작업량 작음, 오픈 전 가능)

현재 서명 로직은 `lib/domain/sign.ts` 한 파일에 모여 있다. 좋은 상태다 —
바깥에서 이 함수들만 갈아끼우면 된다.

| 현재 | 착한거래 전환 후 |
|---|---|
| `createSignToken(contract)` → 우리 토큰 + 공개 슬롯 | → `POST /sign/request` → `signUrl` |
| `getContractByToken(token)` → 우리 공개 슬롯 조회 | (불필요 — 손님이 착한거래 화면에 있다) |
| `submitSign(...)` → 우리가 PII 수집 | (불필요 — 착한거래가 수집) |
| `approveSign` / `rejectSign` | 그대로 (업무 판단은 우리 몫) |

**오픈 전에 넣을 것은 두 개뿐이다.**

1. **계약에 외부 서명 필드 예약** — `esign_provider`(`'self' | 'chakhandeal'`) ·
   `esign_id` · `esign_verify_url` · `esign_seal_hash`.
   지금은 전부 `'self'` 로 두고 비워 둔다. 나중에 추가하면 **후보 Rules 의 불변 validate 때문에
   기존 계약에 못 넣는다**(`!data.parent().exists() || newData.val() === data.val()`).
   → 필드 예약은 **오픈 전에 해야 한다.**
2. **문서 해시 함수** — 계약서 원문(현재 우리가 만드는 PDF/HTML)의 정규화 + SHA-256.
   착한거래에 보낼 값이고, 우리 쪽 원문 보관의 무결성 증거도 된다.

나머지(API 클라이언트·웹훅 라우트)는 착한거래가 준비된 뒤에 만들면 된다.

## 5. 착한거래 쪽에 필요한 것 (2026-07-31 조사, 현재도 유효)

| 항목 | 현재 상태 |
|---|---|
| 서명요청 생성 API · 서명 URL 발급 | **없음** — 손님이 4자리 코드 직접 입력 전제 |
| 서명 이미지 저장 | **없음** — `signed` 불리언만, PNG dataURL 을 버린다 |
| 문서 해시·타임스탬프 봉인 | **없음** — 문서 개념 자체가 없고 PDF 라이브러리 0 |
| 웹훅/콜백 | **없음** (grep 0건) |
| `externalRef` 상관 필드 | **없음** — 이름+생년 HMAC matchKey 뿐 |
| M2M 인증(API Key) | **없음** — 사용자 토큰뿐 |
| 실 본인확인 | **mock** — 휴대폰 인증 전체 mock · 얼굴매칭 엔진 없음 |

**주의**: 하위호환 박제 URL `/consent?code=` · `/v?id=` 는 깨지 않을 것.
착한거래 실제 경로는 `D:\dev\chakhandeal` (rentsafe·rentsafe-pro 는 구본, 손대지 말 것).
Firebase 프로젝트가 freepasserp4 와 **별개**다.

## 6. 보안 — 착한거래 불변식과의 정합

착한거래 `chakhandeal-security-authz-spec` 의 불변식이 이 연동에도 걸린다.

- **교차검색 금지(불변식 2)**: freepasserp4 가 「이 사람 다른 회사 계약 있나」를 물을 수 없다.
  우리가 보내는 것은 `externalRef` 로 우리 계약을 가리키는 것뿐이고, 조회도 우리가 만든 건만 된다.
- **회사별 가명토큰(불변식 3)**: 같은 손님이라도 freepasserp4 토큰과 타사 토큰이 완전히 다르다.
  대조로 동일인 식별 불가 — 이걸 우회하려 하지 말 것.
- **본인 제출 모델(불변식 5)**: 착한거래에 쌓인 이력을 우리가 당겨오는 게 아니라,
  **손님이 자기 이력을 우리에게 제출**하는 방향이다. 심사에 쓰려면 그 흐름을 타야 한다.
- **PII 최소화**: 우리는 `name`·`birth` 만 보낸다. 주민등록번호·주소·면허번호는
  **착한거래가 본인확인 과정에서 직접 받는다** — 우리를 거치지 않는 게 맞다.
  (지금 우리 `signSubmissionPatch` 가 주민번호를 계약에 쓰는데, 전환 후에는 그 경로가 사라진다.
   PII 보관 면적이 줄어드는 게 이 연동의 부수 이득이다.)

## 7. 판단

- **오픈 전**: §4 의 이음매 2개만. 특히 **필드 예약은 지금 안 하면 나중에 규칙이 막는다.**
- **오픈 후**: 착한거래 P4~P6 + 실 IdV 완료를 기다린다. 그게 실데이터 전제 조건이다.
- **전환 시점**: 어댑터 교체 + 웹훅 라우트 신설. `lib/domain/sign.ts` 가 이미 한 파일로 모여 있어
  파급이 작다.
- 착한거래 쪽 구현은 **Cursor 담당**(설계=Claude)이라는 기존 파이프라인 그대로.

## 2. 설계표

### 2-1. 단계 SSOT — 관리자가 보는 축은 이것 하나

| 단계 | 이름 | 들어오는 조건 | 이 단계의 **유일한 행동** | 나가는 조건 |
|---|---|---|---|---|
| ① | **작성** | 「새 계약 만들기」 (저장 전 draft) | 공급사·계약서·정책 → 차량 → 대여조건 입력 → **계약서 만들기** | 저장 성공 |
| ② | **발송 전** | 저장됨 · `sign_status ∈ {미발송, 발행}` | A4 확인 → **링크 만들기** → **링크 복사**·전달 (·해지) | 고객이 엶(`열람`) |
| ③ | **고객 작성 중** | `sign_status ∈ {열람, 진행중}` · 보완 요청 뒤 재작성 포함 | 없음(기다림). 재전달용 링크 복사·해지만 | 고객 제출(`검토대기`) |
| ④ | **검토 대기** | `session.status ∈ {pending_review, approving, rejecting}` | 제출물 확인 → **승인** 또는 **보완 요청** | 승인(`서명완료`) / 보완 요청(→③) |
| ⑤ | **완료** | `sign_status === '서명완료'` | 완료 PDF · 봉인 검증 · 인도일 확정 | — |

- 목록 뱃지 = 상단 스테퍼 = 필터 칩 = 이력 라벨 — **전부 이 표의 이름**. 다른 번호·다른 이름 금지(원문자는 스테퍼에만, 카드 안에는 번호 없음).
- `esign-center.ts esignCenterBucket` 을 이 5단계(목록은 ②~⑤ 4개)로 갈아끼운다. 판정 우선순위: 완료 > 검토 대기 > 고객 작성 중 > 발송 전.

### 2-2. 플래그 — 단계와 섞지 않는다

| 플래그 | 조건 | 표시 |
|---|---|---|
| **확인 필요** | BLOCK 체크 1개↑ (`validateEsignCenterContract`) | 목록 행 뱃지 옆 빨간 점 + 작업면 「발송 전 확인」 카드(문제 있을 때만) |
| **만료** / **해지** | `expiresAt ≤ now`(미제출) / `revokedAt` | ②·③ 카드가 「링크 다시 만들기」 카드로 바뀜 |
| **보완 요청됨** | `sign_status === '반려'` | ③ 단계 + 카드 상단에 요청 항목·사유·횟수 |

- 「확인필요」는 더 이상 버킷이 아니다. 목록 5건 중 4건이 빨갛던 문제의 해법.
- 필터 칩: `전체 · 발송 전 · 고객 작성 중 · 검토 대기 · 완료 · 확인 필요(플래그)` — `/esign` 목록에도 붙인다(지금은 `/contract` 에만).

### 2-4-1. 작성 순서 4단 (사장님 2026-08-20 확정)

> 「회사 선택 - 차량선택(정책없으면 정책까지 선택) - 기간별대여료선택 - 조건(운전연령, 주행거리 등) 선택」

| # | 카드 | 고르는 것 | 열리는 조건 |
|---|---|---|---|
| 1 | **회사** | 공급사(출고가능 대수 병기) | 항상 |
| 2 | **차량** | 그 회사 출고가능 차량 → **정책은 차가 데려온다** · 못 데려오면 여기서 정책 선택 | 회사 선택 |
| 3 | **기간별 대여료** | 대여기간 칩 → 대여료·보증금·납부조건·보증금 납부 회차 | 차량 **+ 정책** |
| 4 | **조건** | 운전자 연령 칩 · 약정주행거리 · 운전자 범위 · 정비상품 · 특약 | 기간·대여료 |

- ★**계약서 종류는 고르지 않는다**(select 폐지). 차량 상품구분(렌트/구독) × 정책 보험조건(포함/별도) → `templateForKindAndInsurance()` 가 표준계약서 3벌 중 하나를 정하고, 카드 2에 「계약서 · 렌트 · 보험포함」으로 표시만 한다. 어긋날 조합이 아예 생기지 않는다.
- ★**차량 → 정책 승계**(`resolveVehiclePolicy`): ① 차량 정책코드로 찾기 → ② 「(프리패스 기본)」이거나 못 찾으면 그 상품구분의 공급사 정책이 **하나뿐일 때만** 그것 → ③ 그래도 못 정하면 미정(사람이 고른다). 찍어서 고르지 않는다 — 남의 조건이 계약서에 실린다.
- 실측(2026-08-20 RTDB): 출고가능 **276대** 중 정책코드 있음 270(98%)이지만 **ERP 정책으로 실제 이어지는 건 135대(49%)** — 114대는 정책코드 칸에 시트 라벨 「(프리패스 기본)」, 21대는 ERP에 없는 `RP006_WEB`(아이언). 그래서 ②·③ 갈래가 실제로 필요하다.
- 차량 후보는 **회사만 정해지면** 열린다(`searchContractVehicles(products, providerCode, null, q)`) — 계약서 종류를 먼저 고르지 않는다.
- 처음 안(한 열)은 사장님이 «4칸» 배치로 고쳐 확정: 「1에 목록 · 2·3에 계약서 작성내용 · 4에 발송링크 만들고 PDF 확인」. 초안 카드 1·2·3이 좌우로 나뉘어 튀어나오던 것(`repeat(auto-fit, minmax(560px,1fr))`)은 폐기.
- 상태는 `useFreepassEsign` 한 번만 읽고 ②·③(`FreepassEsignStagePane`)·④(`FreepassEsignDocumentPane`)가 나눠 쓴다 — 이중 페치 없음.
- 계약 요약은 **한 군데**(`EsignContractSummary`), 초안은 4번 카드 안의 요약 한 벌.

### 2-6. 「고객 진행」 = 실제 여정

- 행 = 발행 스냅샷의 여정 순서: `계약 확인(summary) · 수집 동의(privacy) · 본인확인(identity) · [추가 운전자(additional_driver)] · [추가서류] · snapshot.consentPages[].title(vehicle/rental/payment/driver/insurance/accident/service 중 있는 것) · 약관(agreement) · 서명(signature)`.
- 값 = `session.progress[key]` 시각(`완료 · 시:분`) / 다음 칸 `지금` / 나머지 `—`. 서버 응답에 이미 있음(`contracts/[contractCode]/route.ts stateResponse`) — **서버 변경 없음.**
- `ESIGN_STEPS` 8행 렌더(`FreepassEsignPanes.tsx:502`)는 화면에서 내린다. `esign-progress.ts` 자체는 목록의 `esign_progress` 집계용으로 남겨도 됨(화면 표기 SSOT 아님).

### 2-7. 미리보기 오염 방지

- 관리자 「모바일 미리보기」는 실제 손님 링크를 열지 않는다. 안: 미리보기 iframe → `/sign/{token}?preview=1` → 서명 페이지가 preview 이면 `GET …/public/{token}?peek=1` 호출, 서버는 `peek=1` 이면 **opened 전이·`sign_status '열람'` 기록을 건너뛰고** view 만 준다(입력·제출 버튼은 비활성). 손님이 `peek=1` 을 붙여 봐도 해될 것 없음 — 첫 progress POST 에서 `openedAt` 이 없으면 그때 채운다.
- 이것만 서버 한 줄 예외. **Codex 검증 항목**: peek 로는 어떤 쓰기도 일어나지 않는다.

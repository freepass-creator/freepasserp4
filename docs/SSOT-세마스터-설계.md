# SSOT 세 마스터 설계 — 「한 문으로 들어와 한 문으로 나간다」 (2026-09-09)

> 사장님 2026-09-09:
> 「상품마스터(차종마스터 기본의 차량정보·대여료·정책) / 차종마스터(트림·색상·제원) /
>  상태마스터(팔렸는지 현상태) — 이 값들이 **SSOT에서 모여서 한 곳으로 들어오고 한 곳에서 나가야 함.**」
> 「**SSOT를 명확하게 만들고 거기에 있는 거로만 구현한다.**」

## 0. 왜 이 문서가 필요한가 — 정본은 정해졌는데 «전파가 수동»이라 갈라졌다

차종마스터 정본은 이미 **Firestore `vehicle_master`** 로 확정돼 있다(사장님 2026-09-08, `export-master-firestore-to-json.mts`).
문제는 «정본이 어디냐»가 아니라 **정본→소비처 전파가 수동**이라는 것:

```
Firestore vehicle_master (정본)  ──[export 잡 «수동 실행»]──▶  public/data/vehicle-master.json (파생 캐시)
                                                                 └▶ 이걸 읽음: carmaster API · mirror-to-firestore
                                                                    · check-atom-invariants · 정제 · connectors · spring
```

- 앱·API·미러는 Firestore 를 «직접 안 읽는다» — 전부 **파생 캐시 JSON** 을 읽는다.
- JSON 은 `export-master-firestore-to-json.mts` 로 **사람이 손수 돌려야** 갱신된다(자동 아님).
- ⇒ **Firestore 를 고치고 export 를 안 돌리면 JSON(=런타임이 읽는 것)이 옛날 그대로 남는다.**

★이게 「백번 얘기해도 안 되네」의 «기계적» 정체다(2026-09-09 실측):
  Firestore vehicle_master 에 트림 27개를 채웠는데 export 를 안 돌려 JSON 이 안 바뀌었고,
  미러·검사기가 옛 JSON 을 읽어 **채운 트림이 파이프라인에 한 번도 안 닿았다.**
  export 를 돌리자마자 원자 트림 위반이 **276 → 220** 으로 줄었다(전파 56건).

부가로, Google 시트 「라이브 탭」(엔카 작업 시트)은 **정본이 아니라 수집 원천**이다 — 사람이 이름을 다듬는 작업대.
명명 게이트(`audit-live-master-name-copy`)가 이 시트를 본다. 시트↔Firestore 도 손으로 맞춰야 갈린다.

★**할 일 = «수동 전파»를 없앤다.** 둘 중 하나:
  ㉠ 미러·검사기·carmaster 가 **Firestore 를 직접** 읽게 한다(캐시 JSON 폐기), 또는
  ㉡ export 를 **파이프라인에 넣어**(hourly-sync 미러 «직전») 매 회차 자동 재생성.
  어느 쪽이든 **마스터를 고치면 «자동으로» 모든 소비처에 닿는다** — 이게 「한 문으로 나간다」의 실현.

## 1. 세 마스터 — 원천·속도·낟알이 셋으로 갈린다 (사장님 3분할 채택)

사장님 3분할이 옳다. 셋은 «어디서 오나 · 얼마나 자주 변하나 · 무엇 단위냐»가 전부 다르다:

| 마스터 | 담는 것 | 낟알 | 원천 | 변화속도 | 방향 |
|---|---|---|---|---|---|
| **차종마스터** | 트림·색상옵션·제원(연료·배기량·구동·인승) | 세부모델(모델 카탈로그) | 제조사 컨피규레이터 | 느림(모델 나올 때) | **쏜다(내려보냄)** |
| **정책원자** | 보험·계약·운전·기타 정책 | 공급사 | 정책탭(공급사 입력) | 느림 | **쏜다(내려보냄)** |
| **상품마스터** | «이 차» = 차종참조 + 개체(차번·주행·연식·실색) + 대여료 + 정책참조 | 차번(개체) | 공급사 시트/홈피 | 중간 | 받는다(참조) |
| **상태마스터** | 팔렸나·가용한가·계약중·검수 | 차번(개체) | 공급사 상태칸 | 빠름(매시간) | 받는다(오버레이) |

★**나의 유일한 보탬 = «쏘는 쪽»이 둘이라는 걸 못 박는 것.**
사장님은 정책을 상품마스터 안에 넣으셨는데, «정책원자»도 차종마스터처럼 **카탈로그(쏘는 쪽)**다
(「정책원자에 있는 걸 쏴준다」 — 사장님 2026-09-09). 그래서:

```
   ┌─ 차종마스터 (트림·제원) ──┐         쏜다(복사)
   │                          ├──▶  «이 차»(상품마스터) ──▶ 상태 얹기(상태마스터) ──▶ 원자
   └─ 정책원자 (정책) ─────────┘         ▲                                              │
                                    차번으로 합류                          한 문으로 나감(resolveAtom)
```

- **카탈로그(차종마스터·정책원자)는 «주는 쪽»** — 차가 여기서 «복사»해 간다. 차는 카탈로그를 **못 고친다**.
- **개체(상품·상태마스터)는 차번으로 «받는 쪽»** — 카탈로그를 참조하고, 자기 개체값(차번·주행·대여료)만 갖는다.
- 셋(+정책)이 **차번**으로 합쳐져 **원자 한 문서**가 되고, **한 문(resolveAtom)**으로 나간다.

## 2. 「한 문으로 들어오고 한 문으로 나간다」 — 두 개의 문

### 들어오는 문 (수집) — 마스터마다 «정본 한 곳 + 수집기 하나»
- 차종마스터: 정본 한 곳(§3). 수집기 = 제조사 컨피규레이터 인제스터(있는 데이터로 채움).
- 정책원자: 정본 = `policy` 컬렉션. 수집기 = 정책탭(공급사 입력) → `supplier-policy-link`.
- 상품·상태마스터: 정본 = `products` 원자. 수집기 = 공급사별 직접수집(`ingest-*`) + 미러(옛 공급사).
- ★**한 원자를 넷이 덮어쓰던 것을 끝낸다**(2026-09-08 버그). 각 필드는 «한 수집기»만 쓴다(소유 경계 = `OWNED_BY_INGEST`).

### 나가는 문 (뿌리기) — 소비자는 «오직» resolveAtom 을 읽는다
- finder(상품찾기)·판매시트(make-sample)·ERP·화이트라벨 = 전부 **원자에서만** 읽는다.
- 원자를 «다시 계산»하거나 «원문을 다시 읽지» 않는다(2026-09-01 finder 가 시트를 다시 읽어 대수가 튄 사고).
- 시트는 원자의 «투영»이다 — 원자에 없는 값을 시트가 만들지 않는다(사장님: 「원자에 수집된 내용만 시트에 쏴준다」).

## 3. 정본 = Firestore (이미 확정) · 남은 결정 = «수동 전파»를 어떻게 없애나

정본은 이미 **Firestore**(`vehicle_master`·`policy`·`products`)로 확정됐다(2026-09-08). 다시 정할 게 없다.
남은 결정은 **파생 캐시 JSON 의 «수동 전파»를 없애는 방법**(사장님 승인 사항):

| 안 | 방법 | 장점 | 단점 |
|---|---|---|---|
| **㉠ 직접읽기** | 미러·검사기·carmaster API 가 Firestore `vehicle_master` 를 직접 읽음. JSON 폐기 | 사본이 «하나»(진짜 SSOT) · 드리프트 원천 제거 | carmaster API 가 매요청 Firestore 읽음(캐시 필요) · connectors/spring 클라 fetch 를 API 경유로 |
| **㉡ 자동export** | export 잡을 hourly-sync 미러 «직전»에 넣어 매 회차 JSON 재생성 | 변경 최소(읽는 코드 안 바꿈) · 회차마다 자동 최신 | 사본은 여전히 둘(FS·JSON)이나 «항상 같음»이 보장됨 · 회차 사이 편집은 다음 회차까지 지연 |

**추천 = ㉡(자동export) 먼저, ㉠(직접읽기)는 다음 단계.** 근거: ㉡ 는 읽는 코드를 안 건드려 **당장 오늘 드리프트를 없앤다**
(위험 최소). 그 위에서 소비처를 하나씩 Firestore 직접읽기로 옮기면 캐시 JSON 을 최종 폐기할 수 있다.
정책원자·상품·상태는 이미 Firestore 직접이라 정합.

⚠ 실행 전 확인 하나(사장님): **세부등급 없는 모델**(예 G80 RG3)의 트림을 마스터에 «기본형»으로 둘까,
  아니면 원자를 «공란»으로 둘까? 지금 시트는 「기본형」, JSON 은 「런칭」으로 갈려 있다. 규칙5(트림∈마스터 or 공란)상
  둘 중 하나로 통일해야 한다 — 마스터에 「기본형」을 넣으면 그게 복사되고, 안 넣으면 공란이 정답이 된다.

## 4. 트림 복사 규칙 (사장님 「마스터에 있는 내용으로만 · 분명하게 복사」)

원자의 트림 = 다음 순서. **절대 지어내지 않는다**(「기본형」·노이즈 벗긴 조각 금지):
1. 원문을 차종마스터 행에 매칭(세부모델 확정).
2. 그 세부모델의 마스터 트림과 원문이 맞으면 → **그 마스터 트림을 복사**.
3. 마스터가 못 덮으면 → **트림 공란 + 경고**(검수대기). 사람이 «마스터를 채울지/매칭이 틀렸는지» 판단 → 마스터 채움 → 다음 회차에 복사됨.
- 검사 = `audit-atom-master-warnings.mts`(경고 리포트) · 게이트 = `check-atom-invariants`(트림∈마스터 or 공란).
- ⇒ `clean-trim.ts` 의 «노이즈 벗겨 core·기본형» 폴백은 **폐기**(추출 방식 = 사장님이 거부).

## 5-A. 코덱스 적대검증 (2026-09-09) — 「한 문」의 뜻을 교정하다

3분할은 옳다. 결함은 «마스터 개수»가 아니라 «책임이 무르다»는 것. 코덱스가 꼽은 가장 위험한 셋:

1. **상태에 writer 가 여럿, 우선순위가 상충** — 출고불가·계약중·노출여부가 «실행 경로»에 따라 달라진다.
   ⇒ 공급사 가용상태와 ERP 계약잠금은 «다른 사실»이니 각각 보존하고, **최종 판매가능상태는 «한 함수»에서만 계산**한다.
   (지금처럼 같은 상태 필드를 여러 규칙이 덮으면 정보가 소실된다.)
2. **판매시트·ERP 가 «별도 정본 경로»** — Firestore 원자를 고쳐도 RTDB 정책·로컬 override·시트 재조회·발행순서
   때문에 최종이 달라진다. `hourly-sync` 는 미러 실패도 경고만 남기고 발행을 계속하고, ERP(⑯전)가 최종시트보다 먼저 돈다.
3. **트림 규칙이 «쓰기 게이트»로 강제되지 않음** — `cleanTrim` 한 곳을 고쳐도:
   - 직접수집이 아직 `snap.trim_name || row.trim || '기본형'` (`ingest-supplier-to-firestore.mts:461`) — 기본형 재유입.
   - merge 시 `strip()` 이 «빈 문자열을 버린다»(`:426,:745`) — 공란으로 고쳐도 «기존 오염을 못 지운다».
   - 규칙5는 `warn`이고 마스터 트림이 비면 아예 검사 안 함 — 진짜 게이트가 아니다.

★코덱스가 교정한 「한 문」의 정의 (이게 사장님 「한 곳으로 들어오고 한 곳에서 나간다」의 정확한 구현):
- **들어오는 한 문 = 「공급사별 파서 하나」가 아니라 «최종 쓰기 경계 하나».** 수집기가 여럿이어도 «관측값을 제출»만 하고,
  **소유권·시각·명시적 삭제·검증을 한 곳에서 판정**해 원자에 쓴다. (그래야 넷이 서로 덮던 게 끝난다.)
- **나가는 한 문 = resolveAtom 이 «상품 전체 출력»을 돌려준다**(완전한 읽기 모델). 일부 조인만 공통화하면 나머지 소비처가 재해석한다.
- **자동export(㉡)의 완료조건**엔 «회차별 마스터 버전 고정·export 실패 시 중단·최종 쓰기 이후 검증·배포 소비처까지 전달»이
  빠져 있다(carmaster API 는 1시간 캐시). export 단독으론 부족 — 발행 순서까지 봐야 한다.

## 6. 실행계획 (단계별 — 회귀 없이)

★사장님 최대 고민 =「고쳐놓으면 또 바뀐다」. 그래서 **원천을 막기 «전»엔 원자를 안 비운다**(비우면 다음 회차에 되돌아옴).

- **1단계 — 트림을 «쓰기 경계»에서 강제**(회귀 차단):
  ① 직접수집(`ingest-supplier-to-firestore` 등)의 `|| '기본형'` 폴백 제거 → cleanTrim(복사 or 공란) 경유.
  ② merge 가 «명시적 공란»을 쓰도록(빈 문자열도 삭제 의도로 반영) — `strip()` 우회 경로 하나.
  ③ 정규화기(`clean-atom-trims --apply`)를 «모든 수집 뒤·발행 앞» 한 단계로 파이프라인에 넣는다.
  ④ 그 «다음에» 현재 220 「기본형」을 비운다 → 이제 다음 회차에도 안 돌아온다.
- **2단계 — 정본 전파 자동화(㉡)**: export 를 미러 «직전»에, 실패 시 회차 중단. (그 뒤 ㉠ 직접읽기로 캐시 폐기.)
- **3단계 — 상태 한 함수화 ✓(2026-09-09)**: `lib/domain/atom-status.ts resolveStatus` 로 mirror·ingest·heal 통합. 로직 동일(8케이스 대조).
  ★**계약 우선(정산원장 맨 먼저) 구현(2026-09-09)**: 사장님 「정산원장에 계약이 올라가면 맨 먼저 확인, 계약이 이긴다.」
    - resolveStatus: `locked` 있으면 공급사 「출고가능」이 못 덮는다 — 완료(출고불가)면 숨기고 아니면 계약중(선점).
    - ingest: 잠금 시 base=pin.vehicle_status(우리가 아는 현 상태). heal: 락 있으면 상태를 계약상태로 강제(clobber 복구).
  ⚠ **아직 «airtight» 아님(Codex FAIL, 정산 도메인·컷오버와 얽힘)** — 아래 셋은 이 파이프라인만으로 못 닫는다:
    ① 수집 레이스: ingest 가 pin 읽은 «뒤» 계약이 올라가면 그 회차는 락을 못 본다(재읽기/쓰기가드 필요).
    ② 락 저장소 갈림: 락이 RTDB(app flag=rtdb)·Firestore(mark-contract) 양쪽 — 파이프라인이 읽는 한 곳으로 모아야(=RTDB 컷오버 몫).
    ③ 정산엔진 취소경로: `settlement-engine.ts:277` 이 상태가 계약중/출고불가일 때만 락을 푼다 — clobber 뒤 취소면 락이 남아 «계약중에 갇힘». (정산세션 파일)
    ⇒ 우선순위는 사장님 규칙과 일치(판 차 재노출 < 팔 차 잠깐 숨김). airtight 는 정산세션 + 컷오버 조율 필요.
  ✔ 다른 상태 writer 는 «별도 도메인/레거시»라 통합 대상 아님 — mark-contract(계약잠금=정산 소유) · RTDB writer(폐기 경로) · retire(원천이탈 이유 별도).
- **4단계 — 나가는 한 문**: 소비처(finder·make-sample·ERP)가 resolveAtom «완전 출력»만 읽게. 원문 재읽기·재계산 금지.
- **마스터갭 4건**(아반떼 인스퍼레이션 등)·**세대갈림 19건**(그랜저 IG/GN7 등)은 사람 검수 후 마스터 채움/매칭 교정.

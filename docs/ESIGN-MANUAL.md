## 2. 필수값 — 「비어 있음」과 「없음」은 다르다

빈칸은 «직원이 안 채웠다»로 읽히고, `0원`은 «그렇게 합의했다»로 읽힙니다.
그래서 **보증금 0원 계약도 `0` 을 명시로 받습니다.**

### 없으면 못 보냄

| 값 | 비고 |
|---|---|
| 차명 | |
| 차량번호 | **신차라 아직 없으면 「미정」** 이라고 적으면 통과 |
| 대여기간 | 1~120개월 |
| 월 대여료 | 없으면 `0` |
| 보증금 | 없으면 `0` |
| 운전자 연령 · 약정주행거리 · 특약 확인(있음/없음) | |
| 렌터카사 · 고객명 · 연락처 · 계약 정책 · 납부 조건 | |

### 없어도 보냄

```
차대번호 · 연식 · 주행거리 · 연료 · 배기량 · 구동방식 · 승차정원
색상 · 선택 옵션 · 차량가액 · 비고
```
→ **안 적으면 ERP 값이 그대로 나갑니다.** 발송 화면 자리표시에 `ERP: 가솔린` 처럼 보입니다.

### 고객 식별·매출증빙

> ### ★2026-08-29 사장님 결정 — 주민등록번호를 «다시» 받는다
> 「우리 저신용이라 특히 필요하다. 기존에도 계약서로 수집했다. 보완 걸어서 수집한다.」
>
> **왜** — 저신용 손님이라 채권 추심이 실제 업무다(스위치 미수 68건 7,352만 · 위약금 채권 49건 3.05억).
> 주민번호가 없으면 **소송은 이겨도 돈을 못 받는다** — 재산조회·압류를 법원과 제3채무자가 주민번호로 한다.
>
> **⚠ 되돌릴 때 «반드시» 같이 가는 것** — 2026-08-29 확인: **계약자 주민번호의 암·복호 경로가 코드에서 사라져 있다.**
> `encryptRrn` 은 매출증빙 한 곳뿐이고 `decryptRrn` 은 아무 데도 없다.
> 이 상태로 주민번호만 받으면 **RTDB 에 평문으로 쌓인다.**
>
> ```
> ① 동의 고지 (freepass-esign-consents.ts)   ② 서식 라벨 ('개인'.id)
> ③ 화면 검증 8→13자리                       ④ 서버 검증 + 주민번호에서 연령 파생
> ⑤ ★저장 encryptRrn()   ⑥ ★봉인 decryptRrn()   ⑦ 봉인 스냅샷 배선
> ```
> ⑤⑥ 없이 ①~④만 하면 **평문 유출**이다.
>
> **남은 숙제 — 법령 근거.** 개인정보보호법 §24조의2 는 주민번호를 «법령 근거»가 있을 때만 받게 한다.
> 지금 확실한 근거는 **매출증빙(소득세법)** 하나뿐이다. 추심 목적은 근거가 아니다.
> **저신용 심사(신용조회)를 근거로 삼으려면** 조회기관·제공처가 특정된 신용정보 동의서가 필요한데,
> `consents.ts` 는 심사조건이 「신용조회」면 **발행 자체를 막고 있다**(조회기관이 특정되지 않아서).
> → **실제로 쓰는 신용정보 동의서 문구를 넣어 그 자리를 여는 것이 다음 일.**

- **개인**은 성명·주민등록번호·연락처·주소·운전면허번호를 받는다(위 결정). 저장은 암호화, 화면에는 생년월일만 보인다.
- 개인의 매출증빙은 휴대전화번호 또는 주민등록번호를 고객이 선택한다. 주민번호 선택값은 private 제출자료에만 `enc.v1.` 암호문으로 저장하며 계약서·공개 계약 노드·PDF에는 넣지 않는다.
- 운전면허증 사본은 주민등록번호 뒷자리를 가린 사본만 받는다.
- **법인**은 법인명·법인/사업자등록번호·서명자 성명·관계를 받는다. 위임받은 임직원은 위임장·재직증명서를 추가로 제출한다. 법인 서명자 신분증·셀카·주민번호는 받지 않는다.

## 3. 규격 규칙 — 깨면 안 되는 것

전부 실측으로 잡은 것들입니다. 되돌리면 같은 증상이 다시 납니다.

1. **글자 크기는 `:root` 의 `--fs-*` 9개만.** ERP `tokens.ts FS` 에서 인쇄용으로 한 단(−1px) 내린 값
2. **라운드는 `--radius`(4)·`--radius-card`(8) 둘뿐.** 칩 전용 3px 같은 걸 새로 만들지 않는다
3. **표는 전부 「머리띠 + 카드」.** 장별 override 금지 (칸 여백이 6/5/3.5px 세 갈래였던 적 있음)
4. **`.rhead` 여백을 장마다 바꾸지 않는다** — 문서의 시작선이다
5. **인라인 색으로 글자 크기를 바꾸지 않는다.** 부연은 `.dim` 클래스로
6. **`data-accent` 는 속성 맨 뒤에** — `class="section" data-contract-option="…"` 이 붙어 있어야 sim 통과
7. **약관 조문 참조는 「제17조 및 제18조」.** 축약(`제17조·제18조`)은 sim 이 막고, **주석에 써도 걸린다**
8. **새 `data-field` 는 `FIELD_MAP` 에 등록**
9. **발송 화면에서 받는 값은 `ISSUE_INPUT_FIELDS` 에 등록** — 빠지면 입력해도 말없이 버려진다
10. **세로 간격은 하나의 사다리** — 머리띠→표 0 · 표→그 표의 ※ 1.2mm · 블록→블록 5mm · 섹션→섹션 8mm
11. **한 줄짜리를 표로 세우지 않는다.** 표 밑 부가 설명(※)으로
12. **파란 안내 박스를 잇달아 쌓지 않는다.** 단계 안내는 «가이드»지 알림이 아니다

## 4. 함정 — 겪은 것

| 증상 | 진짜 원인 |
|---|---|
| 보증금 있는 계약이 「계약서 만들기」가 영원히 비활성 | `draftInputRecord` 가 `contract_draft` 를 안 실어 회차 선택이 검증기에 안 닿았다 |
| 발송 화면에서 입력했는데 계약서에 안 찍힘 | `ISSUE_INPUT_FIELDS` 허용목록에 없으면 **말없이 버려진다** |
| 표 칸 「없음」만 이웃보다 작게 인쇄됨 | `[style*="color:var(--mute)"]` 규칙이 **인라인 색을 근거로 크기까지** 줄였다 |
| 약관 하단이 매 장 15~24mm 씩 빔 | 되돌림 판정이 «바닥에 닿음»을 «넘침»으로 오인해 잘 채운 배치를 매번 폐기 |
| 폰트가 이상해 보임 | 파일(`file://`)로 열면 `/fonts/…` 절대경로라 **Pretendard 가 안 붙는다.** 반드시 서버로 |
| 「넘침 0」인데 실제로 글이 잘림 | `.pbody` 가 `overflow:hidden` 이라 `scrollHeight` 로는 못 잡는다 |
| 차량가액에 엉뚱한 값 | 재고 `vehicle_price` 는 **관리자 전용 원가**, 전자계약 쪽 같은 이름 필드는 **기간별 대여료 표**였다 |
| 신차 계약을 아예 못 보냄 | `erp_product` BLOCK 이 항상 걸렸다 — 신차는 ERP 재고에 없는 차다 |
| ERP 차량 고르면 차량번호를 못 고침 | 고르는 순간 입력칸이 사라져, 재고부터 바꾸러 가야 했다 |

## 5. 열린 질문 — 아직 못 정한 것

| # | 질문 | 걸린 사람 |
|---|---|---|
| Q1 | **부속서류 빈칸을 어떻게 채우나** — 인수증 12칸·연대보증 8칸·개인사업자 세금계산서 7칸. 인도 시점 정보라 계약 발송 시점엔 존재할 수 없는 것이 섞여 있다. 손으로 쓰는 서식으로 둘지 / ERP 입력을 붙일지 | 사장님 |
| Q2 | **보증금 빈칸을 저장 시점에도 구분할까** — 지금은 발송 화면에서만 막힌다. `N()` 이 빈 문자열을 0 으로 바꿔 저장하므로, RTDB 에 굳고 나면 「안 적음」과 「0원」을 구분할 수 없다 | Claude·Codex |
| Q3 | **약관 「정비공장」 ↔ 계약서 「정비점」** — 뜻은 같고 글자가 다르다. 약관을 「정비점(정비공장 등)」으로 넓힐지 | 사장님 |
| Q4 | **배포** — `main` 이 162+ 커밋 뒤라 밀면 다른 세션 작업까지 통째로 나간다 | 사장님 |
| Q5 | **작성 중 이탈** — 손님이 창을 닫으면 그때까지 쓴 게 사라진다(중간 저장 없음). localStorage 는 쓰면 안 된다(주민번호가 손님 폰에 평문으로 남고, 공용 기기면 다음 사람이 본다). 답은 «서버 부분 저장»이고 별건. 지금은 `beforeunload` 경고만 있다 | Codex |
| Q6 | **주민등록번호 보안 마무리** — 매출증빙에서 주민번호를 선택할 때만 AES-256-GCM(`enc.v1.`)으로 private node에 저장한다. 키 등록은 확인됐고, 평문 과거자료 이관·감사로그 점검은 남았다 | Codex |

### 손님 확인 원칙

- 손님 여정은 **개인 7단계·법인 5단계**다. 개인은 요약 확인 → 개인정보 입력 → 신분증 촬영 → 본인 셀카 → 세부계약·약관 → 부속서류 → 전자서명 순서이며, 법인은 신분증·셀카 단계를 받지 않는다. 완료 계약서는 제출 뒤 승인·봉인되면 같은 링크에서 다시 본다.
- 손님에게는 요약을 먼저 보여 주고, 차량·기간·금액, 결제·만기, 운전자·보험, 사고·중도해지의 **4개 묶음**은 세부계약·약관 단계에서 한 번만 확인받는다.
- 각 묶음 안의 실제 계약값은 모두 화면에 표시하며, 이 한 번의 확인 시각은 제시된 조건별 진행기록에도 같은 시각으로 남긴다. 조건을 보지 않은 것처럼 개별 확인을 만들어 내지 않는다.
- A4 미리보기나 중복된 「모바일 계약서 전체보기」는 고객 작성 중에 두지 않는다. 웹에 표시한 세부 계약과 전문 약관을 끝까지 확인한 뒤 동의·서명하며, 세부조건 확인·약관 열람 완료·동의·서명·제출 시각은 봉인 대상이다.

| 무엇 | 상태 |
|---|---|
| **계약자 주민번호 암호화 경로** | **없음** — `encryptRrn` 은 매출증빙 한 곳뿐, `decryptRrn` 은 아무 데도 없다. 주민번호를 다시 받기로 했으므로(§2) **이걸 먼저 붙여야 한다.** 안 붙이면 평문으로 쌓인다 |
| 신용조회 계약 발행 | **막혀 있다** — 조회기관·제공처가 특정된 신용정보 동의서가 없어서. 저신용을 다루는데 그 계약을 못 낸다(§2) |
| 미커밋 50개 파일 | 커서·코덱스 작업분. 정리 전에는 배포하지 않는다 |
| `FREEPASS_RRN_KEY` | Vercel 세 환경과 `.env.local` 등록 확인. 주민번호 매출증빙 선택 시에만 fail-closed 암호화에 사용 |

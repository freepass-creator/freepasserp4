# FreepassERP4 조직·역할·권한 기준

작성일: 2026-07-26  
상태: 권한 구현의 기준 문서(SSOT)

## 1. 기본 원칙

1. 권한은 `역할(role) × 소속 조직(org) × 데이터 귀속(scope) × 행위(action)`로 판정한다.
2. 화면에서 버튼을 숨기는 것은 편의 기능일 뿐이다. 최종 권한은 Firebase Rules가 강제한다.
3. 관리자는 전체 데이터와 전체 기능에 접근할 수 있다.
4. 영업 조직은 `agent_channel_code`, 공급사 조직은 `company_code`를 소속 경계로 사용한다.
5. 개인 귀속은 Firebase `auth.uid`를 사용한다. `user_code`는 표시·검색용 식별자이지 인증 기준이 아니다.
6. 계약과 채팅에는 생성 시점의 조직 코드와 담당자 UID를 기록하고, 생성 후 임의 변경하지 못하게 한다.
7. 조직 직원의 퇴사·이동 이후 과거 데이터 접근은 현재 소속이 아니라 별도 이관 절차로 처리한다.

## 2. 표준 역할

| 표준 역할 | 저장 role | 조직 범위 | 개인 범위 |
|---|---|---|---|
| 플랫폼 관리자 | `admin` | 모든 조직 | 모든 사용자 |
| 영업채널 관리자 | `agent_admin` | 자기 `agent_channel_code` | 채널 소속 전체 영업자 |
| 영업채널 직원(영업자) | `agent` | 자기 채널 정보만 | 자기 `auth.uid` |
| 공급사 관리자 | `provider_admin` | 자기 `company_code` | 회사 소속 전체 직원 |
| 공급사 직원 | `provider` | 자기 `company_code` | 개인 제한 없이 회사 업무 수행 |

`agent_manager`는 신규 사용을 중단한다. 기존 값은 마이그레이션 전까지 `agent_admin`과 동일하게 해석한다.

## 3. 데이터 귀속 기준

| 데이터 | 영업 측 귀속 | 공급사 측 귀속 |
|---|---|---|
| 채팅방 | `agent_uid`, `agent_channel_code` | `provider_company_code` |
| 메시지 | 방의 귀속을 상속, `sender_uid` 기록 | 방의 귀속을 상속, `sender_uid` 기록 |
| 계약 | `agent_uid`, `agent_channel_code` | `provider_company_code` |
| 건별 정산 | `agent_uid` 또는 `agent_code`, `agent_channel_code` | `provider_company_code` |
| 재고·정책 | 읽기만 가능 | `provider_company_code` |
| 회원 | 자기 자신 또는 채널 범위 | 자기 자신 또는 회사 범위 |

## 4. 업무별 권한

### 상품찾기

| 역할 | 권한 |
|---|---|
| 플랫폼 관리자 | 전체 상품 및 관리자용 원가·VIN·수수료 확인 |
| 영업채널 관리자 | 판매 가능한 전체 공개 상품 조회·공유, 내부 원가 비공개 |
| 영업자 | 판매 가능한 전체 공개 상품 조회·공유, 내부 원가 비공개 |
| 공급사 관리자·직원 | 판매 가능한 전체 공개 상품 조회, 자기 회사 상품의 비공개 원가·VIN·메모 확인 |

### 계약문의·채팅

| 역할 | 조회·응대 범위 |
|---|---|
| 플랫폼 관리자 | 모든 방 조회·응대 |
| 영업채널 관리자 | 자기 채널 소속 영업자들의 모든 방 조회·응대 |
| 영업자 | `agent_uid === auth.uid`인 자기 방만 조회·응대 |
| 공급사 관리자·직원 | `provider_company_code === company_code`인 회사의 모든 방 조회·응대 |

모든 메시지는 실제 작성자의 `sender_uid`, 이름, 역할을 기록한다. 조직 공유 응대라도 작성자 추적은 개인 단위로 유지한다.

### 계약진행

| 역할 | 조회 범위 | 수정 범위 |
|---|---|---|
| 플랫폼 관리자 | 전체 | 모든 단계·상태 교정 |
| 영업채널 관리자 | 자기 채널 전체 | 영업 측 단계 처리, 채널 소속 계약 지원·인계 |
| 영업자 | 자기 계약 | 영업 측 단계 처리 |
| 공급사 관리자·직원 | 자기 회사 전체 | 공급사 측 단계 처리 |

계약의 영업자·영업채널·공급사·상품·금액·요율 스냅샷은 생성 후 고정한다. 담당자 변경은 일반 수정이 아니라 감사 로그가 남는 관리자용 인계 기능으로만 수행한다.

### 계약 건별 정산

| 역할 | 조회 범위 | 표시 금액 | 상태 변경 |
|---|---|---|---|
| 플랫폼 관리자 | 전체 | 공급 수수료·영업 지급·순수익 전체 | 가능 |
| 영업채널 관리자 | 자기 채널 전체 | 채널 소속 영업 지급액 | 불가 |
| 영업자 | 자기 계약 | 자기 지급 예정·완료액 | 불가 |
| 공급사 관리자 | 자기 회사 전체 | 회사 청구 수수료·정산 상태 | 불가 |
| 공급사 직원 | 자기 회사 전체 | 계약 처리에 필요한 정산 상태, 회사 청구액 | 불가 |

정산 확정·보류·환수 결정은 플랫폼 관리자만 수행한다. 영업 지급률과 플랫폼 순수익은 공급사에 노출하지 않는다.

### 재고관리·정책관리

| 역할 | 권한 |
|---|---|
| 플랫폼 관리자 | 전체 회사 재고·정책 생성, 수정, 삭제, 복원, 강제 교정 |
| 영업채널 관리자·영업자 | 재고관리 화면 접근 불가, 상품찾기에서 공개 필드만 조회 |
| 공급사 관리자 | 자기 회사 재고·정책 전체 관리, 대량 업로드·동기화·삭제·복원 |
| 공급사 직원 | 자기 회사 재고 등록·수정·상태변경·문의 응대. 회사 연결 설정과 직원 관리는 불가 |

공급사 직원도 회사 재고의 일상 업무를 모두 처리할 수 있다. 관리자 전용 범위는 직원 관리, 회사 설정, 대량 삭제·복원 같은 조직 관리 및 고위험 작업이다.

### 회원·조직관리

| 역할 | 권한 |
|---|---|
| 플랫폼 관리자 | 전체 회원 승인, 역할·소속 변경, 조직 생성·수정 |
| 영업채널 관리자 | 자기 채널 직원 조회·초대·비활성화. 플랫폼 관리자나 타 조직 변경 불가 |
| 영업자 | 자기 프로필만 수정 |
| 공급사 관리자 | 자기 회사 직원 조회·초대·비활성화. 회사 코드·플랫폼 역할 변경 불가 |
| 공급사 직원 | 자기 프로필만 수정 |

### 감사·휴지통·개발도구

- 플랫폼 관리자: 전체 접근
- 조직 관리자: 자기 조직의 업무 감사 로그와 허용된 복원 기능만 접근
- 일반 직원: 자기 행위 이력 조회만 허용하거나 화면 미노출
- 개발도구와 전역 데이터점검은 플랫폼 관리자 전용

## 5. 권한 판정 규칙

```text
platform admin:
  role == admin

sales channel admin:
  role in [agent_admin, agent_manager]
  AND record.agent_channel_code == user.agent_channel_code

sales agent:
  role == agent
  AND record.agent_uid == auth.uid

provider admin/staff:
  role in [provider_admin, provider]
  AND record.provider_company_code == user.company_code
```

단, 역할별 계약 단계 필드와 민감 금액은 위 데이터 접근 판정 뒤에 추가로 제한한다.

## 6. 현재 구현과의 차이

1. `lib/auth-session.ts`는 화면 호환용 3역할과 별도로 `rawRole`을 보존한다.
2. `lib/domain/authorization.ts`가 `admin`, `agent_admin`, `agent`, `provider_admin`, `provider`와 레거시 `agent_manager`를 중앙 판정한다.
3. 영업 직원은 개인 UID, 영업채널 관리자는 채널, 공급사 직원·관리자는 회사 범위로 조회한다.
4. Firebase Rules에도 `provider_admin`, `agent_admin`, `agent_manager`의 조직 범위가 반영돼 운영 게시됐다.
5. 정산 금액은 신규 데이터부터 R1/R2/admin private 노드로 물리 분리해 역할별 병합한다.
6. 아직 남은 차이는 공급사 직원과 관리자의 고위험 기능 분리, 역할 부여·초대 UI 세분화다.
7. 자동 권한 시뮬레이션은 통과했지만 5개 실제 역할 계정의 브라우저 격리 테스트는 남아 있다.

## 7. 구현 순서

완료:

1. 역할 스키마·레거시 매핑·`rawRole` 기반 중앙 권한 helper
2. 채팅·계약·정산 어댑터의 개인/채널/회사 범위 쿼리
3. Firebase Rules 역할·조직 판정과 운영 게시
4. 메뉴·버튼·정산 금액 표시 경계
5. 역할 시뮬레이션과 Rules Emulator

오픈 후:

1. 공급사 직원과 관리자 사이의 대량 삭제·복원·회사설정 권한 분리
2. 역할 부여·초대·비활성화 UI 세분화

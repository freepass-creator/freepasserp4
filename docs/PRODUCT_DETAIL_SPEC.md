# 매물 상세 — 무엇을 보여줄 것인가 (2026-08-28 실측)

## 사장님 지적

「상세 내용이 의미 없이 채우기 했거나 내용에 안 맞게 있다」
「손오공은 반납형·인수형을 확실하게 구분해서 보여줘야 한다」

둘 다 사실이었다. 실측으로 원인을 갈랐다.

## 원인 ① — 목록의 59%가 정책이 없어 두 섹션이 빈 껍데기

`보험조건`(5줄) · `계약조건`(10줄)은 **정책에서 값을 가져온다**(`policyOf(p)` → `p._policy`).
정책이 안 붙으면 15줄이 통째로 빈칸·「미입력」으로 렌더된다. 그게 «의미 없이 채우기»의 정체다.

| 공급사 | 대수 | 정책 연결 |
|---|---|---|
| **손오공 RP012** | **403** | **0** |
| **이안카 RP031** | **82** | **0** |
| 그 밖 15곳 | 331 | **331 (100%)** |
| 합계 | 816 | 331 (41%) |

즉 **485대(59%)가 정책 미연결**이고, 그 매물을 열면 두 섹션이 빈 표로 뜬다.
정책 자체는 멀쩡하다 — 54건이 있고 필드도 52개(대인·대물·자손·자차·무보험·보증금·연령·경력·
카드결제·정비…)를 다 갖고 있다. **연결만 안 돼 있다.**

> ⚠ 측정 주의 — `_policy` 는 상품에 «저장»되지 않고 조회 시 **조인**된다
> (`rtdb-records.toV4Record` 의 joinMap). raw RTDB 를 그냥 읽고 세면 전 건이 빈 것으로 보인다.
> 실제로 그렇게 한 번 「100% 빈칸」이라는 틀린 수를 냈다. 반드시 조인 후에 세야 한다.

### 결정 (2026-08-28 사장님)

**빈 줄은 감추지 않는다. 「미입력」으로 적는다.**
줄을 없애면 «이 매물엔 원래 그 항목이 없다»로 읽힌다. 있어야 할 칸이 안 채워진 것과
애초에 해당 없는 것은 다르다. 영업자가 「이건 아직 안 받은 값이구나」를 알아야 공급사에 물어본다.

### 할 일
1. 빈 값을 **전부 「미입력」으로** 통일한다. 지금은 어떤 줄은 빈칸, 어떤 줄은 「미입력」이라 제각각이다.
2. 손오공·이안카에 정책을 연결한다(`apply-policy-link` 계열 — 이 둘만 빠졌다).
   연결되면 485대의 「미입력」이 실제 값으로 바뀐다.

## 원인 ② — 손오공은 «두 상품»인데 한 표에 섞여 보인다

손오공 403대 중 **386대가 인수형 가격까지 갖고 있다.** 반납형·인수형은 같은 차의 다른 상품이다
(만기에 차를 돌려주느냐 사느냐 — 대여료도 보증금도 다르다).

코드에는 이미 갈라져 있다:
- `ACQUISITION_VARIANT = '인수형'` · 가격 키 `${개월}_인수형`
- `acquisitionPriceList(p)` 가 인수형만 따로 모으고, 표준(반납형) 표에서는 제외한다
  (2026-08-18 사고 — 반납형이 없는 60개월에 인수형 대여료가 표준가처럼 찍혔다)

**남은 건 화면이다.** 갈라 놓기만 하고 «무엇이 무엇인지»를 말해 주지 않는다.

### 할 일
- 가격 영역을 **두 표로 명확히** 나눈다. 제목을 붙인다 — `반납형(만기 반납)` · `인수형(만기 인수)`.
- 둘 다 있으면 탭이 아니라 **위아래 두 표**로 둔다. 영업자는 둘을 «비교»해서 답한다.
  탭으로 감추면 손님이 「인수하면 얼마예요?」 물을 때 화면을 바꿔야 한다.
- 인수형만 있거나 반납형만 있으면 그 표 하나만. 제목은 그대로 붙인다.
- 상단 요약바의 최저가는 **반납형 기준**으로 하고, 인수형이 있으면 칩으로 «인수형 있음» 표시.

## 확정 — 상세에 무엇을 보여줄 것인가 (2026-08-28)

**순서는 지금 그대로 둔다**(사장님 「순서는 큰 이슈 없어」). 사진이 맨 위인 것도 그대로다 —
한 번 «영업자는 가격부터 본다»며 사진을 아래로 내리자고 했는데 사장님이 바로잡았다:
「**영업자도 사진부터 봐야지**」. 차를 파는 사람도 차를 먼저 본다.

정리할 것은 **각 섹션의 내용**이다 — 영업자·손님이 보는 화면에 «사람이 읽을 값»만 남긴다.
코드는 필요 없다(사장님 「코드 같은 건 필요 없다는 거지」).

```
사진 → 차량스펙 → 대여료조건 → 보험조건 → 계약조건 → 기타사항(관리자)
```

| 섹션 | 영업자·손님이 보는 내용 |
|---|---|
| 사진 | 그대로 (맨 위) |
| 차량스펙 | 차명 · 차량번호 · 연식/주행 · 동력 · 색상 · 차종 · 차량가격 · 선택옵션(칩) |
| 대여료조건 | **반납형 표 · 인수형 표를 갈라서** (손오공 386/403이 인수형을 들고 있다) |
| 보험조건 | 대인 · 대물 · 자손사고 · 무보험상해 · 자차손해 (보장한도 · 면책) |
| 계약조건 | 심사 · 주행약정 · 보증금 · 카드결제 · 결제/위약 · 연령 · 경력 · 운전자범위 · 지역/탁송 · 정비/대차 |
| 기타사항 | **관리자만.** 공급사 차명 · 공급사 옵션 · 최초등록 · 특이사항 · 차령/차대 · 등록증 · 정책 |

### 걷어낸 것

- **「상품」 줄** — 지웠다. `RP014_188호3065` 는 공급사코드 + 차량번호를 붙인 것이라
  위 「차량번호」와 같은 말을 두 번 한다. 기계가 매물을 세는 열쇠지 사람이 읽는 값이 아니다.
- **정책코드** — 관리자에게만 남긴다. 영업자·손님 화면엔 원래 안 나갔다(`isAdmin` 블록).

### 확인한 것 — 코드가 새는 자리는 없다

`scripts/audit-detail-codes.mts` 로 매물 816대 × 영업자·손님 두 화면의 모든 줄을 훑어
`RP0xx` · `pol_xxx` · `veh_xxx` · 언더바 식별자를 찾았다. **0건.** 사장님이 본 코드는
전부 관리자 전용 「기타사항」에 있던 것이다.

## 빈 값은 「미입력」으로 (2026-08-28 사장님)

**빈 줄은 감추지 않는다.** 줄을 없애면 «이 매물엔 원래 그 항목이 없다»로 읽힌다.
있어야 할 칸이 안 채워진 것과 애초에 해당 없는 것은 다르다.
영업자가 「아직 안 받은 값이구나」를 알아야 공급사에 물어본다.

## ★진짜 문제 — 계약조건·보험조건이 «전부 같은 값»이다

빈 게 문제가 아니었다. **816대 전부가 똑같은 「프리패스 표준」을 보이고 있다.**

정책이 하나도 안 붙어 있다. 매물이 든 `policy_code` 와 정책 노드의 키가 서로 다른 세대다:

```
매물이 가리키는 코드     pol_freepassstd 244대 · pol_7xf8x9ygfn 25대 … · (빈칸) 514대
실제 정책 노드의 키      FP-RP012-RENT · FP-RP004-RENT · POL-0001 · RP031_S01 …
                        → pol_ 로 시작하는 정책은 단 한 건도 없다
```

erp3 절연 때 정책 코드를 새로 발급했는데(`FP-{공급사}-RENT`) **매물이 든 옛 코드는 그대로**다.
그래서 조인이 전량 실패하고, `applyPolicyDefaults` 가 빈 정책을 프리패스 표준으로 채워
화면에는 «값이 있는 것처럼» 보인다. 이게 사장님이 본 「의미 없이 채우기 했다」의 정체다.

영업자가 이 값을 그대로 손님에게 말하면 **그 공급사가 주지도 않은 조건을 약속하는 것**이다.
빈칸보다 나쁘다 — 빈칸은 물어보게 만들지만 이건 안 물어보게 만든다.

### 고치는 법

공급사별 정책이 이미 다 있다. 매물의 `provider_company_code` 로 `FP-{코드}-RENT` 를 걸면 된다:

```
798대  공급사 정책 있음 → 바로 연결 가능
 18대  PT-0023(12) · PT-0001(6) → 그 공급사 정책이 없다. 만들거나 미연결로 남긴다
```
